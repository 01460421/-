# 整體設計

## 一句話

靜態前端 + 九個無狀態的函式 + 一個私有的 Blob store。沒有帳號、沒有資料庫、沒有建置步驟。
後端不在的時候，前端退回單機模式，所有東西存在瀏覽器裡。

```
瀏覽器 ──────────────────────────────────────────────────────────────
  index.html
  assets/js/app.js      手提箱（localStorage）、路由、九個房間
  assets/js/plus/*.js   放映廳、考核、搜尋、名詞、徽記、共鳴、同步…
  sw.js                 離線快取（/api 不經過它）
        │ fetch
        ▼
Vercel CDN ── 靜態檔；GET /api/board、/api/pulse、/api/health 依 s-maxage 快取
        │
        ▼
api/*.js（每個檔案一個端點，只負責把請求交給 lib）
lib/*.js（驗證、頻率限制、讀改寫、清理）
        │ @vercel/blob（private）
        ▼
board/<k>.json   sys/site.json   sys/poll.json   case/<id>.json
```

## 前端

### 檔案怎麼分

原本是一個 28 萬字元的 `index.html`。這一版拆成樣式、畫家、腳本、資料、核心五塊，再加上 `plus/` 底下的模組。
拆開之後：

- 每個檔案可以各自快取，改一處不用整頁重抓。
- 頁面上沒有任何行內的 script，內容安全政策可以寫成 `script-src 'self'`。站上有使用者寫的字，這一條很重要。
- 仍然沒有建置步驟。全部是一般的 script（不是 ES module），用 `defer` 依序載入，所以直接雙擊 `index.html` 也打得開。

### 模組怎麼接上核心

`app.js` 把共用的東西放在 `window.__A`，並提供一個很小的事件匯流排：

```js
A.on('plate', ({ id, at, shot, narr }) => { … })   // 展間換了一張底片
A.emit('stamp', { id })
```

核心在關鍵的時刻發事件（`ready` `route` `leave` `hall` `viewer` `plate` `chapter` `stamp` `reveal` `tally`
`mineCard` `question` `item` `work` `case` `save` `import` `wipe` `board` `loaded` `posted` …），
模組聽事件、往畫面上加東西。新的房間用 `A.addRoom(name, sectionId, enter)` 登記，路由就認得。

開機放在最後一個檔案 `boot.js`：所有模組都掛好事件之後才 `A.start()`。

### 存檔

手提箱是一個 JSON，存在 `localStorage` 的 `nyjn.archive.v1`。v1 的欄位原封不動；
新模組的資料放在 `x` 底下，各自一格（`x.set` 設定、`x.fm` 放映進度、`x.qz` 考核、`x.ac` 徽記、`x.rd` 看過的底片、
`x.gl` 遇見的詞、`x.soc` 共鳴與草稿、`x.sy` 同步碼、`x.st` 來訪）。
讀進來時，`x` 只檢查「是不是乾淨的 JSON、有沒有超過大小」；每個模組用 `K.bag(name, 預設值)` 取自己的那一格，
型別不對的欄位會被換回預設值。所以從別的裝置匯入的存檔代碼，即使被改過，也只會讓某個欄位回到預設。

所有使用者寫的字，畫到畫面上一律用 `textContent`，沒有任何地方把它當 HTML。

### 放映廳

紀錄片不是影片檔。`film.js` 是一份腳本：每個鏡頭指定一個畫家（`paint.js` 裡的函式）和幾句旁白。
`cinema.js` 把腳本攤成一條時間軸，共 247 段：幕卡、章名卡、片名卡、每一段字幕，全長 27 分 25 秒。

時間的算法和原版紀錄片一模一樣：每段字幕 `1.4 + 字數 × 0.155` 秒（夾在 3 到 11 秒之間），超過四十四個字的旁白在最接近中間的句號拆成兩段，
每個鏡頭開頭留 0.7 秒、結尾留 0.9 秒的空白（暴雨的鏡頭是 1.3 和 1.4 秒，而且至少七秒），幕卡 6.5 秒、章名卡 7.5 秒。
之所以要一模一樣，是因為配樂是照這條時間軸剪的。`film.js` 的腳本和原版逐字相同，兩邊算出來的總長都是 1645.5 秒。

畫家的介面是 `P[name](ctx, t, W, H, U, args, k)`：`t` 是這個鏡頭已經過了幾秒（動態用），`k` 是旁白講到第幾句（分段顯示用）。
放映廳自己算這兩個數字，所以畫面的節奏跟著旁白走。每個鏡頭都很慢地推近一點；換鏡頭時，把上一格複製到另一張畫布上淡出。

### 配樂

原版的配樂是一條音軌（`assets/audio/score.mp4`，AAC，27 分 42 秒）：十七段，照章節剪好，比影片多十七秒的尾奏。
影片和音軌要對在一起，重點是**誰跟誰**。每動一次 `audio.currentTime`，耳朵就會聽到一次斷點，所以音軌是主時鐘：

- **平常播放時，影片跟著配樂走。** 放映廳每畫一格就問 `Score.clock()`「配樂唱到哪裡」，影片超前就放慢（最慢四分之一速）、落後就追上、
  差超過 1.5 秒才直接跳過去。音軌本身不動。畫面卡住、裝置很慢、分頁收到背景再回來，聲音都是連續的。
- **只有時間被人動過才定位音軌**：跳章、點逐字稿、上一句下一句，各一次。拖進度條時配樂先停，放開才定位一次。暫停再播放不定位。
- **配樂在起步、跳轉或緩衝時，影片停在原地等它**，最多三秒；等不到就先照自己的時鐘走，配樂回來時再接上（差很多才定位，六秒內最多一次）。
- **不是我們叫它停的暫停**（耳機拔掉、來電、系統的媒體鍵、手機把分頁收走）會讓影片一起停，回來按播放就一起接下去。
- **朗讀開著的時候**，影片的速度由朗讀決定（一句沒唸完就等），配樂不跟著停，只在換場次時對回那一場的開頭。
- 影片放完後，音軌把最後一段奏完。

第一版是反過來的：影片照自己的時鐘走，差超過 0.45 秒就把音軌拉回來。影片的時鐘在慢裝置上會落後（每格最多只算 0.1 秒），
於是音軌每一兩秒被拉回一次，聽起來斷斷續續。`npm run score` 把這些情境都跑一遍，並且數音軌被定位了幾次。

- 音檔只在第一次按下播放、而且配樂開著的時候才建立與下載，瀏覽器用分段請求邊抓邊播。service worker 不碰它。
- 載不到（離線、檔案不在）時，退回即時合成的環境音：雨、一組隨幕次變換的低鳴和弦、每句旁白一個單音。這也是原版的做法。
- 瀏覽器擋下自動播放時（直接用網址開在放映中的頁面），按鈕會變成「點此播放配樂」。
- 配樂響著的時候，館內的雨聲會先退到沒有，停了再回來。

### 聲音

`sound.js` 用 Web Audio 即時合成館內的雨聲與音效：三層濾過的雜訊是雨，偶爾一聲往上滑的正弦波是水滴。這一部分沒有任何音檔。
瀏覽器規定要有使用者操作才能出聲，所以上次開著的話，會等第一次點擊才開始。

## 後端

### 為什麼還是 Blob

v1 已經在用，站主不需要多設定任何東西。代價是 Blob 的操作有額度（Hobby 方案每月大約兩千次寫入、一萬次讀取），
所以整個後端的設計圍繞著「少碰儲存空間」：

| 做法 | 省了什麼 |
| --- | --- |
| `GET /api/board`、`/api/pulse`、`/api/health` 帶 `s-maxage`，由 CDN 快取 | 一百個人同時看接龍，十秒內只讀一次 Blob |
| 前端開機改問 `/api/health`（不碰儲存） | v1 每個訪客開頁面就讀一次 `board/h33.json` |
| 頻率限制的帳本併進 `sys/site.json`，一天一份 | v1 每個 IP 一個檔案，永遠不刪 |
| 共鳴、回報的名單直接記在那一筆資料上 | 不用多讀一份文件 |
| 共鳴、回報、投票、雲端存檔的頻率限制只在記憶體裡算 | 這些動作不會多寫一次 |
| 投票由前端累積 1.5 秒再送、整份一起送 | 選八個時刻不會寫八次 |
| 雲端同步只在按下按鈕時上傳 | 不會每改一個字就寫一次 |

自己剛寫入之後，前端會帶一個 `fresh=<id>` 重抓一次，跳過 CDN，所以作者馬上看得到自己的段落；
其他人最慢十秒後看到。

發一則接龍的成本大約是兩次讀、兩次寫：讀 `sys/site.json` 檢查停權與頻率 → 條件寫入 `board/<k>.json` →
條件寫入 `sys/site.json`（帳本、動態、計數）。

### 同時寫入

所有「讀 → 改 → 寫」都帶著 ETag 做條件寫入。兩個人同時接龍時，後寫的那個會被拒絕，重讀之後再做一次，最多六次。
本機的 `file` 和 `memory` 儲存實作了同樣的語意，測試裡有一題專門驗證兩個交錯的寫入都會落地。

### 身分與防護

- 沒有帳號。瀏覽器自己產生一把作者鑰匙，後端只存它的雜湊；IP 也只存加鹽的雜湊。
- 每個欄位都有長度上限，控制字元會被濾掉；請求本體有大小上限；有蜜罐欄位擋最笨的機器人。
- 同一個人十分鐘內重複送一樣的內容會被擋。
- 三個不同的人回報，那一則自動隱藏，等館主放行或刪除。
- 館主鑰匙用固定時間比較。沒設 `ADMIN_KEY` 時，館主端點一律回 404。
- `vercel.json` 設了 CSP、`nosniff`、`frame-ancestors`、HSTS 等標頭。

### 雲端同步的加密

```
同步碼（16 個字，80 bits，瀏覽器產生）
  ├─ SHA-256("nyjn.case.id|" + 同步碼)          → id，交給後端當檔名
  └─ PBKDF2-SHA256(同步碼, 150000 次)            → AES-GCM 金鑰，永遠不離開瀏覽器
手提箱 JSON ──AES-GCM──▶ 密文 ──▶ PUT /api/case { id, data }
```

後端拿到的只有 `id` 和密文。同步碼弄丟了，那一份就打不開；這是刻意的。
館主鑰匙不會被放進上傳的內容裡。

### 每日清理

`vercel.json` 排了一個每天一次的 `/api/cron/sweep`：刪掉 v1 留下的每 IP 計數檔、過期的雲端存檔，並重算全館計數。

## 驗證到哪裡

**跑過的**

- 後端：`npm test`，164 項，用記憶體儲存。包含每個端點、頻率限制、ETag／304、兩個交錯的寫入都會落地、v1 的舊資料讀得到也刪得掉。
  其中一組測試用真正的 `@vercel/blob` 2.9.0，把 HTTP 攔下來，確認送出去的網址和標頭（`?cache=0`、`x-if-match`、`x-allow-overwrite`）和預期一致。
- 前端：`npm run smoke`，86 項。桌機和手機寬度各把十八個位址走一遍，再用兩位訪客試接龍、共鳴、重複送出、投票。
  本機伺服器會套用 `vercel.json` 的標頭，所以內容安全政策是在開著的狀態下測的。
- 另外手動走過：雲端同步（上傳、另一台取回、版本衝突）、館主模式（鑰匙錯誤、佇列、清掉回報、設選件）、離線重新整理。

**在真正的 Vercel 和 Blob 上跑過的**（`npm run live`，32 項，對象是 `reverse-1999-art.vercel.app`）

- 寫入後帶 `fresh=` 立刻讀得到；`If-None-Match` 回 304。
- 條件寫入：三個人同時對同一則共鳴，三筆都算到；兩個人同時對一個還不存在的頻道發第一則，兩則都在。
- 重複送出回 409、別人刪不掉、沒設 `ADMIN_KEY` 時館主端點回 404。
- 雲端存檔的上傳、取回、版本衝突、刪除。
- CDN：瀏覽器收到的 `Cache-Control` 只剩 `public, max-age=0`（`s-maxage` 和 `stale-while-revalidate` 被 Vercel 留在自己那一層），第二次相同的讀取是 `HIT`。
- `/lib/*` 和 `package.json` 會被導到 404 頁；`dev/`、`test/`、`docs/` 沒有被部署。
- 用瀏覽器開正式網址：接上後端、沒有任何 script 或內容安全政策的錯誤、放映廳會播、離線重新整理可用。

**還沒有驗證的**

- 每日排程 `/api/cron/sweep` 實際被 Vercel 觸發時的行為（包含帶 `CRON_SECRET` 的情況）。
- 回報滿三人自動隱藏、館主的各項操作：這些只在本機測過，正式站上沒有設 `ADMIN_KEY`。
- 大量資料下的表現（單一頻道接近五百則、上千位投票者）。

**已知的限制**

- 每一次共鳴是一次讀加一次寫，是最耗 Blob 操作次數的功能。免費方案的額度很小（每月大約兩千次寫入）；付費方案的額度較高，超過的部分按用量計費。站上很熱鬧的話，先看這一項。
- 預覽部署和正式站連的是同一個 Blob store，在預覽網址上發的內容會出現在正式站。
- 計數是逐次加減的。重算的同時剛好有人發文，數字可能差一，下一次每日清理會修正。
- `@vercel/blob` 自己的相依套件裡有幾則 `npm audit` 警告（zod，經由 `@vercel/oidc`）。那是 SDK 內部的東西，這個專案沒有直接用到。

## 沒有做的事，以及原因

- **即時在線人數**：需要每個訪客每隔幾十秒寫一次，Blob 的額度撐不住。要做的話應該換成 Redis，這是另一個題目。
- **帳號登入**：這是一個同好網站，留名字就夠了。作者鑰匙加雲端同步已經能跨裝置。
- **建置工具與框架**：內容量和互動都還在「幾個檔案」能處理的範圍內，加進來只會讓部署變難。
