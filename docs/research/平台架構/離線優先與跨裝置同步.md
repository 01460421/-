
## area
離線優先的本地資料與跨裝置同步架構（跨平台 iOS / Android / 桌面 / 網頁 超大型考試準備 App）

## recommendation
走「三層分離」：GB 級題庫走唯讀、內容定址、可整檔置換的 CDN 分包（完全不進同步引擎）；使用者資料走自建的 append-only op-log 同步（UUIDv7 + HLC + per-user server_seq 游標）；筆記內文單獨用 Yjs CRDT 但把 update 當成一種 op 塞進同一條管線。儲存端用各平台原生 SQLite 綁定（GRDB / Room / better-sqlite3 / wa-sqlite+OPFS），materialize 與 SRS fold 的純函式邏輯抽成一份 Rust 共用核心（UniFFI + wasm）；PowerSync 是唯一值得認真評估的托管備案。

## rationale
關鍵判斷是：這個 App 裡三種資料的物理特性與衝突語意完全不同，硬塞進同一套同步引擎一定會付出代價。

（1）題庫與教材是 GB 級、唯讀、所有使用者共享、版本由你控制。它根本不需要「同步」，需要的是 CDN + 分包 + delta + 簽章。任何把它塞進 PowerSync bucket / Turso 同步庫 / WatermelonDB 的做法都是反模式：同步引擎會為每一列付出 metadata、變更追蹤與衝突處理的成本，而這些資料永遠不會被使用者改。把它拆出來之後，同步引擎要處理的資料量從 GB 掉到單一使用者幾十 MB，整個問題難度降一個量級。

（2）答題紀錄天生是 append-only 事件。兩台裝置各自答同一題，在領域語意上完全不衝突——兩筆都算數。但在 row-based 的 LWW 或資料庫層級的 rebase（Turso offline writes）裡，這會變成「同一列被兩邊改」的假衝突，你得寫規則把它救回來。反過來，用 op-log 就沒有衝突可解：集合聯集 + op_id 去重就結束了。這也直接回答了「離線三天怎麼合併」——根本不是合併，是把三天的事件補送上去，再讓所有裝置重放。

（3）複習排程（FSRS/SM-2）、錯題本、統計全部是衍生狀態。它們不該同步，該重算。只要 fold 函式是純函式、輸入是同一組事件、排序 key 是全序（HLC），所有裝置必然收斂到位元相同的結果。同步衍生狀態才是災難的來源：一旦同步了 due_at，兩台裝置的 due_at 誰對？

（4）只有筆記是真的需要文字合併，而它只佔資料量的極小部分。為了這一小塊上全庫 CRDT 不划算（Automerge 在大文件上比 Yjs 慢 10–50x 且記憶體大）；正確做法是把 Yjs update binary 當成一種 op payload，這樣同步管線只有一條。

扣住處境：
- 小團隊：所以只自建「協定」，不自建「資料庫」與「傳輸」。協定本身其實只有 push/pull 兩支 API 加一張表；真正的複雜度在 fold 與內容管線，那部分無論選哪個方案都跑不掉。
- 內容量大：所以內容層必須是可整檔替換的獨立 SQLite pack + ATTACH，刪一科等於刪一個檔，不需要 DELETE + VACUUM。
- 要離線：所以 op_log 是本機的唯一真相，寫入路徑不依賴網路，且純本機模式（不登入）是零成本的副產品——op 照寫，只是不 push；日後註冊一鍵補送即可。
- 要原生體感：所以 UI 各平台原生，共用的只有核心邏輯，不用跨平台 UI 框架換取一致性。
- 已有 HTML/React 資產：所以 Web 是一等公民而不是附贈品。這一條直接淘汰 SQLDelight/KMP 主線（wasmJs + OPFS 的 SQLite 支援仍不成熟），也讓 Rust core + wasm-bindgen 成為唯一能讓「一份 fold 邏輯跑四平台」成立的方案；同時桌面版可直接用 Tauri 包既有 React UI，省下一整個平台的 UI 成本。

## architecture
══════════════════════════════════════════
一、三層資料分離（整個架構的地基）
══════════════════════════════════════════

  【內容層】唯讀 · 全使用者共享 · GB 級 · 版本由你控制
    → CDN 分包 + Ed25519 簽章 manifest + delta + 內容定址圖片
    → 絕對不進同步引擎
  【事件層】append-only · 每使用者幾十 MB · 是唯一真相
    → op_log，UUIDv7 + HLC，push/pull 走 per-user 單調游標
  【衍生層】可重算 · 不同步 · 純函式 fold 的輸出
    → srs_card、wrong_book、stat_daily
  （筆記是特例：內文用 Yjs CRDT，但 update binary 以 op 形式走事件層）

══════════════════════════════════════════
二、目錄結構與模組邊界
══════════════════════════════════════════

/core-rs                       ← 唯一真相，四平台共用
  /schema      user.sql、content.sql、migrations/00xx_*.sql
  /ops         op 型別定義（serde + CBOR）、schema_ver 升級器
  /materialize op → 表（純函式，唯一副作用是同一個 write tx）
  /fold        FSRS fold、統計 fold（純函式，附 golden test 語料）
  /sync        push/pull 狀態機、批次切分、退避重試、HLC 產生器
  /content     manifest 驗簽、delta 套用、pack 安裝／逐出
  /crdt        yrs（Yjs 的 Rust 實作）封裝
  /ffi         uniffi（Swift/Kotlin）+ wasm-bindgen（Web）+ napi（桌面 Node）
/apps
  /ios         SwiftUI + GRDB。只做 UI、BGTaskScheduler、URLSession background
  /android     Compose + Room/SQLite。WorkManager、Foreground Service、DownloadManager
  /desktop     Tauri（直接重用 /apps/web 的 React 資產）
  /web         React（沿用既有 HTML/React 資產）+ wa-sqlite/OPFS + core.wasm
/server
  /sync-api    POST /sync/push、GET /sync/pull、GET /sync/snapshot
  /content-api manifest 產生、簽章、依 App 版本分流、CDN 失效
/pipeline
  /build-pack  題庫來源 → 確定性建置的 SQLite pack → delta → 簽章 → 上傳

共用：schema DDL、op 定義與序列化、materialize、fold、同步狀態機、
      manifest 驗證、delta 套用、衝突規則、HLC。
不共用：UI、背景任務排程、檔案下載器（必須用各平台原生下載器才能背景下載）、
      推播、金鑰保管（Keychain / Keystore / DPAPI / WebCrypto）。

理由：fold 一旦兩份實作，兩台裝置就可能算出不同的 due_at 或不同的答對數，
而這種 bug 在測試環境幾乎抓不到，只會在使用者手上出現。

  pack_id         TEXT PRIMARY KEY,   -- 'twgsat.math.b'
  content_version INTEGER NOT NULL,   -- 單調遞增
  min_app_schema  INTEGER NOT NULL,   -- 客戶端相容下限

  sha256          TEXT NOT NULL
);

CREATE TABLE question(
  qid        TEXT PRIMARY KEY,  -- 全域唯一、永不重用（UUIDv7）
  pack_id    TEXT NOT NULL,
  node_id    TEXT NOT NULL,     -- 知識點（跨包穩定）
  qtype      TEXT NOT NULL,     -- single|multi|cloze|essay
  stem_md    TEXT NOT NULL,
  options_json TEXT,
  answer_json  TEXT NOT NULL,
  explain_md   TEXT,
  difficulty   REAL,
  source     TEXT,              -- '113 學測 自然 第 12 題'
  revision   INTEGER NOT NULL,  -- 同一 qid 的內容修訂號

══════════════════════════════════════════
四、同步時序：誰先誰後
══════════════════════════════════════════

【寫入路徑（永遠不碰網路）】
  使用者送出答案
   → 在單一 write transaction 內：
       ① op_id = UUIDv7()、hlc = HLC.now()（單調保護）
       ② INSERT INTO op_log(..., server_seq = NULL)
       ③ INSERT INTO applied_op(op_id)
       ④ materialize：INSERT INTO attempt(op_id, ...)
       ⑤ UPDATE srs_card SET dirty = 1 WHERE qid = ?
     COMMIT
   → UI 立刻反映。網路狀態完全不影響此路徑。

【同步路徑：PUSH 先於 PULL】
  step 1  PUSH
    SELECT * FROM op_log WHERE server_seq IS NULL ORDER BY hlc
    分批：≤ 500 筆 或 ≤ 1 MB（zstd 壓縮後），每批帶 batch_id
    → POST /sync/push {device_id, batch_id, ops:[...]}
    ← {acks:[{op_id, server_seq}], tail_seq}
    → UPDATE op_log SET server_seq = ? WHERE op_id = ?

  step 2  PULL
    GET /sync/pull?since={pull_cursor}&limit=1000
    ← {ops:[...], next_cursor, tail_seq}   （伺服器過濾掉本機 device_id 的 op）

  step 3  APPLY（單一 write transaction）
    for op in ops ORDER BY server_seq:
        r = INSERT INTO applied_op(op_id) ON CONFLICT DO NOTHING
        if r.changed == 0: continue          ← ★ 冪等閘門，重複 op 直接跳過
        INSERT INTO op_log(...)              ← 保留遠端 op（重算與稽核需要）
        materialize(op)
        if op 影響某 qid: UPDATE srs_card SET dirty = 1 WHERE qid = ?
    UPDATE sync_state SET v = next_cursor WHERE k = 'pull_cursor'
    COMMIT
    ★ 游標只在 apply 成功 commit 後才前進 →
      at-least-once 傳輸 + 冪等套用 = effectively-once 語意。

  step 4  RECOMPUTE（可中斷、可分批、放背景）
    SELECT qid FROM srs_card WHERE dirty = 1 LIMIT 200
    for each qid:
        SELECT * FROM attempt WHERE qid = ? ORDER BY hlc      ← 全序輸入
        state = fold_fsrs(attempts)                            ← 純函式
        UPDATE srs_card SET ..., fold_upto_hlc = max_hlc, dirty = 0
    重複直到沒有 dirty。

  step 5  對帳（每日一次，或使用者手動）
    本機：SELECT COUNT(*), xor_checksum(op_id) FROM op_log WHERE server_seq IS NOT NULL
    伺服器：同樣的 count / checksum
    不一致 → 觸發區間二分比對，只重拉不一致的 seq 區間。

★ 為什麼 PUSH 先於 PULL：
  ① 三天的本機事件先取得 server_seq，之後任何重算都不會把它們誤判為「不存在」。
  ② PULL 回來的 op 與剛送出的本機 op 一起進入同一輪 recompute，只算一次。
  ③ push 回應直接帶回 tail_seq，pull 少一輪往返。

══════════════════════════════════════════
五、冪等如何保證（三道防線）
══════════════════════════════════════════

防線 1｜op_id 在使用者按下送出的那一刻於本機產生並落地（UUIDv7）。
  網路重送、App 被殺後重試、伺服器逾時後客戶端重傳，送的永遠是同一個 op_id。
  op_id 不是伺服器發的，所以「送出但沒收到回應」不會產生第二筆事件。

防線 2｜伺服器端唯一索引：
    INSERT INTO user_op(...) VALUES (...)
    ON CONFLICT (user_id, op_id) DO NOTHING
    RETURNING server_seq;
  若 DO NOTHING（重送），回查既有 server_seq 一併放進 acks →
  重送同一批得到完全相同的回應，客戶端無需區分「新寫入」與「重送」。

防線 3｜客戶端 applied_op 閘門與 materialize 在同一個 transaction 內，
  且只有 INSERT 成功（changed == 1）才執行 materialize。
  跨程序被殺也安全：要嘛整個 tx commit，要嘛整個 rollback。

★ server_seq 可見性空洞（最容易踩的坑）
  若多個 push 併發取號，可能出現 seq=105 已 commit、seq=104 還在交易中，
  另一台裝置此時 pull 到 105 並把游標推進 → 104 永遠拉不到。
  解法（擇一，建議 a）：
   (a) 每個 user 用 Postgres advisory lock 序列化 push。
       單一使用者的寫入量極低（一天幾百筆），完全不構成瓶頸。
   (b) pull 只回傳 server_seq < (已知安全水位) 的資料，水位取自 pg_snapshot 的 xmin。

══════════════════════════════════════════
六、如何避免重複計分（結構性保證，不靠紀律）
══════════════════════════════════════════

原則：任何計數都不准寫成 UPDATE stat SET n = n + 1。

  ① 權威來源永遠是 SELECT COUNT(*) FROM attempt WHERE ...
     因為 attempt 的主鍵是 op_id，同一事件在表裡結構上不可能出現兩次。
  ② stat_daily 只是快取，用「增量摺疊」維護：
       只摺 hlc > fold_upto_hlc 的 attempt，摺完把 fold_upto_hlc 推進。
       若亂序到達的舊 op 落在某天之前 → 把該 (day, subject) 的
       fold_upto_hlc 回退並重摺該天（一天的資料量很小，成本可控）。
  ③ 每晚（或每次 App 進背景時）跑一次「快取重建對帳」：
       用 COUNT(*) 重算當週的 stat_daily 並比對，不一致就以重算為準並回報遙測。
  ④ SRS 同理：srs_card 從來不是「被更新」的，而是「被重算」的。
     只要 fold 是純函式、輸入是同一組 attempt、排序 key 是全序 hlc，
     任意兩台裝置在收到相同事件集合後必然得到位元相同的 srs_card。
     這是收斂性的形式化保證，不是「應該會一樣」。

══════════════════════════════════════════
七、衝突解決規則表
══════════════════════════════════════════

  資料                     語意        規則
  ─────────────────────────────────────────────────────────
  答題事件                 append-only 集合聯集；op_id 去重。無衝突
  兩裝置同時答同一題       兩者皆有效  兩筆都保留（誠實反映），按 hlc 排序 fold
  SRS 卡片狀態             衍生        不同步、不合併，dirty → 重算
  統計 / 錯題本            衍生        同上，view 或可重建快取
  筆記內文                 需合併      Yjs CRDT，逐字元自動合併
  筆記標題 / 顏色 / 標籤   純量        欄位級 LWW by hlc（比字串，不比牆鐘）
  學習計畫（目標、考試日） 純量        欄位級 LWW by hlc
  收藏 / 釘選 / 標記       集合        Add-Wins OR-Set：remove 只能砍見過的 add_op_id
  刪除筆記                 tombstone   deleted_at 軟刪，保留 90 天再 GC
  題目被下架 / 修訂        內容層      retired_at + revision；attempt 保存 q_revision，
                                       歷史紀錄不因改題而失真

★ 一律用 hlc（混合邏輯時鐘）比較，不用 occurred_at。
  hlc = (wall_ms, counter, device_id)，格式化為可字典序比較的字串。
  取號時 wall = max(now, last.wall)；若 wall == last.wall 則 counter++。
  → 使用者手動把系統時間往回調，hlc 仍單調遞增，LWW 不會被時鐘攻擊翻盤。
  伺服器另存 received_at，若 |hlc.wall − received_at| > 24h 就標記為時鐘異常，
  UI 顯示提示但不拒收（拒收會造成資料遺失，比顯示怪時間嚴重得多）。

══════════════════════════════════════════
八、實際流程：離線做了三天的題，上線後怎麼合併
══════════════════════════════════════════

情境：手機在通勤與宿舍離線三天，做了 1,200 題、改了 40 篇筆記；
      同期間平板也離線兩天做了 400 題；桌機一直在線上。

T0  離線期間
    手機本機 1,200 + 40 ≈ 1,240 筆 op，CBOR 約 300 KB，zstd 後約 80 KB。
    op_log.server_seq 全為 NULL。attempt / srs_card 已即時物化，
    使用者體感上「一切正常」，只有狀態列顯示「1,240 筆待同步」。

T1  手機連上網（或 WorkManager / BGAppRefresh 觸發）
    PUSH 批次 1（500 筆）→ ack → 更新 server_seq
    PUSH 批次 2（500 筆）→ 途中斷線 → 指數退避重試 →
        伺服器已寫入前 300 筆，重送整批 → ON CONFLICT DO NOTHING →
        回傳的 acks 與第一次完全相同 → 客戶端不需要特別處理
    PUSH 批次 3（240 筆）→ ack。耗時數秒。

T2  PULL since = pull_cursor
    拉回桌機這三天產生的 op（假設 600 筆）。平板還沒上線，它的 400 筆還在平板上。

T3  APPLY（單一 transaction）
    600 筆逐一過 applied_op 閘門 → materialize →
    受影響的約 600 個 qid 標記 dirty=1 → commit → 游標前進。

T4  RECOMPUTE
    dirty 卡片約 600 張，每張讀完整 attempt 序列 fold。
    1,800 筆 attempt 規模下，本機約數百毫秒完成，且可分批中斷。
    ★ 關鍵：不是「照收到的順序增量套用」，而是「按 hlc 全序重放該卡片的完整歷史」。
      這就是為什麼平板晚兩天才上線也不會出錯。

T5  平板上線（兩天後）
    平板 PUSH 自己的 400 筆 → PULL 手機與桌機的 1,840 筆 →
    APPLY → 受影響卡片 dirty → RECOMPUTE。
    手機下次同步時 PULL 到平板的 400 筆 → 同樣流程。
    最終三台裝置的 attempt 集合完全相同，
    fold 的輸入集合相同 + 排序 key 全序 → srs_card 位元相同。收斂完成。

T6  筆記
    手機 40 篇筆記的 Yjs update 已隨 op_log 送出；桌機若編輯了同一篇，
    兩邊的 update 合併後由 Yjs 保證收斂，使用者看到的是兩邊編輯都在的版本。
    合併後把新 state 寫回 note_doc.snapshot 並更新 snapshot_upto 與 text_cache（重建 FTS）。

T7  使用者看到什麼
    「已同步 1,240 筆，新增 600 筆來自其他裝置，複習排程已更新」
    今日待複習題數可能因為平板的作答而改變 —— 這是正確行為，不是 bug，
    UI 要能解釋（「因為你在平板上已複習過 x 題」）。

★ 三天離線不需要任何「衝突解決 UI」。唯一可能需要使用者介入的只有
  筆記的極端情境（一邊整篇刪除、一邊大幅改寫），這時保留兩個版本讓使用者選，
  而不是自動決定。

══════════════════════════════════════════
九、內容分發：打包、delta、驗證、空間管理
══════════════════════════════════════════

【分包粒度】{exam}/{subject}/{level} 三層，單包目標 20–200 MB。
  太大 → 使用者不願下載、delta 失效成本高；太小 → manifest 與請求數爆炸。
  圖片不放在包裡，走內容定址（CAS）：assets/{sha256[0:2]}/{sha256[2:4]}/{sha256}
  → 跨科目、跨版本自動去重（同一張元素週期表不會存三份）。

【manifest（伺服器產生，Ed25519 簽章）】
  {
    "catalog_version": 412,
    "packs": [{
      "pack_id": "twgsat.math.b",
      "version": 37,
      "full":   {"url": ".../v37.sqlite.zst", "sha256": "...", "size": 41234567},
      "deltas": [{"from": 36, "url": ".../36-37.patch.zst", "sha256": "...", "size": 812345},
                 {"from": 35, "url": ".../35-37.patch.zst", "sha256": "...", "size": 2103444}],
      "assets": {"url": ".../assets-v37.jsonl.zst", "sha256": "..."},
      "min_app_schema": 5
    }],
    "sig": "ed25519:..."
  }

【delta 策略：雙軌】
  主線 = row-level patch（JSONL）：{"op":"upsert","table":"question","pk":"...","cols":{...}}
    優點：體積最小、可跨多版累積、與 SQLite 檔案佈局無關、客戶端可驗證。
    缺點：需要客戶端 schema 與伺服器一致 → 用 min_app_schema 把關。
  輔助 = binary patch（zstd --patch-from）：
    僅在大版本升級時用。要有效必須做「確定性建置」：
    固定 page_size、固定插入順序、建置後 VACUUM，讓 page 佈局穩定，
    否則 diff 命中率會低到沒有意義。
  逃生門：delta 鏈超過 5 版，或累積大小 > 整包 60% → 直接下載整包。

【完整性驗證（四層）】
  ① manifest 用 Ed25519 驗簽（公鑰內建於 App，含備用鍵支援輪替）
  ② 每個檔案下載後比對 sha256
  ③ 套用 delta 後，重算結果檔的 sha256 並與 manifest 的目標值比對
  ④ PRAGMA quick_check + SELECT content_version FROM pack_meta 交叉確認
  安裝一律：下載到 .tmp → fsync → rename 原子替換 → 更新 pack_install。
  任一步失敗 → 保留舊版可用，絕不留下半套狀態。

【版本控制】
  content_version 單調遞增，永不回退。
  伺服器依 App 版本分流 manifest：舊版 App 只看得到相容的舊 content_version，
  避免「App 沒更新但題庫用了新欄位」造成崩潰。
  qid 永不重用、永不刪除；改題用 revision++，下架用 retired_at。

【儲存空間管理】
  · 使用者可選：下載哪些考試 / 科目 / 是否含高解析圖與影片。
  · 設定總量上限（預設 4 GB），逼近上限時提示。
  · LRU 逐出：依 pack_install.last_used_at；pinned = 1 的科目不逐出。
  · 圖片分層：題幹圖隨包（離線必要）；詳解圖與高解析版 lazy 下載並可獨立清除。
  · 預設僅在 Wi-Fi 下載，可由使用者放寬；HTTP Range 斷點續傳。
  · ★ 目錄選擇（第一版就必須做對，事後極難補救）：
      iOS   已安裝包 → Application Support 並設 isExcludedFromBackup = true
            （否則幾 GB 會灌進 iCloud 備份，是災難級的評價殺手）
            可重新下載的資產 → Caches（允許系統在空間不足時回收，App 要能自癒）
      Android getExternalFilesDir()，manifest 設定排除自動備份
      Web   navigator.storage.persist()；未取得 persist 的 OPFS 隨時可能被清除，
            UI 要明示並提供一鍵重新下載

十、背景同步：各平台差異與退路
══════════════════════════════════════════

  iOS
    BGAppRefreshTask       ~30 秒，系統依使用習慣配發配額，完全不保證。適合小批 push/pull
    BGProcessingTask       充電 + 閒置，可跑數分鐘。適合 recompute、VACUUM、delta 套用
    BGContinuedProcessingTask（iOS 26+）使用者可見的前景延續，適合大包下載
    URLSession background configuration  唯一可靠的大檔背景下載，App 被殺也能續傳
    Background Assets（iOS 26 起支援 Managed，系統代管下載/更新/壓縮，可 Apple-hosted）
    silent push (content-available)  可觸發，但被系統節流，只能當「提示」不能當「保證」
    → 實務主力：「開 App 就同步」+ URLSession background 管內容下載
      + BGProcessing 管重算。不要把正確性押在 BGAppRefresh 上。

  Android
    WorkManager            OneTimeWork + 網路/充電 constraint；Doze 下延後但保證最終執行
    Expedited Work         有配額，適合「使用者剛按下同步就切出去」
    Foreground Service     大包下載必備（要顯示通知列與進度）
    DownloadManager        系統級下載，適合單純大檔
    → 最可靠的平台，但 OEM 省電策略（小米 / 華為 / OPPO / vivo）會殺背景任務。
      需要引導使用者關閉電池最佳化，並在設定頁提供「為什麼同步沒跑」的自我診斷。

  桌面（Tauri / Electron）
    幾乎無限制。常駐背景執行緒 + 定時器；
    開機自啟走 launchd（macOS）/ systemd user unit（Linux）/ Task Scheduler（Windows）。
    適合當「家裡那台永遠在線的節點」，也是內容包預下載的最佳位置。

  網頁
    Background Sync 與 Periodic Background Sync 只有 Chromium 支援；
    Safari（含 iOS）與 Firefox 完全不支援 → 不能當作架構前提。
    退路組合：
      · online / visibilitychange 事件觸發同步
      · pagehide 時用 fetch(keepalive) 或 sendBeacon 送最後一批（有 64 KB 限制，只送尾巴）
      · 未送出的 op 安全留在 OPFS，下次開頁自動續送
      · Service Worker 只用於資產快取與離線殼，不承擔同步保證
    → 網頁版必須假設「只有分頁開著才會同步」，並在 UI 常駐顯示未同步筆數。

  ★ 統一原則：所有平台的同步都必須在「前景手動觸發」下能完整跑完，
    背景排程只是優化。UI 永遠顯示「未送出 N 筆 / 最後同步時間」，
    讓使用者在系統背刺你的時候還能自救。

十一、加密與隱私
══════════════════════════════════════════

【分級，不要一刀切全庫加密】
  題庫內容（唯讀、本來就公開） → 不加密。
    加密會擋掉 mmap、拖慢查詢、讓 CDN 快取與 delta 失去意義，收益是零。
  答題事件 → 不加密內容，靠平台檔案保護。
  筆記 → 提供可選的端對端加密（E2EE）。

【本機】
  iOS      預設 Data Protection 即足夠：
           NSFileProtectionCompleteUntilFirstUserAuthentication（背景同步需要）。
           金鑰放 Keychain（kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly），
           由 Secure Enclave 保護。整庫 SQLCipher 會付出 5–15% 效能與除錯工具的代價，
           在 iOS 上收益不明顯。
  Android  檔案級加密只在裝置鎖定時生效，保護較弱 →
           敏感欄位（筆記）建議用 sqlcipher-android
           （舊的 android-database-sqlcipher 已淘汰），
           金鑰由 Android Keystore 保管；或用 Bloomberg 的 selekt。
  桌面     金鑰放 Keychain / Credential Manager / libsecret；
           資料庫檔案本身依作業系統全碟加密（FileVault / BitLocker）為主。
  網頁     ★ OPFS 無法真正加密——金鑰必然落在 JS 可及之處，加密只是心理安慰。
           正確做法二選一：
             (a) 網頁版不落地敏感資料（筆記只在記憶體，關頁即清）
             (b) 以使用者密語派生金鑰（Argon2id → XChaCha20-Poly1305），
                 只在分頁生命週期內解密，明確告知使用者風險模型

【傳輸】
  TLS 1.3 為底線；payload 額外 zstd 壓縮（不是加密）。
  Certificate pinning 可選，但要規劃 pin 輪替與備用 pin，否則憑證換發那天全體斷線。
  不要用自訂加密取代 TLS，只在 E2EE 情境下疊在 TLS 之上。

【純本機模式（完全不上傳）】
  ★ 這是 op-log 架構的免費紅利：
    未登入時 op_log 照常寫入、materialize 照常跑、fold 照常算，
    只是同步器不啟動。功能上與登入完全一致，零程式碼分岔。
  日後註冊 → 把全部 op 按 hlc 批次 push 即可。
    因為冪等，中途斷線可續，不需要特別的「首次上傳」流程。
  提供「匯出 .zip（user.db + 筆記 Markdown + 題庫清單）」與「匯入」，
    作為換機與資料可攜的保底路徑。

【E2EE 檔位（筆記）】
  passphrase → Argon2id → 主金鑰 → 每篇筆記的 data key（XChaCha20-Poly1305）。
  op_log.payload 在離開裝置前就已加密；伺服器只看得到
  op_type / entity / hlc / 大小 / 時間。
  代價必須先講清楚，事後改不了：
    · 伺服器端全文搜尋消失（只能在本機搜）
    · 網頁版每次開啟都要輸入密語
    · 忘記密語 = 資料救不回 → 必須提供 recovery key（列印/下載）流程
  答題事件建議不做 E2EE：伺服器需要它做題目難度校準與推薦。
  若要滿足最嚴格的隱私需求，把「去識別化的答題統計」拆成獨立、
  可在設定中關閉的遙測通道，與同步通道完全分離——
  不要讓隱私偏好污染同步協定。

## effort
以 2–3 人的小團隊（1 後端／管線、1–2 客戶端）估算，單位為人月。這是「能上線給真實學生用」的量級，不是 demo。

【先做 6 週釘子（spike），不要跳過】
必須在投入主線前用實測回答三個問題，任何一個答案是紅燈都會改變架構：
  · wa-sqlite + OPFS 在目標瀏覽器（Safari 17+ / Chrome / Firefox）裝載 2 GB 題庫、
    跑 FTS5 查詢與多包 ATTACH 的實際表現與失敗模式
  · iOS URLSession background 下載 200 MB 包在真實網路與 App 被殺情境下的續傳可靠度
  · Rust core 的 uniffi（Swift/Kotlin）+ wasm-bindgen 雙輸出建置鏈能否穩定進 CI
  約 1–1.5 人月。

【主線分期】
  P0  資料層與離線單機
      schema、op_log、HLC、materialize、FSRS fold、golden replay test 語料      1.5–2 人月
  P1  內容管線
      確定性打包、row-level delta、Ed25519 簽章、CDN、下載/驗證/安裝/逐出、
      科目選擇與空間管理 UI                                                     2–2.5 人月
  P2  同步後端與協定
      push/pull/snapshot API、per-user 序號與 advisory lock、
      客戶端同步狀態機與退避重試、對帳工具                                      2.5–3 人月
  P3  筆記 CRDT（yrs）+ 快照壓縮 + FTS 重建 + 可選 E2EE                        1–1.5 人月
  P4  四平台背景同步適配（BGTask/URLSession、WorkManager/FGS、SW 退路、桌面常駐） 1–1.5 人月
  P5  各平台 UI（核心已共用，只做介面與平台整合）                         每平台 1–2 人月

【時程量級】
  雙平台上線（iOS + Web，含既有 React 資產重用）
    ≈ 10–12 人月工程量 → 3 人團隊約 4–5 個月日曆時間
  四平台全開（+ Android + Tauri 桌面）
    ≈ 16–22 人月 → 3 人團隊約 6–8 個月
  桌面若走 Tauri 重用 Web UI，P5 可壓到 0.5 人月，這是本架構最划算的一筆。

【改走 PowerSync 的差異（誠實版）】
  P2 可從 2.5–3 人月壓到 1–1.5 人月，總計約 8–10 人月。
  省下的是「協定與重試」，省不掉的是 fold、衝突規則、內容管線、背景任務適配——
  這些本來就佔七成。所以 PowerSync 省的是約 1.5 人月，不是省一半。
  換來的是每月費用與供應商風險。若團隊只有 1–2 人且沒有 Rust/分散式經驗，
  這 1.5 人月換到的「有人幫你顧同步的正確性與監控」很值得；
  若團隊有 3 人以上且打算長期經營，自建的控制權更值錢。

【常態維運（容易被漏掉）】
  內容管線的內容更新、pack 版本管理、同步對帳與異常追查、
  各平台背景任務的 OEM 相容問題回報處理
  ≈ 0.3–0.5 人力常駐，上線後永遠存在。編列預算時要算進去。
