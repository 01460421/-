
## area
後端架構：Cloudflare 既有資產評估、資料層選型、原生 App 認證／推播／AI 服務化／離線分發／可觀測性

## recommendation
Cloudflare Workers 這一層全部留下（它是既有資產裡最值錢的部分），但**把 D1 從「主資料庫」降級成「控制面小庫」**，主資料層換成 Neon Postgres（pgvector + 中文全文一次解決）走 Hyperdrive，答題事件流走 Queues → Analytics Engine + R2，題庫與離線包放 R2，認證改成「Worker 自己當 Authorization Server」的 BFF + PKCE + refresh rotation，並且**把 AI 從「即時對話」改成「預生成解析為主、即時推論為輔」**——這一項比其他所有決策加起來更能決定這個 App 活不活得下去。

## rationale
## 一、先講結論：撐不住的不是 Cloudflare，是 D1

Cloudflare 平台本身（Workers / R2 / KV / Queues / Vectorize / Durable Objects / Analytics Engine）以你描述的規模來說**綽綽有餘**。真正撐不住的只有 D1，而且它是現在 `worker/` 裡所有資料的唯一去處。逐項對照如下（規模假設：註冊 30 萬、DAU 20% = 6 萬、每人每日 200 筆答題事件 = **1,200 萬事件／日**、題庫 30 萬題）。

### 1. 資料庫大小上限 10 GB（付費）／500 MB（免費）— ❌ 硬性死亡

| 資料 | 估算 | 判斷 |
|---|---|---|
| 答題事件 | 每列含兩個索引約 180 B × 1,200 萬 = **2.16 GB／日** | **4.6 天就撞上 10 GB 天花板** |
| 題庫 30 萬題（題幹＋選項＋解析 ~2 KB） | 600 MB，加中文全文索引 1.2–1.5 GB | 單獨一個 D1 勉強可以 |
| 帳號＋prefs（30 萬 × ~2 KB） | 600 MB | 完全沒問題 |

這一條不是「調參數可以撐」，是「架構層級的不可行」。答題事件流**絕對不能進 D1**。

### 2. rows read／rows written — ⚠️ 錢還好，延遲才是問題

- 計費（2026）：rows read 每月免費 250 億、之後 $0.001/百萬；rows written 免費 5,000 萬、之後 $1.00/百萬；儲存 5 GB 免費、之後 $0.75/GB-月。
- 寫入：3.6 億／月 → 超出部分約 **$310/月**，可接受。
- 讀取：`rows read` 算的是**掃描列數不是回傳列數**。若「我的學習統計」頁跑 `WHERE user_id=? AND ts>?` 掃該使用者 6 萬列，6 萬 DAU × 每日 5 次 = 30 萬次查詢 × 6 萬列 = **每日 180 億 rows read**，月 5,400 億 → 約 **$515/月**。錢還好，但這代表每次開統計頁都在做萬列級掃描，p95 延遲會很難看。
- **每次查詢最多 100 個 bound parameters** ← 這條會直接絆倒你。離線同步時一次上傳 200 筆答題（200 × 6 欄 = 1,200 個參數）**直接違規**，必須拆成 `db.batch()` 且每句自控在 100 參數內。
- 單列／BLOB 上限 **2 MB** → 離線包不可能塞 D1。
- 每次 Worker invocation 最多 **1,000 次 D1 查詢**（付費）／50 次（免費）；單一 SQL 最長 **30 秒**。

### 3. 並發／寫入吞吐 — ❌ 尖峰超出 3–4 倍

D1 是**單一 primary、寫入序列化**。多份實測與生產回報一致指向：**超過約 200 writes/s 開始出現 SQLITE_BUSY，250 req/s 附近開始逾時，p99 陡升**。

- 1,200 萬事件／日均攤 = 139 writes/s，看起來剛好。
- 但考試 App 的流量絕不均勻：晚上 20–23 點通常是均值的 4–6 倍 → **尖峰 600–800 writes/s**，**超出 D1 上限 3–4 倍**。
- 唯一能救的做法是「客戶端批次 + 只寫聚合」：每 50 筆打包成一個 transaction，寫入交易數降到 24 萬/日、尖峰約 17 txn/s。這可行，但代價是你必須先建整套離線佇列與衝突處理——而那套東西建好之後，你會發現用 Postgres 反而更簡單。

### 4. Region — ⚠️ 可接受但要主動指定

D1 primary 綁在單一 region，讀取複本（Sessions API）目前 6 個 region、**寫入一律轉發 primary**。台灣使用者應把 primary 指定在 `apac`（東京／新加坡），寫入 RTT 約 40–80 ms。SRS 是典型「讀後即寫」，需要 `first-primary` 或 bookmark 一致性，讀複本幫助有限。若使用者集中在台灣，單一 apac primary 其實可接受——**region 不是這裡的關鍵問題**。

### 5. 全文與語意搜尋 — ❌ D1 做不到

- **中文全文**：D1 是 SQLite，FTS5 的預設 tokenizer（unicode61）不切中文詞，等於整段當一個 token。要能用得靠 trigram tokenizer 或自建 bigram 索引，而 D1 不保證 SQLite 擴充可用。在 D1 上做中文全文是自找麻煩。
- **語意搜尋**：D1 完全沒有向量能力，必須外掛 Vectorize（2026-01 起單 index 支援 **1,000 萬向量、最高 1,536 維**，30 萬題就算每題切 3 塊也才 90 萬，容量不是問題）。
- 但**中文題庫必須做混合檢索**：純向量對「113 年學測第 12 題」這種精確查詢極差，需要 BM25／全文 + 向量以 RRF 融合。**D1 + Vectorize 是兩個服務、要自己在 Worker 裡 merge 兩份結果；Postgres 的 tsvector + pgvector 是同一句 SQL 做完。** 這是選 Postgres 最主要的技術理由。

### 二、既有資產可以沿用多少：程式碼約 30%，設計模式約 70%

我讀完 `worker/src` 全部 4,559 行。誠實分類：

**直接搬、幾乎不用改（最值錢的部分）**
- `chats.js` 的 `appendMessages`：**把額度條件寫進 `UPDATE ... WHERE msg_count+? <= ? AND chars+? <= ?`，用 `meta.changes` 判斷有沒有真的收下**。這是全專案最好的一段程式碼——大多數團隊要被並發打爆一次才學得會。這個手法在新系統的 SRS 狀態更新、額度扣減、推播去重上要原封不動地複製。
- `db.js` 的 `saveApplication` / `spendCredit` / `bumpVerifyTry` / `confirmOrder`：同一個模式（條件寫進 WHERE、冪等 token、batch 當交易）。`confirmOrder` 用一次性 `confirm_token` 讓「改狀態 + 加點數」原子成立，是教科書級的正確做法。
- `tasks` 表 + `claimTask(lease_until)` + `reclaimStaleTasks` 的**租約搶佔排程模型**：白名單 action、失敗記錄、`repeat_s` 週期——複習提醒需要的東西它全有了。設計 100% 沿用，程式碼約 70%。
- `admin.js` 的 `PROFILES` 抽象（前端只送代號、模型與參數一律伺服器決定）與 prompt caching 斷點策略（tools 最後一個 + system 下 1h TTL 斷點，因為渲染順序是 tools → system → messages）。這兩件事直接是新系統分模型分級的骨架。
- `cors.js` 全部；`auth.js` 的 HMAC 簽／驗、`safePath`、`esc`；`review.js` 的 `sanitizeNote`（清洗不可見字元**並記錄清掉幾個**——那個 `apply_note_dropped` 欄位的設計理由寫得非常好）。
- **AI 安全模型**：`/admin/ask` 的「唯讀快照 + 零工具 + 模型輸出不決定後續動作」，加上刻意排除 `apply:%` 事件標題以免申請者文字流進管理員的 AI。這個原則整套帶走。

**必須重寫（規模化會死）**
- `aiUsedToday` / `aiUsedTodaySite`：後者是 `SELECT count(*) FROM admin_log WHERE created_at>=?`，**全表掃描**。每次 AI 請求都掃一次，在每日數十萬次呼叫下是災難。改成 `ai_usage(user_id, day)` 計數表 + `ON CONFLICT DO UPDATE`，站台總量用 Durable Object 計數器。
- **額度單位**：現在「一次呼叫算一次」，但批改（in 500 tokens）和解題（in 20,000 tokens）差 40 倍。必須改成 token 加權點數。
- cookie session：原生端不適用（見第三節）。
- `mail.js` 的單封 for-loop、`dueTasks(db, 10)` 每分鐘 10 筆：扇出量差三個數量級，要換 Queues。
- `watch.js`、`dashboard.js`：PJSK 專用，考試 App 用不到。
- `validateChat`：只檢查工具數量與大小，**不檢查工具名稱白名單**。目前因為工具真正在瀏覽器執行、Worker 不執行任何東西所以危害有限，但 App 版必須把工具定義移回伺服器端白名單。

### 三、AI 成本：這是會決定生死的一題

先算清楚。6 萬 DAU × 每人每日 3 次解題講解 = **18 萬次／日**。

| 方案 | 單次成本 | 每日 | 每月 |
|---|---|---|---|
| 全 Opus（比照現在的 in 20.7k / out 1.4k） | ~$0.14 | $25,200 | **$756,000** |
| 全 Haiku + 精簡 context（in 3k / out 800） | ~$0.005 | $900 | **$27,000** |
| **解析預生成 + 快取，5% 走即時** | — | $45 | **$1,350** |

第一列直接出局。第二列對小團隊仍然是燒錢。**第三列才是可行的架構**：30 萬題每題預先生成一次高品質解析（30 萬 × $0.02 ≈ **$6,000 一次性**），使用者看到的 95% 是快取內容，只有「我還是不懂，換個說法」才即時打模型。

`wrangler.toml` 裡那段「調整 AI_CAP_USER 前請先換算：400 次 ≈ $55／人／日」的註解，證明這個 codebase 已經有正確的成本直覺。規模化之後這個直覺只會更重要——但答案不是把 cap 調低，是把架構從「即時推論」改成「預生成 + 快取」。

## 資料流

**1. 答題事件（寫入最重的路徑）**
App 本機 SQLite 先寫（**離線優先，UI 不等網路**）→ 每 30 秒或滿 50 筆打包 → `POST /v1/attempts`（帶 `idempotency_key`）→ Worker 只做驗簽 + 大小檢查 + 丟 Queue，**立刻回 202**（p95 < 60 ms）→ consumer 批次 `INSERT ... ON CONFLICT DO NOTHING` 進 Postgres `attempts`（按月 partition）→ 同一批同時 `writeDataPoint()` 進 Analytics Engine 做即時聚合。
- Worker 這一跳**不碰資料庫**，是它能扛尖峰的原因。
- `idempotency_key` = `device_id + local_seq`，重送不會重複計分。

**2. SRS 複習排程**
`srs_state(user_id, question_id, due_at, ease, interval, reps)`，主鍵 `(user_id, question_id)`，索引 `(user_id, due_at)`。答題事件落庫時在同一個 transaction 更新 srs_state（用 `UPDATE ... WHERE ... AND reps < ?` 的條件式寫法，沿用 `chats.js` 的手法防重放）。
「今天要複習什麼」= `WHERE user_id=? AND due_at <= now() ORDER BY due_at LIMIT 50`，一次索引掃描。

**3. 混合檢索（RAG 的檢索端）**
```sql
WITH kw AS (SELECT id, ts_rank_cd(tsv, q) r FROM questions,
              plainto_tsquery('simple', $1) q WHERE tsv @@ q LIMIT 50),
     vec AS (SELECT id, 1-(embedding <=> $2) r FROM questions
              ORDER BY embedding <=> $2 LIMIT 50)
SELECT id, SUM(1.0/(60+rank)) score FROM (...) GROUP BY id ORDER BY score DESC LIMIT 8;
```
一句 SQL 完成 BM25 + 向量的 RRF 融合。embedding 用 Workers AI 的 `bge-m3`（多語、支援中文）就地產生，省一趟外部往返。

**4. AI 推論**
`/v1/ai/explain` → 先查 `question_explanations` 快取（**95% 在這裡結束**）→ miss 或使用者按「換個說法」→ 檢索 top-8 → 依 profile 選模型 → AI Gateway → Anthropic SSE → Worker 用 `TransformStream` 邊透傳邊累積 → 串流結束時一次寫進 `chat_messages`（沿用 `chats.js` 的兩表模型）。

**5. 推播**
cron（每分鐘）→ 查 `jobs WHERE bucket = <當前分鐘序號> AND status='pending'`（**按分鐘分桶，避免掃全表**）→ 每 100 個 user 打包成一則 Queue 訊息 → consumer 併發 → 依 `push_tokens.platform` 分派 APNs / FCM / Web Push → 失敗（410 Gone / `UNREGISTERED`）就標記 `push_tokens.enabled=0`。

```sql
-- 身分抽表：加供應商不用改 schema，帳號合併有地方記

CREATE TABLE users (
  id UUID PRIMARY KEY,
  kind TEXT NOT NULL DEFAULT 'guest',  -- guest | member
  birth_year SMALLINT,                 -- 中性年齡輸入的結果，不是勾選框
  age_bracket TEXT,                    -- child(<13) | teen(13-17) | adult
  consent JSONB,
  merged_into UUID,                    -- tombstone：合併後舊 id 指向新 id
  deleted_at TIMESTAMPTZ,              -- 帳號刪除（Apple 5.1.1(v) 強制要求）
  ...
);

-- refresh token：現有架構完全沒有，必須新建
CREATE TABLE refresh_tokens (
  id UUID PRIMARY KEY, user_id UUID NOT NULL, family_id UUID NOT NULL,
  token_hash BYTEA NOT NULL,     -- 只存雜湊，不存明文
  device_id TEXT, expires_at TIMESTAMPTZ NOT NULL,
  revoked_at TIMESTAMPTZ, replaced_by UUID   -- rotation + reuse detection
);

-- 答題事件：按月分割，舊分割每季導出 Parquet 到 R2 後 DETACH
CREATE TABLE attempts (
  id BIGSERIAL, user_id UUID NOT NULL, question_id BIGINT NOT NULL,
  answered_at TIMESTAMPTZ NOT NULL, correct BOOLEAN, ms INT,
  choice SMALLINT, session_id UUID, idem_key TEXT,
  PRIMARY KEY (id, answered_at)
) PARTITION BY RANGE (answered_at);
CREATE UNIQUE INDEX ON attempts (user_id, idem_key);   -- 冪等
```

## 認證流程（BFF + PKCE）

**不要**讓原生 App 直接拿 Google/Apple 的 token。正確做法是 Worker 自己當 Authorization Server：

```
App                        Worker(AS)               Google/Apple(IdP)
 │ 產 code_verifier          │                        │
 │ ASWebAuthenticationSession│                        │
 ├─ GET /oauth/authorize ───►│                        │
 │   (code_challenge, S256)  ├─ 302 (confidential) ──►│
 │                           │◄─ callback + code ─────┤
 │                           │  換 token、建/找 user  │
 │◄─ 302 app://cb?code=… ────┤                        │
 ├─ POST /oauth/token ──────►│  驗 code_verifier      │
 │   (code, code_verifier)   │                        │
 │◄─ access(JWT 15m) +       │                        │
 │   refresh(opaque, 90d) ───┤                        │
```

- client_secret 永遠不出伺服器；App 是 public client 只用 PKCE。
- **`auth.js` 現有的 `signToken`/`verifyToken`（HMAC-SHA256 + base64url payload）實質上就是 JWT，可以直接沿用當 access token 簽發器**，但要正式化：加 `kid`（讓密鑰能平滑輪替——現在改 `SESSION_SECRET` 等於全站登出）、`iss`、`aud`、`jti`。
- refresh token 做 **rotation + reuse detection**：每次刷新換一組，舊的被再用一次就撤銷整個 family。這是偵測 token 被竊的唯一實用手段，現有架構完全沒有。
- Web 端可以繼續用現在的 cookie session（`SameSite=Lax` + `Domain=.project-sekai-center.com`），兩套並存，`users` 是同一份。

## 如果要縮短，唯一有效的槓桿是砍範圍

| 砍掉 | 省下 | 代價 |
|---|---:|---|
| **AI 即時對話**（只留預生成解析） | **6 週** | 最推薦砍。同時省掉絕大部分 AI 成本與 injection 風險 |
| 語意搜尋（v1 只做全文） | 3 週 | 檢索品質下降，但中文全文其實已經能解決八成查詢 |
| Web Push（只做 APNs/FCM） | 1.5 週 | Web 端改用站內通知（既有 `events` 表已經是這個模型） |
| 增量更新（每包整包重下） | 2 週 | R2 egress 免費，這個取捨對小團隊是划算的 |
| 離線包（線上優先 + HTTP 快取） | 5 週 | **不建議砍**，這是考試 App 的核心差異化，也是 DR 紅利的來源 |

**砍掉前四項後，後端可壓到 3–4 個月**，這是我認為最務實的 v1 範圍。

## 既有資產的量化沿用率

- `worker/src` 共 **4,559 行**，可直接搬或小改沿用約 **1,200–1,500 行（約 30%）**。
- 但**設計模式的沿用率遠高於此，約 70%**：條件式 UPDATE 防並發、租約搶佔排程、冪等 token、AI profile 分級、prompt caching 斷點、prompt injection 邊界、`no-store` + 具名 CORS、IDOR 用 `AND user_id=?` 寫死而不是查完再比對——這些在多數團隊要吃過虧才學得會，這個 codebase 已經全部有了。
- 節省的不只是程式碼，是**不會再踩一次的坑**。以這些模式平均各值 1–2 週的除錯時間計，既有資產實質省下 **8–12 人週**。

## 建議的執行順序（每階段都可上線、可回頭）

1. **第 0–4 週**：建 Postgres schema、題庫匯入、混合檢索跑通。**不動任何既有程式碼。**
2. **第 4–10 週**：認證 BFF + SIWA + 訪客。此時 Web 仍走舊 cookie session，兩套並存。
3. **第 10–16 週**：事件上行 + SRS + Queues。App 可以開始內測刷題。
4. **第 16–22 週**：離線包 + 推播。這兩件事一起做，因為「離線可用 + 會提醒你」才構成完整的複習迴圈。
5. **第 22–26 週**：解析預生成跑完 30 萬題、觀測性與備份補齊、第一次 DR 演練。
6. **送審前**：帳號刪除入口、隱私政策、年齡分級、SIWA 寄件網域註冊——這四項少一項就會被退件。
