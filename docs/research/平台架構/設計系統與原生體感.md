
## architecture
## A. Token 管線（單一真實來源 → 四平台產物）

```
design/
  tokens/                          ← 唯一真實來源，W3C DTCG 格式 (.tokens.json)
    core/                          ← primitive，只有原始值，沒有語意
      color.palette.tokens.json    #  sky.50…900 / sakura.50…900 / neutral.0…1000
      dimension.tokens.json        #  space.1=4 … space.12=48（4pt grid）；radius.sm=10/md=14/lg=20
      typeface.tokens.json         #  fontFamily stack、weight 400/500/700/800
      duration.tokens.json         #  fast=140 base=220 slow=380 sheet=500
      easing.tokens.json           #  ease=(.32,.72,.24,1) spring=(.34,1.45,.44,1)
      elevation.tokens.json        #  sh.xs / sh.sm / sh.md / sh.lg（含深色替代值）
    semantic/                      ← 只 reference core，禁止寫死色碼
      color.light.tokens.json      #  bg / bg.soft / surface / surface.raised / text.primary…
      color.dark.tokens.json
      color.sepia.tokens.json      ← 新增：護眼紙感閱讀模式
      color.oled.tokens.json       ← 新增：AMOLED 省電模式（非純黑）
      type.scale.tokens.json       #  以 pt 表達，各平台自行換算 rem/sp/pt
      motion.semantic.tokens.json  #  motion.enter / motion.sheet / motion.answer.reveal
      haptic.tokens.json           ← 語意事件名，非數值：answer.correct / selection / page.turn
      contrast.lock.tokens.json    ← fg/bg 配對的最低對比要求，餵給 CI
    tone/                          ← 六色調，只允許覆蓋 accent 家族三個 key
      sakura / jade / wisteria / amber / ink / aurora .tokens.json
    platform/                      ← 平台覆寫層，只能改值、不能新增語意名
      ios.tokens.json      # radius 對齊 SwiftUI continuous corner；elevation 大幅降權
      android.tokens.json  # 映射到 Material3 ColorScheme 的 40 個 role
      desktop.tokens.json  # 密度提高一階、shadow 減弱、hover 態才存在
      web.tokens.json
  build/
    style-dictionary.config.mjs    ← Style Dictionary v4，唯一建置入口
    formats/
      swift.mjs      → DesignTokens.swift（enum + Color/Font/CGFloat 擴充 + UIFontMetrics 綁定）
      compose.mjs    → Tokens.kt（Color/Dp/TextStyle）+ SekaiColorScheme.kt（Material3）
      css.mjs        → tokens.css（:root / [data-theme] / [data-tone] / [data-reading]）+ tokens.d.ts
      dart.mjs       → tokens.dart（ThemeExtension<SekaiTokens>）※ 只在走 Flutter 備案時啟用
      flat.mjs       → tokens.flat.json（設計工具、視覺回歸、文件站共用）
    checks/
      contrast.spec.mjs   ← 對 contrast.lock 逐對驗 WCAG 2.2 AA，失敗即 CI red
      naming.spec.mjs     ← 語意層出現 hex 字面值即失敗
      drift.spec.mjs      ← dist/ 與重新建置結果 diff，不一致即失敗（防手改產物）
  dist/                            ← 全部 generated，加 .gitattributes linguist-generated
    apple/Sources/DesignTokens/
    android/tokens/src/main/kotlin/
    web/tokens.css  tokens.d.ts
```

規則三條：(1) UI 程式碼只准引用 semantic 層名稱，引用 core 或 hex 由 lint 擋下；(2) `dist/` 進版控但唯讀，CI 重建比對；(3) 新增語意 token 必須同時補 `contrast.lock` 條目，否則無法合併。

## B. 元件庫結構（內容一致、殼層原生）

```
packages/
  content-core/            ← 純邏輯，無 UI，TypeScript（Web/Desktop 直用；iOS/Android 走 WASM 或伺服端預編）
    ast/                   #  講義與題目的正規化 AST（JSON Schema 有版本號）
    md/                    #  Markdown + 自訂指令 → AST
    math/                  #  LaTeX → MathML Core（建置期預編，不在裝置上跑 KaTeX）
    chem/                  #  mhchem → 同一條 MathML 出口
    code/                  #  tree-sitter 建置期標記 → span+class，執行期零 highlighter
    chart/                 #  圖表規格 → draw-plan（純座標與文字，無繪圖 API）
    a11y/                  #  LaTeX → 中文朗讀字串（VoiceOver/TalkBack 用）
  study-core/              ← Kotlin Multiplatform（或 Rust + UniFFI），四平台共用二進位
    quiz/  scoring/  srs/  timer/  ink-model/  search-index/  sync-queue/
  content-view/            ← 唯一一份「內容排版」實作：HTML + tokens.css，四平台共用
    reader.html  reader.css  reader.js（注入 dist/web/tokens.css）
  shell-ios/       SwiftUI，TabView + NavigationStack + PencilKit + VisionKit
  shell-android/   Compose，NavigationBar/Rail + Predictive Back + CameraX + ML Kit
  shell-desktop/   Tauri（Rust 殼 + 同一份 React），NSToolbar/WinUI 風格側欄
  shell-web/       React PWA，與 desktop 共用 90% 畫面碼
```

關鍵決策：**題目與講義的內文區在四平台都是同一份 `content-view`（iOS WKWebView / Android WebView / Desktop 與 Web 原生 WebView），殼層（導覽、工具列、手勢、鍵盤、觸覺、相機、筆）100% 原生。** 這一刀切在「內容 vs 容器」而不是「畫面 vs 畫面」，因為內容的一致性（數學式行距、上下標、中西混排）是正確性問題，容器的一致性反而是體感缺陷。WebView 只吃 `dist/web/tokens.css`，主題／色調／字級由殼層透過 JS bridge 設 `data-theme` / `data-tone` / `--reading-scale`，一次呼叫、零閃爍。

例外：儀表板型獨立圖表（學習統計、正確率趨勢）不進 WebView，由 `chart/draw-plan` 餵原生畫布（SwiftUI Canvas / Compose Canvas / inline SVG），因為它們需要原生手勢與無障礙焦點；文流內嵌的小圖表留在 WebView 的 inline SVG。

## area
跨平台設計系統：共用 token 管線與各平台原生體感的平衡

## effort
誠實估計，以「2–3 人（1 設計 + 2 工程）」為前提，單位是人週。

**Phase 0 — token 抽取與體檢（3–4 人週）**
把 core.css / app.html 的兩套變數合併成一份 DTCG、補語意層、修對比、建 Style Dictionary + CI。這階段不改任何畫面，只讓現有 Web 改吃 `tokens.css`。這是投報率最高的一段，先做完再談跨平台。

**Phase 1 — 閱讀排版與內容渲染核心（8–10 人週）**
AST、Markdown、LaTeX→MathML 預編、tree-sitter 程式碼標記、chart draw-plan、`content-view` 的四種閱讀模式。含 a11y 朗讀字串產生器。這是整個系統最重、也最不能外包的一塊。

**Phase 2 — Web + Desktop（6–8 人週）**
共用 React 畫面 + Tauri 殼。桌面鍵盤全操作、側欄、離線內容打包（SQLite + 內容包）。兩個平台一起做只比單做 Web 多約 2 人週。

**Phase 3 — iOS 殼（10–14 人週）**
SwiftUI 導覽、Dynamic Type 到 AX5 的版面回流、PencilKit 手寫（含筆跡模型對接與掌拒）、VisionKit 拍照、觸覺、WebView bridge、離線包。PencilKit 與 AX5 回流各自會吃掉 3 人週以上，別低估。

**Phase 4 — Android 殼（8–10 人週）**
Compose 導覽、Predictive Back、低延遲筆跡（androidx.input）、CameraX + ML Kit、MathML fallback（Android WebView 的 MathML 支援比 iOS 差，需要 aria-label 兜底的實作與測試）。

**Phase 5 — 無障礙驗收與內容量產管線（4–6 人週）**
WCAG 2.2 AA 逐條驗、VoiceOver/TalkBack 實機走查、色盲模擬、CI 視覺回歸、內容編輯者的 lint 工具。

**合計 39–52 人週 ≈ 9–13 個月人力。**

日曆時程：3 人並行約 **6–8 個月** 到四平台 v1。1–2 人的話務實做法是 **Phase 0→1→2 先出 Web+Desktop（約 4–5 個月），iOS 再排 3 個月，Android 延到第二年**——Android 用 PWA 先撐（Chrome 的 PWA 在 Android 上體感落差比 iOS 小很多）。

不建議壓縮的兩段：Phase 0（壓縮會讓後面每個平台各自漂移，是複利型債務）與 Phase 5（無障礙補做的成本是內建的 3–5 倍）。

## rationale
扣住四個現實條件來看，答案幾乎是被逼出來的。

**一、現有資產的價值不在「畫面」，在「內容渲染」。** 讀完 `core.css` 與 `app.html` 的 style 區塊，真正有複用價值的是三樣東西：一套完整的雙主題語意色彩分層（`bg / bg-soft / card / card-2` 四階背景 + `text / text-light / primary / secondary` 四階文字）、六色調只覆蓋 accent 家族的乾淨疊加設計、以及 `.tut-a` 表格「外層 block 負責捲動、內層 tbody 保欄寬、首欄 sticky」這種被真實手機坑過才寫得出來的細節（註解裡甚至留著 2026-08-01 修 iOS Safari `position:fixed` 脫鉤的紀錄）。這些是**內容排版**的資產，不是 App 殼的資產。所以正確的切法是保住內容層、丟掉殼層，而不是保住全部或丟掉全部。

**二、「長時間讀書」對現有風格的判決：氣質保留，數值全改。**
- **必須保留**：`--ease` / `--spring` 兩條曲線（克制、不誇張，適合工具型 App）；圓角三階（圓潤感是這套設計的識別，且對長時間視覺負擔是正向的）；四階背景分層（讓題卡浮在底色上而不靠陰影，正是長閱讀要的）；深色底用 `#0c0f1d` 而非純黑（這點原本就做對了）；`prefers-reduced-motion` 全域處理（已到位）；`:focus-visible` 的 3px 描邊（少見地做得好）；六色調的疊加架構。
- **必須改**：**字級**。全站 `font-size` 統計是 11px(37 次) > 13px(27) > 12px(26) > 10px(16)，`core.css` 裡 **rem 出現 0 次**，全部寫死 px。這是資訊看板的密度，不是讀書的密度，而且寫死 px 等於 Dynamic Type 完全不可能實作。內文基準必須拉到 17pt 並改用可縮放單位。
- **必須改**：**對比不合格**。實算幾個關鍵配對：`--text-light:#8b93ac` 對白卡只有 **3.06:1**（AA 正文需 4.5:1），但它現在承載著 `.description`、`.cc-sub`、`.stat-label` 這些會出現在題目說明位置的文字；`--link:#0d9cba` 對白只有 **3.24:1**；`--accent-deep:#0891a2` 只有 **3.76:1**；六色調中連表現最好的 jade `#1f8770` 也只有 **4.41:1**，全數落在 4.5 以下。也就是說**六個色調沒有一個的強調色可以合法當內文連結色**。必須為每個 tone 增列一個只供文字使用、鎖定 ≥4.5:1 的 `--accent-text`。
- **必須改**：**深色模式對比過高**。`#ccd3e8` 對 `#0c0f1d` 是 **12.8:1**，在暗房長讀會產生光暈（halation），字看起來會「發毛」。長閱讀的深色文字應落在 9–11:1，把文字降到 `#b9c2da` 或把底提到 `#12172a`。
- **必須改**：**字體**。`Huninn`（粉圓系）是圓體，筆畫粗細均一、字腔小、辨識線索少，當品牌與標題很好，當長文內文會加速疲勞，而且與數學式的上下標、根號、分數線搭配時基線很難對齊。更關鍵的是 `M PLUS Rounded 1c` 是**日文字型**，被放在中文 fallback 鏈的第二位，遇到日文漢字與中文漢字字形不同的字（如「骨」「直」「every 帶點的異體字」）會混排出兩種字形，考試內容不能接受。而且兩者都從 Google Fonts CDN 載入，離線直接失效。
- **必須改**：`body::before` 那三層固定定位的 radial-gradient（藍/青/粉）在整個視窗鋪一層彩色霧。做品牌氛圍很漂亮，但長閱讀時它會讓正文底色在捲動中微幅偏色、破壞對比穩定性，在 OLED 上還是持續耗電的大面積非黑像素。閱讀模式必須完全關閉。`--rainbow` 彩虹漸層同理——留給品牌、成就、里程碑，絕不可進入「對/錯/選項/難度」這種語意層（既是色盲問題，也是視覺噪音）。
- **已存在的無障礙地雷**：`.diff-badge` 的 `min-width:23px`、`.close-btn` 28px、`.cal-dot`/`.gs-dot` 7px 都低於或貼近 WCAG 2.2 新增的 **2.5.8 目標尺寸 24×24 CSS px**；而 `.m-dock`（底部浮動膠囊）與 `nav#siteNav`（頂部固定膠囊）會遮住捲動到邊緣的聚焦元素，直接命中 **2.4.11 Focus Not Obscured**。這兩條是 2.2 的新條款，舊稽核不會抓到。

**三、「離線 + 內容量大」把 PWA 路線判出局。** iOS 的 WKWebView 儲存配額會被系統回收，對一個學生考前要離線讀完整本題庫的 App，內容包被清掉一次就流失一個用戶。需要的是 iOS on-demand resources / Android asset packs 這種平台原生的內容分發，這只有原生殼能拿到。

**四、「原生體感」的真正定義是手勢與輸入，不是像素。** 使用者不會抱怨你的按鈕圓角差 2px，但會立刻感覺到右滑返回不跟手、捲到底沒有回彈、答對時沒有那一下震動、中文輸入法候選字擋住輸入框。這些全都在殼層。反過來，數學式的分數線粗細、化學式的下標基線、程式碼的等寬對齊——這些**必須**四平台完全一致，否則是內容正確性問題。所以「殼層原生、內容統一」不是折衷，是把一致性用在對的地方。

**五、小團隊的槓桿在 token 管線的 CI，不在減少平台數。** 四份殼層的維護成本是可控的（各約 2000–4000 行），真正會拖垮小團隊的是「四邊視覺慢慢漂移、沒人知道哪個才對」。所以 Phase 0 的對比檢查、命名檢查、產物 drift 檢查三道 CI 關卡，價值高於任何跨平台框架。

## recommendation
採「一份 DTCG design token → Style Dictionary 產出 Swift/Kotlin/CSS/Dart 常數」＋「內容渲染層四平台共用一份 HTML/CSS（WebView）、殼層各平台原生（SwiftUI / Compose / Tauri / React PWA）」；現有溫柔圓潤風格保留其色彩分層、圓角與動效曲線，但字級、對比、字體與全域漸層背景必須為長時間閱讀重做——目前正文字級 10–13px 全寫死 px、`--text-light` 對比僅 3.06:1、六種色調的強調色沒有一個達到 4.5:1，是不能直接搬上四平台的。
