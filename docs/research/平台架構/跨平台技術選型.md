
## area
跨平台技術選型（iOS / Android / macOS / Windows / Web，內容密集型考試準備 App）

## recommendation
手機走 Expo + React Native（New Architecture），Web 走 React + Vite，桌面用 Tauri v2 直接包 Web 產物；三者之上共用一層純 TypeScript 的領域核心（題庫、SRS 引擎、同步層）。現有的 dc-runtime（support.js）作為執行期框架必須**丟棄**，但要從中搶救三樣東西：設計 token、app.html 裡的領域邏輯、以及整個 Cloudflare Worker 後端（原地保留）。

## rationale
【先講 dc-runtime 的判決：丟棄，且沒有第二選項】

我實際讀了 /home/user/Project-sekai-center/support.js（1,911 行）與 /home/user/Project-sekai-center/app.html（17,097 行），三個硬事實決定了這件事：

1. **它從設計上就綁死 DOM，不是「可以移植」而是「本質是 DOM」**。compileTemplate() 在 support.js 第 471–478 行做的事是 `document.createElement("template")` → `tpl.innerHTML = encodeCase(html)` → 遍歷真實 DOM 節點的 `node.attributes` 產生 React builder；parseDcText() 在第 41 行用 `new DOMParser()`。也就是說模板編譯這件事發生在**執行期**，而且需要一個真的瀏覽器 DOM 當 parser。React Native 沒有 DOM，Flutter 沒有 DOM，Compose 沒有 DOM。這不是補幾個 polyfill 的問題，是要重寫一個 HTML parser。

2. **evalDcLogic() 用 `new Function(...)`（support.js 第 843 行）執行 `<script type="text/x-dc">` 的字串**。RN 的 Hermes 引擎不支援 eval / Function-from-string，這條路在 RN 上直接是執行期崩潰。而且「執行期把 template + 邏輯字串抓下來評估」這個模式，若在 App 內從網路載入，會直接踩到 App Store 對動態程式碼的界線（EAS Update / CodePush 之所以合法，是因為只換 JS bundle 且不改變 App 主要用途，跟這個模式不同）。

3. **模板語法的表達力其實非常低，所以「捨不得丟」是錯覺**。resolve()（support.js 第 202–290 行）是手寫的迷你求值器，只支援屬性存取 `.`、索引 `[]`、`!`、`== != === !==` 和字面量——**沒有算術、沒有函式呼叫、沒有三元運算**。所以 `<sc-if>/<sc-for>/{{ }}` 這層幾乎沒有商業價值可言，真正的資產全部在 app.html 第 3439–17097 行那個約 13,600 行的 `class Component extends DCLogic` 裡（BOOST 表、UNITS、PAGES、ALIASES 五百多條別名對照、各種計算）。那些是**純 JavaScript**，可以逐段搬進共用核心。要遷移的是邏輯，不是模板。

4. 補一刀：support.js 第 1 行寫著「GENERATED from dc-runtime/src/*.ts — do not edit」，而 dc-runtime/ 原始碼**不在這個 repo 裡**。要拿它當四平台的基礎，等於這個團隊要開始維護一套自有 UI 框架。全部 50 個 commit 的作者都是 github-actions[bot]，這是 1–2 人規模的專案，養框架是自殺。

【為什麼是 RN + Tauri，而不是別的】

**扣住「內容密集」**：考試 App 的核心畫面是「幾千題的可捲清單 + 長度差異極大的題目 + 內嵌數學式 + 圖表」。這在四種方案裡表現差異最大。RN 這邊 2026 年有 LegendList（原生支援不定高，不需要 estimatedItemSize）與 FlashList v2，跑在 Fabric 上是真正的原生 UIScrollView / RecyclerView，慣性、彈跳、捲動條、大標題收合都是系統給的。Flutter 是自繪，捲動物理是模擬的，在 iOS 上老手一摸就知道；更致命的是文字選取——考生會想長按複製題目，Flutter 的選取與放大鏡不是系統原生的。

**扣住「繁體中文」**：這是我不推薦 Flutter 的最硬理由。Flutter 因為自己畫字，必須自帶字體，而 flutter/flutter#16870（一律以 CN 變體渲染 CJK）與 #138386（Impeller 下 CJK 字重與對齊跑掉）到 2026 年仍是已知問題。對一個繁中考試 App，「骨、直、真、房」渲染成簡體字形是使用者第一眼就會回報的 bug。RN 在 iOS 直接吃系統 PingFang TC（體積 0、Dynamic Type 免費相容），Android 吃系統 Noto Sans CJK TC，這一條就省掉 8–12MB 和一整類字形災難。

**扣住「離線」**：現在專案的離線能力是 0——沒有 service worker、沒有 manifest.json，data/ 底下 6.6MB 的題庫是 `const X = [...]` 靠 script tag 全域載入（billing.js 387KB、ep-songs.js 290KB、card-sigs.js 291KB），使用者狀態塞在 localStorage（app.html 裡出現 53 次）。考試 App 的題庫規模用 localStorage 必掛（5–10MB 上限、同步 API 會阻塞 JS thread）。RN 這邊 expo-sqlite 是成熟解，題庫可以當 asset 打包 + delta 更新；Web 端用 sqlite-wasm + OPFS 可以共用同一份 schema 與同一組 Repository 介面。

**扣住「原生體感 + 系統整合」**：Widget、Live Activity、App Intents/Siri、分享、Apple Pencil——這些在 2026 年的 Expo 生態已經有路（expo-widgets 可用 React 定義 widget，expo-apple-targets 可掛 SwiftUI 的 Widget/Share Extension）。但要誠實：**Apple Pencil 手寫沒有現成方案**，PencilKit 的 PKCanvasView 要自己寫一個 Expo Module 包起來，Android 要接 Ink API，這一塊四平台完全無法共用，是最貴的長尾。

**扣住「已有 HTML/React 資產」**：這是選 RN 而非 Flutter/CMP 的第二個理由——語言與心智模型不換。app.html 裡 13,600 行 JS 邏輯搬進 packages/core 是「加型別、拆檔案、寫測試」，不是「翻譯成 Dart/Kotlin」。設計系統那 971 行 css/core.css 加上 app.html 第 19–177 行的 `<style>`（CSS 變數、深淺色、六套配色 tone）可以機械化萃取成 design token JSON，同時餵給 Web 的 CSS 變數和 RN 的 theme object。這是全部資產裡遷移成本最低、價值最高的一塊。

**桌面為什麼是 Tauri 而不是 react-native-windows/macos**：RNW 0.84 確實還在動（2026/04 仍有 commit），但 Microsoft 的支援政策是「新版釋出一個月後舊版進入維護、再兩個月變 Unsupported」——1–2 人團隊跟不上這個節奏，而且 RN-macOS 落後主線更多。反過來看，桌面上「原生手感」的期待值本來就低（大家都在用 Electron App），而且桌面不必過 App Store 4.2 那關（可走 DMG / MSI 自行分發）。Tauri v2 用系統 WebView，5–10MB，選單列、全域快捷鍵、檔案匯出、自動更新都是原生的，前端可以直接吃 apps/web 的建置產物——桌面與 Web 共用率 90% 以上，成本近乎於零。這是整個方案裡 CP 值最高的一步。

【誠實的共用率】
領域核心（TS）85–95% 共用。UI 層不共用：手機一套、Web/桌面一套。react-strict-dom 理論上能把 UI 共用拉到 50–60%，Meta 自己在 FB/IG VR 上跑到 60% 檔案共用，但官方文件仍寫著「under development，native 尚未全功能」——1–2 人團隊不該賭這個。實務估：**全專案共用率 55–65%**，其中 Web 與桌面之間 90%+，Web 與手機之間 40–55%（核心 + hooks/view-model 共用，component 各寫）。任何人跟你說「一次寫完到處跑」都是在賣東西。

【共用核心的邊界（packages/core 的鐵律）】
可以放進去：領域模型與型別、SRS 排程演算法、作答判定與計分、能力估計、同步的合併與衝突解、內容 schema 與版本協定、Repository 介面。
不可以放進去：任何 UI、任何 I/O 實作、任何 Date.now() 直接呼叫（時間必須當參數傳入，否則測不了）、任何平台 API。
判準：這個檔案能不能在 Node 裡零 mock 跑測試？不能就不屬於 core。

【必須各平台各自實作（不要硬共用，硬共用會兩邊都難用）】
- UI shell 與導覽：expo-router（手機 tab/stack、手勢返回）／ TanStack Router（Web URL、瀏覽器前後退）／ Tauri 原生選單列與視窗管理。三者的導覽心智模型不同，抽象化的成本高於重寫。
- 列表虛擬化：手機用 LegendList（不定高原生支援）；Web 用 CSS content-visibility: auto + contain-intrinsic-size（比自幹虛擬列表好維護太多）。
- 手寫輸入：iOS PencilKit（PKCanvasView，自寫 Expo Module）／ Android Ink API ／ Web Pointer Events + Canvas + 壓感。筆跡資料格式（點序列 + 壓力 + 時間戳）放進 core 統一，渲染各平台各寫。
- Widget / Live Activity：WidgetKit（透過 expo-widgets 或 expo-apple-targets）／ Android Glance。資料經 App Group 的共享 SQLite 讀取，**不可以**依賴 JS runtime 啟動。
- 通知與背景任務：iOS 用 expo-notifications 排本地通知（複習提醒必須用本地排程，不能寄望 BGTaskScheduler——它的執行時機由系統決定且不保證）；Android 用 WorkManager，並處理各 OEM 省電白名單。伺服器推播沿用 worker/src/watch.js 的偵測訂閱邏輯，把 mail.js 那條出口再加一條 APNs/FCM。
- 字型與動態字級：iOS 吃系統 PingFang TC + Dynamic Type；Android 吃 Noto Sans CJK TC + fontScale；Web 用 font-family stack + rem。品牌字（現在的 Huninn / M PLUS Rounded 1c 從 Google Fonts 載入）在 App 內必須改成打包或首啟下載，否則離線會 fallback。
- 分享 / Siri / App Intents / 深連結：各平台各寫，無共用可能。

【資料流】
題庫（唯讀）：content-pipeline 產出版本化 SQLite bundle → 首次安裝隨 App 打包（手機）或 SW precache（Web）→ 之後只下載 delta。題庫**不走**使用者同步層。
使用者資料（讀寫）：UI → core/exam 或 core/srs（純函式）→ Repository 介面 → 平台 db 實作 → 本地 SQLite（單一真實來源，離線可完整運作）→ core/sync 產生 oplog → worker → D1/KV。UI 永遠只讀本地，同步是背景行為，網路斷線對使用者完全無感。
數學式：建置期由 packages/math/prerender 把每道題的 LaTeX 轉成 SVG path + baseline metrics 存進題庫 → 執行期只做縮放與對齊（react-native-svg / Web 的 <svg>），零 runtime 排版、零 WebView、離線可用、四平台像素一致。**絕對不要在題目列表裡放 WebView**——每個 WKWebView 是獨立 process，這是內容密集 App 卡頓的頭號來源。只有使用者自行輸入公式的場景才需要 runtime 排版，那時再用 MathJax→SVG 的純 JS 方案，或用一個隱藏 WebView 當「排版計算服務」（只回傳 metrics，不當 UI）。
圖表：現有的手繪 <svg data-chart>（app.html 裡 11 處）是好資產——把繪圖計算（座標映射、刻度、路徑字串）搬進 core，輸出純資料，Web 用 <svg>、手機用 react-native-svg 渲染，共用率可達 80%。

【dc-runtime 的三樣搶救品】
1. 設計 token：app.html:19–177 的 CSS 變數（含深淺色雙套與六種 tone）→ packages/tokens/tokens.json。這是遷移成本最低、價值最高的資產。
2. 領域邏輯：app.html:3439–17097 的 class Component → 用 tools/migrate-dc 抽出後人工拆進 packages/core。BOOST 表、UNITS、PAGES、ALIASES（五百多條別名對照）這類純資料常數可以直接搬。
3. 後端：worker/ 那 4,559 行（auth / api / db / mail / watch / review / admin / chats）原地保留，只加推播出口與內容 CDN 路由。這是唯一一行都不用改的東西。
丟棄：support.js 整份（1,911 行）、<sc-if>/<sc-for>/{{ }} 模板語法、StreamableLogic 的 class 生命週期模式（改用 React hooks）。

## effort
【前提假設】以 2 人計（1 人主攻行動端、1 人主攻 Web + 共用核心），皆為熟練工程師但對 RN/Expo 有學習曲線；題庫內容本身（出題、校對、授權）不計入，那是另一條完全獨立的產線。

Phase 0｜地基與抽取（6–8 週）
- monorepo、TS 設定、CI、tokens 萃取管線：1.5 週
- 從 app.html 抽出 13,600 行邏輯、拆檔、加型別、補測試：4–5 週（這是最容易被低估的——舊碼沒有型別也沒有測試，每搬一段都要人工判讀意圖）
- content-pipeline 雛形 + data/ 那 6.6MB 轉成正規化 SQLite：1.5 週
產出：packages/core 可測、題庫有 schema。此階段對外**零可見產出**，要先講清楚。

Phase 1｜Web 版（10–14 週）
- 設計系統移植（現有的固定 px 與絕對定位要重畫成 flex + 相對單位）：3–4 週
- 核心畫面（題庫瀏覽、練習、模考、統計、設定）：5–6 週
- sqlite-wasm + OPFS + Service Worker 離線：2–3 週
- 數學式預渲染管線接上：1 週
產出：可上線的 Web 版，同時驗證了 core 的介面設計是否站得住。

Phase 2｜桌面（3–5 週）
- Tauri 殼、選單列、快捷鍵、檔案匯出、自動更新、簽章與公證：3–4 週
- 平台差異修正：1 週
產出：macOS + Windows 版。這是全案 CP 值最高的一段。

Phase 3｜iOS（16–20 週）
- Expo 專案、expo-router、設計系統 native 化：3 週
- 核心畫面 RN 重寫 + LegendList 調校：6–7 週
- expo-sqlite + 離線 + 同步接上：3 週
- 推播、本地通知排程、背景任務：2 週
- Widget + Live Activity（expo-widgets / expo-apple-targets）：2–3 週
- Dynamic Type、VoiceOver、深色模式、無障礙驗證：2 週（不要省，這是「原生體感」的一半）
產出：可送審的 iOS 版。

Phase 4｜Android（6–9 週）
- 大部分 UI 沿用 iOS 的 RN 程式碼，但要處理：Material 手感差異、返回鍵、字體打包、Glance widget、WorkManager、各 OEM 省電白名單、螢幕尺寸碎片化
- 實測經驗值：Android 的「補完」約是 iOS 工作量的 35–50%，不是傳說中的 10%。

Phase 5｜長尾（8–12 週，且永不結束）
- Apple Pencil / Android Ink 手寫模組：4–6 週（若列入 v1）
- App Intents / Siri / 分享擴充：2–3 週
- 上架流程、TestFlight、審查往返、被退件重送：2–3 週（4.2 不是風險，但 4.3 與 IAP 是）

【總計】
2 人並行、階段有重疊：**約 9–12 個月**到「四平台 v1 全部上架」。
1 人：**約 16–20 個月**，且中途放棄的機率很高。
若把 Apple Pencil 手寫從 v1 砍掉，兩種情境各省 1.5–2 個月。

【建議的實際排程（強烈建議不要並行四平台）】
第 1–2 月：Phase 0
第 3–5 月：Phase 1（Web 上線，開始收真實回饋）
第 6 月：Phase 2（桌面，低成本補刀）
第 6–10 月：Phase 3（iOS）
第 10–12 月：Phase 4（Android）
Phase 5 併入各階段末端。

【誠實的但書】
上面的數字假設「需求不變」。考試 App 的實際經驗是：題型會長出來（填空、拖曳配對、作圖、程式碼題）、報表會長出來、老師端/家長端會長出來。每多一種需要特殊互動的題型，四平台各加 1–2 週。抓 30–40% 的緩衝不算保守，是必要的。
