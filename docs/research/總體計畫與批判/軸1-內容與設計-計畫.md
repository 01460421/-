## 一、源檔格式：一單元一份 .unit.md

沿用 /home/user/Project-sekai-center/docs/research/內容深度/單元講解規格與範例章節.md 已經定死的規格（S01–S14、S07 七欄位、L1⊂L2⊂L3 單調包含、A2 單元 ID 命名）。這份規格已經是可 lint 的形式，不要重寫，直接當契約用。

檔案落點：$ROOT/content/{subject}/{chapter}/{UNIT-ID}.unit.md

為什麼不用 JSON：TeX 要雙重跳脫（\frac 寫成 \\\\frac）、prose 擠成一行、git diff 完全不可讀、無法寫註解。為什麼不用 .js：內容變程式碼，學科老師不能寫，而且會被吸進主 bundle。為什麼不用 MDX：內容能 import 元件就等於內容是程式碼，破壞「內容是惰性資料」這個讓整套快取與 CSP 模型成立的性質。

結構化的部分用型別化 fenced 區塊（區塊內是 YAML）：
- ```problem — S07 例題七欄位（題目/特徵辨識/想法起點/完整解/檢驗/變式提示/標籤）
- ```cardset — S14 速記卡（正/反面 + 難度）
- ```plot — 函數圖與統計圖規格
- ```tree — S10 解題決策樹（graphviz dot 的簡化 DSL）
- ```exam-table — S13 考點對照表

鐵則：任何含 TeX 的 YAML 欄位一律用區塊純量（key: |），不要用雙引號字串。這是這套格式最常見也最難查的一個 bug，寫進 lint。

front matter 必填（照 A3）：id, title, stage, subject, course, strand, exam, prereq, next, estimate{L1,L2,L3}, misconceptions, exam_tags, assets, version, authors, reviewed{subject,pedagogy,editorial}, sources[]。

sources 每筆結構化：{kind, ref, year, url, accessed}；歷屆題另用 origin: {exam:學測, year:113, subject:數A, number:12}。年度一律民國西元雙寫。

## 三、分片與快取

分片鍵必須是內容自身的穩定屬性（科目/章），章內成員只增不重排。
陷阱：如果分片是「按順序每 N 個一包」，新增一個單元會讓後面所有分片成員位移、hash 全變，一次小修訂就讓使用者重下整科。
$ROOT/content.lock.json 記錄 unitId → chunk → contentHash；建置時偵測到某單元換了 chunk 就明確報錯要求人工確認。

輸出格式沿用模板的兩種慣例：
- 內容分片 data/content/{subject}/{chapter}.js：ES module（export const UNITS = {...}），走 import('./data/content/math-a/polynomials.js?v=hash')，模組快取自動去重
- 目錄索引 data/index/{subject}.js：只有 id/標題/層級/預估分鐘/卡數/題數/難度，單科壓在 20KB 內
目標：一章 30–80KB（br），單元中位數 15–25KB。超過 150KB 再往下切節。

## 四、搜尋索引

第 0 步（P0，不可跳過）：先花一天用 200 題人工查詢集實測 Pagefind 的中文召回率。Pagefind 幾乎就是這套東西的現成 Rust 實作（建置期分片索引、零後端、MIT）。贏了就直接用，省下數週；下面的自建方案是它 CJK 表現不佳時的備案，不是預設。

自建方案（$ROOT/tools/build-search-index.py）：
中文用 bigram 不用斷詞器。理由：jieba 對「複數平面」「莫耳濃度」「原子軌域」這類學科詞會切壞，擴字典無止境；Intl.Segmenter 各引擎 ICU 版本不同、切法不一致，而只要索引端與查詢端的切法有一點分歧，召回率就會無聲地爛掉。bigram 是 Lucene CJKBigramFilter 的做法：不需字典、對未登錄詞天然免疫、索引端與查詢端共用同一個十行函式，不可能分歧。
三層索引：
1. data/search/titles.js（≤25KB br）——全站標題 + 別名 + 考點碼，開站 idle 時預載，供 ⌘K 即時第一屏。別名表沿用模板 ALIASES 的做法：寫在資料裡而不是塞進 AI prompt（它有五百多條，每次請求都送一遍太貴）。
2. data/search/{subject}/{bucket}.js——該科正文的 bigram 倒排索引，hash(term)%64 分桶，一次查詢只抓 1–8 桶（每桶壓縮後約 30–80KB），進到該科任一頁才載，支援離線全文。posting list 用 delta 編碼 + base36 存成字串（JS 解析比 JSON 物件陣列快得多）。df 存桶內供 BM25。
3. Worker /api/search（D1 FTS5）——跨科全文與拼錯容錯，離線時唯一缺席的那層。
排名：BM25 + 欄位加權（標題×5、S01 定位×3、考點碼×3）。

## 五、校對、勘誤與 AI 內容治理

$ROOT/tools/lint-content.py 是上架閘門，直接 fail build，不是流程建議。「請大家記得標來源」這種規範在幾百個單元的規模下必定失效。
檢查項：S01–S14 齊全且順序正確 / 字數落在規格區間 / S07 每題七欄位齊全 / 每個結論必須有 source 或 derivation 或 convention 三者之一 / prereq 與 next 指向存在的單元 / [[…]] 連結目標存在 / 每條 TeX 能被 KaTeX strict 編譯 / 每張圖有 alt 且沒有硬寫色碼 / layer 標記單調（L1-DANGLING 規則擋懸空指涉）/ 含 TeX 的 YAML 必須用區塊純量 / app.html 體積門檻。
輸出 GitHub Actions annotation 格式，直接標在 PR 的行上。

$ROOT/tools/verify-answers.py 是投報率最高的一道防線：AI 產生解析最常錯的正是計算與代數化簡，而那正好可以自動驗。用 sympy 對可符號化的題目（多項式、方程、微積分、極限、機率算式、單位換算、化學平衡係數）實際算一次，與 answer 欄位比對，不一致就 fail 並列出差異。無法符號化的題型標記 unverifiable 並強制走真人審查。

三重防線 + 一條紅線：
1. 機械驗算（verify-answers.py）
2. 第二個模型獨立解一次，答案不一致標 needs_human
3. 真人學科審查（GitHub CODEOWNERS 按科目分派 reviewer，front matter 的 reviewed.subject 記簽名者與日期）
紅線：絕不讓 AI 生成來源標註欄位。出處只能由人填或由題庫查詢自動帶入。AI 會產出看起來極度可信的假引用——錯的計算學生會算不出來，錯的出處沒有人會去查，那是整套系統最危險的失效模式。

預覽隔離：lint 依 reviewed.subject 是否有簽名決定單元進 data/content/ 還是 data/content-preview/。未經人工審查的單元物理上進不了 production 分片，不是靠 UI 藏起來。預覽站帶 noindex + 頂端顯眼橫幅。

勘誤流程：
第一階段用預填的 GitHub Issue URL（零後端、公開可追蹤、天然版控）。每個區塊右側「回報」按鈕預填單元 ID、區塊 ID、內容雜湊——雜湊是用來判斷該回報針對的是不是舊版內容。
量起來再搬進 Worker：新增 /api/errata 與一張 D1 表，沿用 /home/user/Project-sekai-center/worker/src/dashboard.js 既有的後台列表模式。
SLA 分兩級：影響答案正確性的 24 小時內修並發 hotfix 分片；錯字排週更。

$ROOT/tools/report-health.py 產一頁靜態 HTML：各科覆蓋率、審閱進度（未審/已學科審/已教學審/已編輯審）、AI 草稿比例、勘誤未結案數與平均處理時間、每單元字數與三視圖時長是否落在規格區間、知識圖譜孤兒節點與斷鏈。

## data_model
## 一、分層原則

三層，界線要一開始就畫清楚：
1. **建置產物**（不是使用者資料）：章節內容、複習卡定義、題目、目錄索引。存 data/*.js，吃一年 immutable 快取，永遠不進 localStorage、不進 D1。
2. **本機個人狀態**：小而扁平的偏好進 localStorage；量大或高頻寫入的進 IndexedDB。
3. **雲端**：D1，只在使用者主動登入後同步，且只同步「使用者無法重建的東西」。

## 二、localStorage 鍵名規劃（前綴 gsat-）

沿用模板的 sekai-* 前綴慣例，換成 gsat-。全部存取包 try/catch——無痕模式與部分 iOS 設定會直接丟例外，模板每一處都包了，照做。

偏好類（小、每次啟動就要讀，必須同步 API）：
- gsat-theme：light | dark | auto（給 head 內防閃爍腳本讀，鍵名不能改）
- gsat-tone：aurora | sakura | jade | wisteria | amber | ink（同上）
- gsat-font-scale：100 | 115 | 130 | 150
- gsat-subjects：JSON array，選考科目（決定首頁與側欄顯示哪幾科）
- gsat-exam-date：YYYY-MM-DD，倒數與排程收斂用
- gsat-device-id：UUIDv7，同步的分割鍵，第一次進站就產生，永不變更
- gsat-daily-cap：每日複習卡上限
- gsat-retention：0.85 | 0.90 | 0.95（FSRS 目標保留率）
- gsat-a11y：JSON，{reduceMotion, handedness:'left'|'right'}

狀態類（小，但會頻繁更新）：

## 三、IndexedDB（DB 名 gsat，版本化 schema）

為什麼不用 localStorage：複習紀錄會超過 5MB，而 localStorage 是同步 API，寫入會卡主執行緒。順手沿用模板既有模式是很自然的選擇，也是後來最痛的一次資料遷移——第一天就要分開。

store ops（keyPath: id）
  { id: uuidv7, card: cardId, ts: unix秒, rating: 1..4, dur: ms, dev: deviceId }
  append-only，永不修改、永不刪除（只在 checkpoint 折疊時搬走）。
  index: by_ts、by_card

store derived（keyPath: card）
  { card, stability, difficulty, due, reps, lapses, srcHash }
  這是 fold 的快取，可隨時整份丟掉重算。srcHash 是輸入 op 集合的雜湊，對不上就重算。

store progress（keyPath: section）
  { section, readAt, scrollPct, msSpent, layer }（layer = 讀到哪一層視圖）

store mistakes（keyPath: id）
  { id: uuidv7, q: questionId, chose, correct, reason:'concept'|'calc'|'misread'|'time', at, cleared: 0|1, sections: [sectionId…] }
  sections 由題目的 concept tag 反查得來，這條外鍵就是「回去讀哪一節」按鈕的依據。

store scores（keyPath: id）
  { id, kind:'mock'|'gsat', date, subject, raw, grade, note }

store tombstones（keyPath: key）
  刪除用墓碑。不然資料會從另一台裝置復活。

## 四、複習排程的資料結構（這是整個 data model 最關鍵的一個決定）

**review log 是唯一真相；stability / difficulty / due 全部由 fold(FSRS, 依 (ts, id) 全序排好的 ops) 推導出來。**

這一個決定同時解掉三個問題：
1. 換演算法（SM-2 → FSRS）或使用者重新最佳化參數時，歷史不用遷移，重算即可
2. 跨裝置同步不會有「哪台的 due_at 才對」這種無解衝突——因為 due_at 根本不同步
3. 兩台裝置離線各答同一張卡，在領域語意上兩筆都算數，用事件集合聯集就結束；而 row-based LWW 會把其中一筆吃掉

演算法選 FSRS（ts-fsrs，MIT，約 10–20KB，自架 /vendor）。SM-2 只有二十行、好懂，但在相同保留率下多排約 20–30% 的複習量。FSRS 是 Anki 24.11 起的預設，參數只有十幾個浮點數。
零歷史時用通用預設參數；累積足夠複習次數（建議 ≥ 500 筆）後在本機重訓一次個人參數，並跳一則說明。筆數不足時明確沿用通用參數，不要假裝已個人化。
學測特有條件（標準 SRS 不處理的）：日期固定、複習不是無限期。填入 gsat-exam-date 後切換「有終點模式」——任何會排到考後的間隔一律壓回考前；考前兩週自動轉全範圍輪掃。

fold 必須是純函式且可單獨測試——它決定所有裝置會不會收斂到同一個 due。

## 六、本機優先與雲端同步的合併策略

**核心手法：單寫者分割——每個裝置只寫自己的 key，讓衝突在結構上不可能發生。**

必須貼著既有後端的真實形狀設計。/home/user/Project-sekai-center/worker/src/api.js 的 /api/prefs 是一個 KV：GET 回整包、POST 逐 key upsert（db.js:66 的 ON CONFLICT DO UPDATE），**沒有 If-Match、沒有版本號**——同一個 key 被兩台裝置寫就是後到的無條件覆蓋。

key 佈局：
- srs/log/{deviceId}/{段序號}：複習 op log，一台裝置永遠只 append 自己的 key → 兩台裝置永遠不會寫同一個 key → 寫入衝突在結構上不存在，完全不必動 worker
- srs/ckpt/{deviceId}：90 天前已封存段折成的快照（也是 per-device，一樣沒有競爭）
- mist/log/{deviceId}/{段}：錯題 op log，同上
- prog/{deviceId}：閱讀進度（per-device，讀取時取 max(readAt)）
- settings：共享 key，唯一會真正衝突的地方

拉取流程：GET 整包 → 聯集所有 srs/log/* 與 srs/ckpt/* → 依 op id 去重 → 依 (ts, id) 排序 → fold。因為 op 以 id 冪等，**聯集本身就是正確的合併**，不需要任何「保留本機還是保留雲端」的對話框——那個對話框正是使用者實際弄丟資料的地方。

共享 key（settings）用**欄位級 HLC LWW**：每個欄位存 {v, t}，POST 前先 GET 合併。絕不能用整包 LWW——那會讓一台裝置改主題色就把另一台改的每日上限蓋掉，而且難以重現。

容量計算（必須算，不能猜）：op 用位置陣列 + 卡片字典 + ts delta 編碼壓到約 12–18 bytes。重度使用者一個月約 6000 筆 ≈ 90KB，安全。200 key 上限用「檢查點 + 尾巴」處理：每台裝置把自己 90 天前的已封存段折成快照後刪掉原始段。

刪除一律用墓碑，不然會從另一台裝置復活。

未登入時所有寫入都進 IndexedDB；首次登入時不問任何問題，直接聯集去重，並顯示「已合併 1,284 筆本機紀錄與雲端 3,051 筆，去重後共 3,977 筆」。

同步 UI：導覽列一顆小圓點——綠＝已同步、黃＝待上傳 N 筆、灰＝離線。Safari 不支援 Background Sync，同步只能在前景做，UI 上不要承諾背景同步。

寫入節流：複習卡排程與作答是高頻寫入。客端批次合併後上傳（每 30 秒或每 20 筆，取先到者），而不是每次翻卡都打一次 API。一萬名活躍學生每天數十萬筆，遠超模板現有的訂閱與通知量級。

## 七、要避開的資料模型陷阱

- 卡 id 用 unitId + 序號的穩定雜湊，內容修訂時 id 不變、歷史留存，只在 UI 標「內容已更新」。用內容雜湊當 id 會讓每次修訂都清空該卡的學習歷史。
- prefs 沒有刪除端點且 setPrefs 是整個 key 覆蓋（last-writer-wins），模板的 pullCloud() 只補「本機沒有」的鍵——所以在 A 裝置刪掉一筆，同步後在 B 裝置還在還會被推回雲端。單寫者分割 + 墓碑就是為了解掉這個。
- IDOR 防線靠的是「每支查詢都寫死 AND user_id = ?」這個紀律，不是框架保證。新增任何端點時，查得到但不是本人的一律回 not_found。
- D1 沒有跨 await 的交易。全站並發安全靠「條件式 UPDATE + 看 meta.changes」達成。任何「先 SELECT 再判斷再寫」的新程式碼在並發下都是壞的。
- 本機優先的資料遺失是真實風險：清除瀏覽器資料、換手機、iOS 對網站儲存的回收機制，都可能讓一年的進度消失。設定頁要顯眼提供「匯出我的資料（NDJSON）」，並在偵測到儲存空間壓力時提前警告。

## 一、六科視覺語彙：直接沿用模板 UNITS 的六團色票

/home/user/Project-sekai-center/app.html:3502 的 UNITS 已經有六組在深淺主題下都驗證過的色 + 對比前景色（t 欄位），色相分得夠開。直接對應六科，省掉整輪配色設計，也讓使用者在幾天內建立顏色記憶。

| 科目 | slug | 色（--subj-*） | 前景（--subj-*-on） | 來源 |
|---|---|---|---|---|
| 國文 | chinese | #ee6644 | #fff | vbs |
| 英文 | english | #4455dd | #fff | ln |
| 數學A | math-a | #44cccc | #0c2b29 | vs |
| 數學B | math-b | #88cc44 | #1d2610 | mmj |
| 社會 | social | #ffbb33 | #2b2208 | wxs |
| 自然 | science | #aa66cc | #fff | n25 |

子科用同色相的明度階，不另開色相——第七、第八個顏色只會稀釋記憶：
- 社會三子科（歷史 / 地理 / 公民）：#ffbb33 的 oklch L 各差 8%（歷史 L−8、地理 L±0、公民 L+8）
- 自然四子科（物理 / 化學 / 生物 / 地科）：#aa66cc 的 L 各差 6%

深色下必須提亮，比照模板對 tone-* 的處理（app.html 第 105–115 行）：深色時 --subj-*-deep 要比 --subj-* 更亮，否則在 #0c0f1d 底上會糊掉。每個科目定義四個 token：--subj-{k}（主色）、--subj-{k}-on（其上文字）、--subj-{k}-deep（深色模式提亮版，也是連結色）、--subj-{k}-soft（color-mix(in oklab, var(--subj-{k}) 13%, transparent)，選中底色，與模板 navGroups 的算法一致）。

用法：科目首頁與其下所有章節頁的頂部 4px 色條、麵包屑第一段的色點、側欄目錄的選中底色、進度環與圖表的序列色、搜尋結果的科目標記。

**六科色不得是唯一區辨**。六個色相在色覺缺陷者眼中可能塌成三組（尤其 math-b 綠與 chinese 紅橘）。每科同時有固定圖示（Unicode 或 inline SVG）與文字標籤，顏色只是輔助。

## 二、深/淺色三態：照抄模板結構，只換數值

模板的三態機制已經是對的，結構不動：
1. head 內同步 <script> 讀 localStorage 打 theme/tone class（app.html:7–9）——這是防閃爍的第一件套
2. `:root{}` 淺色 → `@media(prefers-color-scheme:dark){:root:not(.theme-light){…}}` → `:root.theme-dark{…}`，深色值寫兩份（一份給系統偏好、一份給手動），並用 `:not(.theme-light)` 讓手動淺色能否決系統深色
3. `color-scheme` 宣告必須保留（prefers-color-scheme 只是「偵測」，color-scheme 才是「宣告」），以及 select option 的明確配色（app.html:164–176）——Safari 深色下 option 顏色不能只靠繼承

**兩套主題類名的不一致必須在新站消滅**：模板 app.html 用 `.theme-dark/.theme-light`，index.html + css/core.css 用 `.dark`，卻共用同一個 localStorage 鍵。新站只用一套（`.theme-dark` / `.theme-light`），若之後要沿用 iframe ?embed= 面板協定，子頁一開始就用同一套類名。

## 三、六色調 tone 系統：保留但降級為「氛圍」

模板的 SKINS（aurora / sakura / jade / wisteria / amber / ink）照抄 applyTone()，但語意改變：在遊戲站 tone 是強調色，在學科站科目色才是主角。所以 tone 只覆寫全站的 --accent / --accent-deep / --cta / --rainbow（UI 元件、按鈕、焦點框），**絕不覆寫 --subj-***。預設 aurora 不加任何 class。
設定頁的文案要說清楚：「配色風格只影響介面色調，六科的顏色不會變。」

## 四、字體

模板正文用 'Huninn'（圓體）。圓體在 UI 上很好，但長文閱讀可讀性差，這站的主要頁面是幾千字的章節閱讀，必須分開：
- **正文**：`'Noto Sans TC', 'PingFang TC', 'Microsoft JhengHei', sans-serif`，字重 400，行高 1.9
- **標題與 UI**：保留 `'Huninn', 'M PLUS Rounded 1c', …`，維持模板的個性與辨識度
- **數學**：KaTeX 自帶（KaTeX_Main / KaTeX_Math / KaTeX_Size*），自架 /vendor/katex/fonts，不走 fonts.gstatic.com
- **等寬**：`ui-monospace, 'SF Mono', 'Cascadia Code', Consolas, monospace`，用於化學式、程式碼、數據表

字型全部自架在 /vendor（拿掉對 fonts.googleapis.com 的依賴，這是模板 helmet 裡唯一的外部 CSS 來源，也是未來立 CSP 的障礙），並用 fonttools 依全站實際用字產生 unicode-range 分片：常用 3500 字先載（≤60KB），罕用字後補。所有 @font-face 加 `font-display: swap`。

字級四段（100 / 115 / 130 / 150%），全部用 rem，根字級由 `gsat-font-scale` 控制。必須確保 150% 字級 × 320px 寬不破版、不出現橫向捲動——這是 lint/CI 的一條檢查。

正文行寬 `max-width: 34em`（約每行 38–42 個中文字）。

## 六、動效

模板的 --anim 是 .5s，那是給遊戲站的頁面轉場用的。內容站要更快：
- --anim-page: .24s（換頁淡入，沿用 pageIn keyframe）
- --anim-ui: .14s（按鈕、摺疊、hover）
- easing 沿用模板 `cubic-bezier(.32,.72,.24,1)`

禁止項：內容區的自動輪播、視差捲動、翻卡 3D 動畫（改用淡入）、任何非使用者觸發的位移動畫。

## site_concept
一個把「學測六科的完整複習內容」與「個人化的練習閉環」焊在一起的靜態內容站：每一節都是一份可被 lint 檢查的單元講解（一句話定位 → 先備自測 → 直覺 → 定義 → 推導 → 必背清單 → 四級例題階梯 → 迷思概念 → 變式陷阱 → 解題決策樹 → 跨科連結 → 考點對照 → 速記卡），同一份原始檔投影出「速覽 3 分／紮實 30 分／深挖」三種視圖；讀完的每一節底下都掛著它自己的複習卡與考古題，答錯的題目會自動歸因回它所屬的節，長成補救卡並排進明天的計畫。對象是準備學測的高三生與提前規劃的高一高二生，其次是需要查制度、查級分、查落點的家長與導師。跟補習班網站的差別是：這裡沒有押題、沒有名師、沒有課程要賣，所有結論都必須有推導、有出處或明確標示為約定，三者缺一就不得上架，而且每一則制度數字都帶學年度與官方連結，過期會自動掛警示。跟筆記共享站的差別是：內容不是眾人上傳的散裝 PDF，而是有固定結構、有交叉引用、有人工學科審查簽名的單一知識庫，所以它可以被搜尋、被排程、被自動出卡、被 AI 助教引用出處——共享站做不到這些不是因為沒做，是因為散裝內容在結構上就承載不了。技術上不需要伺服器渲染也不需要付費訂閱：內容是建置期預先算好的惰性資料，讀內容永遠不用登入、離線可用，登入只綁跨裝置同步。
