# 對「跨平台超大型考試準備 App」藍圖的破壞性檢視

## 先講三個會直接殺死專案的結論

**A. 藍圖的題量比它自己的驗收標準少 3–7 倍，這使 Phase 3 在數學上不可能通過。**
- Phase 1 定義：一個 unit = 12 個知識點節點。Phase 3 定義：60–80 個 unit → 720–960 個葉節點。
- Phase 3 的 exit criteria 寫「每個葉節點 ≥15 題」→ 需要 **10,800–14,400 題**。
- Phase 3 的交付物寫「1,300–1,800 題」。**差 6–8 倍。**
- 更糟：`intelligent_engine` 明訂「每個知識點至少要有 6 題原子題」→ 720 × 6 = **4,320 題原子題**，單獨就超過整個 1,800 題的預算 2.4 倍。也就是說**先備責任歸因（藍圖列為核心差異化之一）在 Phase 3 的題量下根本不可能運作**。
- 原始研究自己算的是「高中數學 A/B ~350 葉節點 × 18 題 = 6,300 題」。藍圖把題量砍到 1,800，卻沒有同步砍掉覆蓋率標準與原子題需求。
- **怎麼修**：三選一，現在就選。(a) 把葉節點顆粒度放粗到 250–300 個（一個 unit 4–5 個節點而非 12），覆蓋率標準改成「每節點 ≥8 題、其中 ≥3 題原子題」→ 需求降到 2,400 題，接近可行；(b) 保留 12 節點/unit，但範圍砍到 18 個主單元中的 5 個；(c) 承認 Phase 3 是 6,000+ 題並把工期乘以 4。**不准三個都不選然後照原計畫開工。**

**B. 內容工時估算與藍圖自己的單位成本互相矛盾，差 4–5 倍。**
- 藍圖 `cost_model` 自己寫：單題全流程 0.9 人時、教材 498 字/小時（500 萬字 = 5.7 人年）。
- 套用到數學 A：40 萬字 ÷ 498 = **803 小時（教材）**；1,550 題 × 0.9 = **1,395 小時（題目）**；合計 **≈ 2,200 小時 ≈ 15 個月全職**。
- 藍圖同一段卻寫「撰稿 320–420 小時 ＋ 標註 90–120 小時 = 410–540 小時 = 3–4 人月」。**光教材就是這個上限的 1.5 倍，題目再多 2.6 倍。**
- 即使套用藍圖自己承認的「AI 淨節省 35–45%」，仍是 **1,300 小時 ≈ 7.5 人月**，是宣稱值的 2 倍。
- Phase 1 的 60–100 小時/unit 反而是自洽的（5,700 字 ÷ 498 ≈ 11.4h + 70 題 × 0.9 ≈ 63h ≈ 74h）。**所以錯的不是單位成本，是乘法。**
- **怎麼修**：把 Phase 3 的 12–14 週內容工期直接改成 **8–13 個月**，然後你會發現這個 Phase 不該存在（見第 8 點）。並且把 Phase 1 exit criteria 第 5 條升格為 **kill switch**：若實測單一 unit > 40 小時，則整科 > 2,400 小時，強制觸發「改變策略」分支（找共同作者／砍到 5 個單元／改成解題導向），而不是繼續往 Phase 2 走。目前的計畫量了這個數字但不讓它改變任何事。

**C. 損益平衡點需要該科考生約四分之一的市佔，而整份藍圖沒有任何獲客章節。**
- 藍圖自己算：640 個付費使用者 → 3% 轉換 → **21,000 個活躍使用者**。學測數學 A 每年報考約 7–9 萬人。21,000 = **25–30% 的全體考生**。
- 12–18 歲族群、付費權在家長、無品牌、無通路，3% 轉換是樂觀值；1.5% 更接近現實 → 需要 **42,000 活躍 = 半個世代**。
- 八個 Phase、42 人年的內容估算、19 條法遵條目——**零行關於「使用者從哪裡來」**。SEO 只出現在一個表格儲存格裡。
- **怎麼修**：在 Phase 0 補一份三頁的獲客假設，並讓它決定內容策略。若答案是 SEO 長尾（「配方法 例題」），那 v1 的內容形態應該是**可被 Google 索引的公開解題頁**，而不是登入後的 App；這會反過來改變資料模型與路由設計。若答案是 B2B（賣補習班，客單價 100×，只需 200 個機構），那家長端／老師端的優先序要從 Phase 6 拉到 Phase 2，整個產品取捨不同。**這一題不回答，前面所有工程決策都是在賭。**

## 1. 範圍失控

- **藍圖把差異化寫在內容裡，卻把約 60% 的工程量花在引擎上。** `product_concept` 明說三個空缺是「講解品質、誤答診斷、考試日感知」。其中「誤答診斷」的完整價值——學生選了 D，系統告訴他「你把 √(x²) 化簡成 x」——**只需要在 `.item.md` 的每個誘答填一段文字，然後把它顯示出來。零演算法。** Elo、BKT、MST CAT、log-odds 六分類、閉迴路修正 δ、交錯約束修復、挫敗四級階梯，在 5–50 個使用者、每題 2–5 筆作答的情況下，全部退化成「按作者標的三級難度出題」。
- **具體被高估的項目與處置**：
  - `MST 15 分鐘診斷`（Phase 2）：20 題估 8 個領域，σ 不可能降到 0.30 以下，依藍圖自己的誠實規則會對大多數領域顯示「資料不足」。第一次使用就看到一整頁「資料不足」是最糟的開場。**砍掉，改成「你想先練哪一章」+ 3 題確認。**
  - `建置期預渲染 SVG + baseline metrics`：這是 React Native 的問題，v1 是 Web。**砍掉，見第 2 點。**
  - `內容包 zstd + 唯讀 SQLite + Ed25519 簽章 + bsdiff 差量`：v1 是自家 HTTPS origin，TLS 已經解決中間人；藍圖自己說 R2 零 egress，所以 bsdiff 省的是已經是零的錢。**三項全砍。**
  - `op-log + HLC + 冪等閘 + golden replay`：v1 是單裝置 Web，沒有第二台裝置要合併。**砍到只剩「attempt 用裝置端 ULID 當主鍵、伺服器 INSERT OR IGNORE」，這是 5 行。**
  - `DTCG token pipeline + contrast.lock + Style Dictionary + 四平台產物`：v1 只有一個平台。**改成一個 `tokens.css`，contrast 用一次性腳本檢查完就好，不進 CI。**
  - `pnpm workspace + Turborepo`：Turborepo 的快取在一個 app、一個人、無 CI 分鐘費用的情況下是純負債。**改成單一 Vite 專案 + 一個 `content/` 目錄。等第二個 app 出現再拆。**
  - `dist/ 進版控 + CI 重建比對`：防的是「有人手改產物」——沒有別人。**砍掉。**
  - `六層 lint`：**留 L0（schema）、L3（誘答缺 diagnosis 即 error，這是差異化本身，10 行）、L4（授權）。L1/L2/L5/L6 降為警告或砍掉。**
  - `考招制度模組`（Phase 3，4–6 萬字 + 150–200 個逐年欄位 + 0.2–0.3 人力常駐）：這是**第二個產品**，與「講解品質」的定位無關，且帶來永久維運負債。**v1 用一頁靜態說明 + 連到大考中心官網。**
  - `靜音窗 22:30–07:30 寫死 + 單元測試`：v1 Web 沒有推播系統。**這是在測一個沒有人呼叫的函式。連同整個推播設計一起砍到 Phase 4。**
  - `筆跡資料格式必須第一天定成中性格式`：v1 不存任何筆跡，就沒有格式要定，也沒有遷移成本。**砍掉這條「day-one 決定」。**
  - `L0/L1/L2 危機分級偵測器`：見第 7 點——Phase 1 沒有 AI 對話、沒有情緒自評，**偵測器沒有任何輸入來源**。留下靜態求助資源頁（1 天工作量、內建於 bundle），砍掉偵測器、分類器、90 天保留政策與心理專業審核的模板（後者是外部相依，前置 4–8 週）。
- **只能留三個功能，我會留**：
  1. **讀得懂的單元講解（只做 L2 一個視圖，不做三視圖投影）＋ 逐題詳解，含「想法起點」欄位。** 這是整個定位的本體。
  2. **作答 → 錯了立刻顯示「你選的這個選項對應的迷思概念」（純查表，零統計）→ 進錯題本。**
  3. **固定間隔的錯題複習佇列（1/3/7/21 天，以同知識點變式題重出），加上唯一一條考試日規則：距考 ≤7 天不引入新內容。**
- 這三件事不需要 Elo、不需要 IRT、不需要 BKT、不需要 CAT、不需要 CAS、不需要 AI、不需要離線、不需要同步。而它們涵蓋了藍圖自己宣稱的三個市場空缺中的兩個半。

## 2. 技術風險

- **跨平台選型（Web → iOS → Android → 桌面，不並行）是這份藍圖最正確的決定，不要動它。** 以下是它站不住的地方。
- **「數學式建置期預渲染成 SVG」被錯誤地升格為 day-one 架構決定。**
  - 引用的 200–500ms 閃爍是低階 Android 上 RN 執行期渲染的數字。**v1 沒有 Android，沒有 RN。**
  - 在 Web 上，SVG 預渲染讓你失去：文字選取與複製、全文搜尋、隨字級縮放、深淺色繼承、無障礙。而 KaTeX 的正確建置期產物是 **HTML + CSS（SSR 模式），它同一次就會輸出 MathML**，搜尋、朗讀、縮放全部免費解決，體積比 SVG 小，而且沒有 baseline metadata 這個坑。
  - **怎麼修**：v1 用 KaTeX SSR 產 HTML+MathML（或乾脆執行期渲染，一頁 12 條式子在瀏覽器是幾毫秒）。SVG + baseline metrics 的整套工程延到真的開 `apps/mobile` 那一週再做。省下 Phase 0 的一根釘子與 Phase 1 的一週。
- **`golden replay：任意順序重放，θ 與 FSRS 狀態位元相同` 是一個聽起來嚴謹但測不到東西的驗收標準。**
  - Elo 依定義是順序相依的：`K_u = 0.8/(1+0.05·n_u)` 隨作答數衰減，且 `p` 依賴當下的 θ。**同一組事件不同順序必然得到不同 θ。** FSRS 的 S/D 依賴 elapsed interval，同樣順序相依。
  - 所以這條標準只有兩種結果：先按 HLC 排序再重放（那你測的是排序穩定性，不是順序無關性），或者不排序（那它永遠失敗）。
  - **「位元相同」本身也不可達成**：FSRS 大量使用 `Math.pow` / `exp`，ECMAScript 不要求正確捨入，不同引擎（V8 / JavaScriptCore / Hermes）與不同 CPU 可能有 ULP 級差異。你在 Phase 4 換到 Hermes 的那天這個測試會紅，而且原因與你的程式碼無關。
  - **怎麼修**：改成「亂序 + 重複 + 時鐘倒退的事件流，經 HLC 排序後重放，結果與順序到達相同，容差 |ΔS| < 1e-6、|Δθ| < 1e-6」。若真要位元相同，θ 與 S 必須改成定點整數運算——那是另一個決定，現在不值得。
- **`個人化 FSRS 參數` 破壞了「衍生狀態可從事件重放」這個基石，而藍圖沒有察覺。**
  - 21 個 w 在裝置端用 MLE 擬合。兩台裝置的 review_log 進度不同（一台 400 筆、一台 380 筆）→ 參數不同 → **同一組事件重放出不同的 S/D**。
  - **怎麼修**：參數擬合本身必須是一個帶 HLC 的 op（`fsrs_param_updated`），進入事件流；重放時參數也依時間點切換。否則就明訂「個人化參數是裝置本地的展示層優化，不參與重放與同步」，並接受兩台裝置的到期日不同。**兩者選一，寫進 `packages/core/srs` 的 README。**
- **「壞題回溯重算 θ」與「θ 在裝置端」互相衝突。**
  - Phase 2 exit 要求「回溯重算了受影響使用者的 θ」。但若 θ 是裝置端從本地事件流增量算出來的，伺服器沒有權限也沒有資料去重算——它只能推一個「作廢題目 X」的 op，然後每台裝置自己從頭重放。這要求裝置永久保留全部 attempt 歷史，且重放成本 O(全部歷史)。
  - **怎麼修**：明訂**伺服器是衍生狀態的事後權威**——夜間批次重算 θ 並下推覆蓋；裝置端的增量 Elo 只是樂觀估計。同時在裝置端存 `(θ, n, hlc_watermark)` 檢查點，只重放 watermark 之後的事件；收到亂序舊事件時退回上一個檢查點。**這兩句話現在不寫，Phase 2 會卡住兩週。**
- **iOS Safari 的 ITP 不只是「不能承諾離線」，它是一個資料遺失漏洞。**
  - Phase 2 的設計是「離線作答寫入 OPFS 的 outbox queue」。ITP 在使用者一段時間未開啟後清除儲存 → **outbox 連同未上傳的作答一起消失，而且是靜默的**。Phase 2 exit 卻要求「恢復連線後事件零遺失」。
  - **怎麼修**：(a) 線上時**每答一題立刻上傳**（一筆 attempt 幾十 bytes，不要為了省 request 而批次 30 秒）；(b) 呼叫 `navigator.storage.persist()` 並把結果顯示給使用者；(c) 放一個 sentinel key，開啟時發現 OPFS 有資料庫但 sentinel 消失 → 明確告知「瀏覽器清掉了離線資料」；(d) **最務實的：v1 不做離線。** 500 個使用者、Web、你自己一個人——離線是 Phase 3 之後的事。
- **D1 的限制被低估的地方不是容量，是這兩條：**
  - **每次查詢最多 100 個 bound parameters。** 原始研究抓到了，藍圖整段刪掉了。批次上傳 20 筆 attempt × 8 欄 = 160 個參數，**上線第一天就撞牆**。修法：用單一 INSERT 帶一個 JSON 參數 + `json_each()`，或 `db.batch()` 每句自控在 100 以內。這一條寫進 `db.js` 的檔頭註解。
  - **D1 沒有互動式交易，`db.batch()` 是唯一的交易原語。** 「插入 applied_op → materialize → 更新 srs_state」必須塞進同一個 batch，且中途不能讀取再決定寫什麼。這會逼你改寫套用邏輯。
  - 藍圖的遷移門檻（每日 100 萬事件 / attempt > 4GB）是合理的，保留。但要補一句：**`wrangler d1 export` 在 attempt 表變大後會逾時**，備份腳本要一開始就按月份分段匯出，不要等到匯不出來才發現。
  - 附帶：`server_seq 可見性空洞`這個 bug 在 D1 的單寫者模型下意外不會發生，但**一旦開啟 Sessions API 讀取複本或搬到 Neon 就會回來**。在 `sync/` 的註解寫下這句話，否則三年後沒人記得為什麼原本沒事。
- **兩個控制器互打**：挫敗保護 L1「靜默把 p* 從 0.80 拉到 0.88」與閉迴路修正 `δ ← δ + 0.3·(p_obs − p*)` 會互相對抗——保護拉高成功率，積分器觀察到 p_obs 上升就把難度推回去。**修法**：保護模式期間凍結 δ 的更新。一行程式碼，但不寫就會產生「難度莫名其妙震盪」的除錯地獄。

## 3. 內容瓶頸與冷啟動

- 藍圖**口頭上**正視了內容瓶頸（「內容是序列瓶頸，AI 幫不上」），但**排程上完全沒有**：Phase 3 給內容 12–14 週去做一件 2,200 小時的事。口頭承認不等於正視。
- **藍圖漏掉的最大變數：一個人寫到第 20 個單元會停下來。** 獨立內容專案的典型死法不是算錯工時，是第 4–6 個月的內容疲勞。藍圖有 spike、有 exit criteria、有護欄指標，**沒有任何一條在處理「作者本人會撐不住」**。修法：Phase 3 必須設計成「每 5 個單元就有一次可上線、可收到回饋的發布」，而不是 18 週後一次交付；並且明訂一個心理停損點（連續兩週產出低於 50% → 強制觸發找共同作者的分支）。
- **冷啟動策略藍圖完全沒有考慮的一條，而它便宜 15 倍**：
  - 藍圖自己查證了 **§9 第 1 項第 5 款：依法令舉行之考試試題不受著作權保護**，而數學科幾乎沒有嵌入第三方著作（`has_embedded_work=false`）。
  - 近 10–15 年學測數學 A 歷屆題約 **200–300 題，題目本身零撰稿成本**，只需要自寫詳解 + 誘答診斷標註 ≈ **25 分鐘/題 → 85–125 小時 → 3–4 週**。
  - 這是使用者**最想要**的東西（考古題全解），有現成搜尋量，而且是最乾淨的授權區。
  - **對照組**：1,500 題原創題 = 1,395 小時。**差 11–16 倍。**
  - 藍圖把歷屆題當補充（Phase 3 的 `gsat-2024-math-a-07.item.md`），**它應該是 v1 的骨幹。**
- **第二個冷啟動槓桿：不寫教材。** 40 萬字教材是最貴的單一項目（803 小時），而且是與課本、參考書、YouTube 正面競爭、你最沒有優勢的部分。藍圖自己說差異化在「想法起點」與「誤答診斷」——這兩者加起來的字數是教材的 1/5。
  - **怎麼修**：v1 的內容單位不是「單元講解」，是「一題的完整思路」。S01–S14 的 14 區塊規格砍到 5 區塊（考點、想法起點、標準解法、常見迷思、變式）。等到有 200 個付費使用者且他們明確要求「我想從頭學一遍」時再寫教材。
- **「每題多花 8–12 分鐘寫誘答診斷」這個決定要保護，其他都可以砍。** 它是整份藍圖裡唯一「競品短期內無法複製」的東西，而且它是內容實務不是工程，不依賴任何演算法。

## 4. 智慧引擎的空轉風險

- **藍圖有退路，但退路不夠深，而且沒有一個開關把它們一次關掉。**
- 具體會空轉的地方（以 50 個使用者、每人 60 題/日 計算）：
  - **題目難度 b 永遠不會收斂**。50 人 × 60 題散在 1,800 題上 → 單題每月 2–5 筆作答。藍圖自己的分級：`n<30 用命題者先驗`。**所以整個 v1 期間，b 就是作者標的三級難度標籤。** 於是 `b* = θ − logit(p*) − δ` 這條核心公式，在 v1 的資訊量等於「按易/中/難出題」。你寫了 3,000 行去得到 20 行的效果。
  - **θ_kc 的 σ 降不下來**。12 個知識點、每個 5–8 題 → σ ≈ 0.8–1.0。藍圖誠實地規定「max(P) > 0.6 才顯示分級」，結果就是**幾乎永遠顯示「資料不足」**。
  - **錯因六分類需要每題按題型的 median/P25/P75/P90 作答時間**——那需要每題 30+ 筆作答。v1 期間**沒有任何一題達標**，所以分類器會在垃圾百分位數上運行，然後被信心門檻 0.55 全部擋下，什麼都不顯示。**寫了整套東西，行為等同於沒寫。**
  - **Phase 2 exit 的校準度標準（10 桶、每桶偏差 <0.08）會因為 b 未收斂而失敗**，失敗原因與產品品質無關。這個 gate 會浪費你兩週去追一個不存在的 bug。
- **怎麼修（這是我最強烈建議的一條）**：
  - 在 `packages/core` 開一個 **`engine_mode` 全域開關**，v1 硬編在 `static`：
    - 出題 = 章節順序 × 作者難度階梯（易→中→難）× 錯題優先重排
    - 複習 = 固定間隔 1/3/7/21 天，連續兩次答對移出
    - 掌握度 = 「這個知識點你做對 8/12 題」，**不顯示任何 θ、σ、p(L)、S、R**
    - 錯因 = 只做一件事：選中帶 `misconception` 的干擾項 → 顯示該迷思的預寫文字；其餘不歸因
  - `adaptive` 模式的程式碼可以寫（甚至可以先寫好），但**掛在開關後面、不進 v1 的 UI、不進 v1 的驗收標準**。開啟條件寫死：某科單日作答 > 5,000 筆且該科 ≥ 200 題的 n ≥ 200。
  - **FSRS 保留，但只保留兩件事**：預設 21 參數的 `R(t,S)` 與 `I(r,S)`（純函式，30 行），以及「距考 ≤7 天 `daily_new_cap = 0`」。砍掉個人化參數、負載平滑、逆向規劃、動態 r_target 四階段。這是整個引擎裡唯一在零資料下就成立的部分（FSRS 的預設參數是族群先驗，不需要你的資料）。
- 這個切法的好處：**`static` 模式下的使用者體驗與 `adaptive` 幾乎沒有差別**（因為 adaptive 的輸入是垃圾），但工程量差 10 倍，而且沒有任何「演算法給出詭異推薦」的除錯成本。

## 5. 法律

- **著作權的第 9 條分析本身是好的、查證扎實的，但它被放在錯誤的時序位置上。**
  - 藍圖把「函詢智財局確認學測是否為『依法令舉行之考試』」放在 `open_questions`，同時把「歷屆題直接可用（§9 免除）」寫進 Phase 1 的選題理由。**如果整個內容策略建立在這個定性上，這封信必須在寫第一題之前寄出。**
  - 而且定性強度是有差別的：國中會考的法源明確（國民教育法、高級中等學校教育法、成績評量準則）；**學測是財團法人依大學法與招生規定辦理，「依法令舉行」的認定相對弱一點。** 藍圖對兩者用同等的確定語氣，這是過度樂觀。
  - **怎麼修**：(1) Phase 0 第一週寄出函詢（智財局電子郵件諮詢 + 正式函釋雙軌）；(2) 設計上讓產品**在定性不利時仍然成立**——`rights_flags` 欄位已經存在，要真的用：歷屆題全部標記可一鍵批次下架，且下架後產品仍有自製題可用；(3) 只用數理科歷屆題；(4) 逐題重打、自寫詳解，**不做整卷重製**（整份試卷的選擇與編排可能構成編輯著作，是第二層風險，藍圖只在研究裡提過一次）。
- **會先收到存證信函的，多半不是大考中心。** 藍圖把 19 條法遵幾乎全押在著作權，但一人公司實際會遇到的前三件事是：
  1. **家長因為落點推估或 AI 批改失準要求退費並公開發文**。修法：服務條款要有明確的推估免責與退費政策，所有推估標「非官方」並揭露推估基礎（藍圖有寫，但要真的做成 UI 元件而不是條款文字）。
  2. **出版社或補習班主張你的題目與他們的高度相似**。數學題的獨立創作撞題率極高，SimHash > 0.85 是常態不是異常。修法：保留每題的創作歷程（草稿 commit、時間戳），作為獨立創作的證據——**這正好是 `content/` 進 Git 的第二個理由**，把它寫進理由清單。
  3. **未成年人契約效力**（民法 77–79 條）——藍圖完全沒提。16 歲學生訂閱 NT$149/月，法定代理人可拒絕承認、要求返還，形成爭議款與拒付。修法：訂閱流程要有家長同意環節，或直接把付費主體設計成家長帳號；iOS 的 Ask to Buy 只能部分緩解。
- **最嚴重的一條內部衝突：兒少權法第 53 條的責任通報義務，與藍圖「L2 明確自傷訊號時不自動通報家長」的設計，可能直接抵觸。**
  - 藍圖把兩者並列（一條在 `core_flows` 說不通報，一條在 `legal_compliance` 說要問律師），**但沒有解決它**。若營運者被認定屬第 53 條的責任通報人員，24 小時內未通報主管機關是可罰的。
  - 更麻煩：若隱私政策承諾「不通報」，之後又依法通報，通報本身可能構成違反自己揭露的個資使用目的。
  - **怎麼修**：v1 若砍掉危機偵測（見第 1 點），這個問題暫時消失——**這是砍掉它的第二個理由**。等到真的要做 AI 對話時，先取得書面法律意見，並把隱私政策寫成「在法律要求的情況下我們可能必須通報主管機關」，而不是「我們不通報」。**不要在沒有法律意見前上線任何會接收自傷訊息的介面。**

## 6. AI 成本與正確性

- **成本數字本身沒問題，但它是為一個不存在的 v1 算的。**
  - 1,800 題預生成詳解 ≈ US$50（Opus 5 + Batch）這個數字檢查下來是合理甚至偏保守的。
  - 但 v1 只有 60–80 題，且藍圖說 v1 沒有 AI 家教。**所以 v1 的 AI 成本接近零**（只有「換個說法」，500 人 × 每月 20 次 × $0.008 ≈ **US$80/月**）。
  - 「6 萬 DAU 全 Opus 5 = US$756,000/月」是稻草人——沒有人會那樣蓋。拿它當「架構決定生死」的論據是修辭。真正要管的數字是 US$80/月，而它小到不需要任何架構。
  - **怎麼修**：把整個 AI 成本模型移到 Phase 3 的附錄，v1 的預算行寫「US$100/月上限，超過就關掉」。不要讓一個 Phase 3 的問題塑造 Phase 0 的架構。
- **真正被漏掉的成本是人審工時，不是 token。**
  - 1,800 篇 AI 生成的詳解，一篇人審 5 分鐘 = **150 小時**。這 150 小時**不在 Phase 3 的 18 週裡**。
  - 而 lint 的 L0–L6 沒有任何一層能檢查「這篇詳解的數學是否正確」——那本來就不可自動化。
  - **怎麼修**：明訂「AI 生成的詳解在人審簽核前一律 `status: draft`，不對使用者顯示」，並把 150 小時排進計畫。或者更好：**v1 只有 60–80 題，詳解由人寫**（那才是「講得清楚」這個定位的本體，外包給模型是自毀定位）。
- **安全模型在它唯一保留的即時 AI 功能上失效。**
  - 「AI 只能讓判定變嚴格」這條原則對批改成立，**對「換個說法」完全不成立**——那是純生成，沒有程式可以把關。
  - grounding check（抽出數值與專有名詞逐一比對）對「用另一種方式解釋二次函數的開口方向」這種輸出幾乎無效，因為它沒有可驗證的數值斷言。
  - **怎麼修**：v1 的「換個說法」**限制為從預先寫好的 2–3 個替代解釋中選一個**（作者寫的，不是生成的）。這同時解決成本、正確性、與延遲。真正的自由生成留到有錯誤召回機制、有回報處理人力之後。
- **`answer_cards` 關聯表（記錄誰看過哪張知識卡）確實事後補不回來，這條要保留。** 但在 v1 它的形式應該極簡：`ai_answers(id, user_id, item_id, prompt_version, created_at)` 四個欄位，不需要 RAG index version 與 retrieval card ids（因為沒有 RAG）。

## 7. 分期是否真的可交付

- **Phase 0 宣稱 2 週，實際 5–8 週。** 內容包含：新 repo + workspace + Turborepo + TS strict + Vitest + `.unit.md`/`.item.md` schema + **六層 lint** + DTCG token 機械化萃取 + contrast.lock 進 CI + 文案 linter + 靜音窗 + **6 天技術釘子**。光是六層 lint 就是 2 週，DTCG 產線 1 週，釘子 6 天。**這期沒有任何使用者可見產出**，而藍圖要求「要事先接受」——一個人在專案第一個月完全沒有可見產出，是最容易放棄的時間點。
- **Phase 1 宣稱 6 週，實際 14–20 週。** 光是列表：三視圖投影、SVG 預渲染管線、Elo+σ、閉迴路修正、交錯修復、四級挫敗階梯、BKT、EWMA、FSRS-6、六分類 log-odds、**CAS 答案等價判定（型別化 AST + 精確有理數 + 隨機代入）**、危機三級處置、Web 前端。CAS 那一項單獨就是 2–3 週（你要解析學生輸入的自由文字算式）。
- **三個隱藏相依，每一個都會讓 Phase 1 卡住：**
  1. **Phase 1 exit 要求 golden replay 亂序測試，但 op-log 排在 Phase 2。** 沒有事件流就沒有亂序可測。
  2. **Phase 1 交付「L1/L2/L3 三視圖投影」，但 Phase 0 的 content-kit 只列了 parse 與 lint，沒有 `project/`。** 那個模組要在 Phase 1 從零寫。
  3. **危機處置模板需要「心理／諮商專業人員審核簽核」——這是外部相依，前置時間不可控**（找人、排時間、來回修改），實務上 4–8 週。排在 6 週的 Phase 1 內完成是幻想。
  - 另外 exit criteria 第 4 條「找到 5 個真實使用者連續用滿 7 天」本身就是開發完成之後的 2–3 週。
- **幾條驗收標準在統計上不成立，會誤導決策：**
  - Phase 2「20–50 個使用者，兩週留存 ≥35%」：n=50 時 35% 的抽樣誤差約 ±13pp。**這個 gate 分不出 25% 與 45%。** 修法：改成質性 gate——「至少 5 個使用者主動說出某個講解讓他懂了以前不懂的東西」。
  - Phase 3「付費轉換 ≥3%，或至少 30 個付費使用者」：3% × 200 使用者 = 6 人，所以真正的約束是 30 人，那需要 ~1,000 使用者。**兩個子句差 5 倍，且 1,000 使用者沒有獲客計畫支撐。** 修法：只留「30 個付費使用者」，並把獲客當成 Phase 3 的第一交付物而非隱含假設。
  - Phase 6「新增會考 < 200 行程式碼變更且沒有 `if (exam === 'cap')`」：這個標準會誘發壞行為（把差異塞進 YAML 的 `special_case: true`，或在 Phase 0 過度抽象）。而且光是六科的 UI 文案、band 切換、15 區比序介面就不只 200 行。修法：改成**「新增會考不需要修改 `packages/core/{srs,ability,session,diagnose}` 這四個目錄」**——範圍明確、可自動檢查、不誘發規避。
- **元評論**：這份藍圖建立在一份自己標記為「19/36，未完成」的研究之上（我查了 repo，`docs/research` 有 20 個 md，commit message 寫「19/36，未完成」），但全文語氣是確定的。研究本身也高估了自己的範圍——**這是同一個系統性偏誤在兩個層級上重複出現。** 把它當成一個訊號：這份藍圖的所有工時估計都要乘上一個係數，我建議 2.5–3。

## 8. 一個人做得完嗎

- **以藍圖的範圍，不行，而且差距不是 30%，是 2.5–3 倍。**
  - Phase 0：5–8 週（宣稱 2）
  - Phase 1：14–20 週（宣稱 6）
  - Phase 2：20–28 週（宣稱 10）
  - Phase 3：內容 8–13 個月 + 工程 8–12 週（宣稱 18 週全包）
  - **Phase 0–3 合計 24–34 個月，藍圖宣稱 9–12 個月。**
  - 這還假設：不換工作、不生病、需求不變、課綱不改、第 45 個 unit 跟第 1 個一樣快。最後一項一定不成立。
- **我查了這個 repo：51 個 commit，50 個是 `github-actions[bot]` 的榜線快照，唯一一個非 bot commit 是那份未完成的研究文件。** 也就是說，「一個人 + AI 的加速倍率 3–5×」這個宣稱，在這個 repo 裡**沒有任何可驗證的基準**。它是從 AI 的樂觀自述來的，不是從實測來的。Phase 1 exit 第 5 條（記錄實際工時）是整份藍圖裡最重要的一行，因為它是第一個真實數據點——**所以 Phase 1 應該盡快到達，而不是塞滿 13 項交付物。**

### 最務實的縮減版：「學測數學 A 歷屆題誤答診斷」，12 週，Web only

- **內容（3–4 週，85–125 小時）**：近 10 年學測數學 A 歷屆題約 200 題（§9 免除，題目零撰稿成本）。每題產出四樣東西：想法起點（一句可遷移的規則）、標準解法、**每個誘答選項的迷思概念一句話**、一題同知識點的變式題。不寫教材，不寫 14 區塊 unit。
- **工程（4 週）**：
  - Vite + React + TanStack Router，單一專案，無 monorepo、無 Turborepo。
  - 內容存 `content/*.md`（front-matter + 五個區塊），一支 200 行的 build script 轉成 JSON 塞進 bundle。無 SQLite pack、無 zstd、無簽章、無 bsdiff。
  - KaTeX 執行期渲染（或 SSR 產 HTML+MathML）。
  - Cloudflare Worker：直接搬 `cors.js`（39 行，一行不改）、`auth.js`（218 行，HMAC session）、`db.js` 的條件式 UPDATE 模式。新增一支 `POST /api/attempts`。
  - D1：`users`、`attempt`（PK 是裝置端 ULID，`INSERT OR IGNORE`）、`review_queue`。**注意 100 參數上限**，用 JSON + `json_each`。
  - 無離線、無 Service Worker、無同步、無 op-log、無 HLC。
- **功能就三件事**：讀題作答 → 錯了顯示你的迷思 → 錯題在 1/3/7/21 天後以變式題回來。
- **心理安全網（1 天）**：一頁靜態求助資源（1925 / 1995 / 1980 / 113 / 110 / 119 / 學校輔導室），內建於 bundle。**沒有偵測器**（因為沒有自由文字輸入面），因此不需要專業審核與 90 天保留政策。
- **lint（2 天）**：只有兩條——front-matter schema、每個誘答必須有 misconception 文字。
- **剩下 4–5 週**：找 20 個真人用、修、補內容、跑 SEO 實驗（把 30 個「二次函數 配方法」這類長尾頁公開索引，看有沒有自然流量）。
- **不收費。** 用「你願意為這個付多少」的問卷 + 一個誠實標示的假付費按鈕測意願。這比真的接金流早三個月拿到訊號，而且不觸發 IAP、未成年契約、退費政策這一整包。

### 這個版本明確砍掉的（全部延到有 200 個真實使用者之後再談）

Elo / BKT / IRT / MST 診斷 / 閉迴路修正 / 交錯約束 / 挫敗四級階梯 / 六分類錯因 / CAS 等價判定 / AI 家教 / AI 出題 / 拍照批改 / 模考模組 / 考招制度模組 / 家長端 / 會考 / 原生 App / 桌面 / 離線 / 內容包與簽章 / DTCG token 產線 / Turborepo / op-log 同步 / 推播與靜音窗 / 危機偵測器 / 三視圖投影 / SVG 預渲染。

### 三個 kill criteria（現在就寫下來，到時候不准解釋）

1. **12 週結束時，若沒有 5 個人連續用滿 7 天並說得出「哪個講解真的講清楚了」** → 問題在內容品質或需求，不是在功能太少。不要加功能。
2. **實測單一單元（或 20 題）的製作工時 × 目標題數 > 2,400 小時** → 一個人做不完，必須在此時決定找共同作者、砍範圍、或接受這是 side project。
3. **公開的長尾頁在 8 週內帶不進任何自然流量** → 唯一免費的獲客管道不成立，21,000 活躍使用者的路徑不存在，商業模式必須改成 B2B 或放棄商業化。

## 最後一句

這份藍圖的判斷力遠高於它的執行計畫——`support.js` 的丟棄理由、§9 與其例外的分析、分科 60 級分的更正、「θ 表達學會、R 表達提取得出來」的區分、「粗心的正確處方是不處理」，這些都是對的，而且是很難得的對。問題是它**為一個 30 人的內容組織做了治理設計**（CI 擋 person 歸因、contrast.lock、rights-audit 不可 override、雙人盲審、Cohen's kappa、200 份作答的影子期、家長端架構測試），然後把這套治理交給一個人在還沒有第一個使用者的時候實作。把治理砍掉九成，把演算法砍掉九成，把題量的算術修正，把獲客補上——剩下的那個 12 週版本，才是這份藍圖裡真正值得做的東西。
