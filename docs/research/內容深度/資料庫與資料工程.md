
## area
超大型多考試多科目學習 App 的資料庫與資料工程（內容／題庫／使用者／營運四平面、版本化與事件溯源、中文檢索、離線包管線、資料品質與規模推算）

## summary
核心主張六條：

一、**四平面物理分離**。內容平面（權威在 git，DB 是唯讀投影）、題庫平面（同上，但統計欄位 DB-native）、學習者平面（append-only 事件 + 可重算衍生狀態）、營運平面（工作流狀態）。混在一個庫裡的後果不是效能問題而是治理問題：內容要 code review，事件要高吞吐寫入，兩者的變更節奏差三個數量級。

二、**內容用 git-first、DB-projected、R2-distributed**。講解與詳解是「有作者、要 diff、要 blame、要回退」的作品，這是版本控制系統的定義域；查詢、關聯、統計是資料庫的定義域。單向編譯，DB 永不回寫 git；標註台與勘誤在 DB 產草稿，但發布必須走「產 PR → CI 驗證 → merge → 重編譯」。允許 DB 直接改內容的那一天，blame 失效、離線包與線上開始漂移。

三、**版本化用「身分表 + 不可變 revision + release 凍結集」三層**。學習事件綁 `item_revision_id`（事實：他當時看到的是哪一版）；掌握度綁穩定的 `concept_id`（狀態：改版不該歸零）。這個區分是整套設計的樞紐。課綱改版不重建圖——`standards` 是獨立層，`edition` 是使用者屬性驅動的查詢過濾條件，絕不 fork 出兩張圖。

四、**掌握度、SRS 排程、錯題本、統計全部是 fold(events) 的衍生狀態，可整份重算**。理由不是優雅：FSRS 參數會重估、IRT 會重估、圖譜會 SPLIT、答案會被發現寫錯——每一件都要求回頭重算歷史。若掌握度是唯一真相，這些事一發生就永遠回不去。離線多裝置合併也因此沒有衝突可解：集合聯集 + 三層去重。

五、**中文檢索用「同一份切詞器跑兩端」**。裝置端 SQLite FTS5 的 unicode61 不斷中文詞，ICU tokenizer 需要自訂 build（D1 與 iOS 系統 SQLite 都沒有），trigram 對 < 3 字查詢失效——正解是**應用層 bigram + 術語詞典 unigram 混合切分**，寫進 contentless FTS5；伺服器端 Neon 沒有 pg_bigm/pgroonga/zhparser，就用同一份切分器產出空白分隔字串再 `to_tsvector('simple', ...)`。一份 Rust 切詞核心，兩端排序一致。語意檢索只對概念層與講解區塊做（55k 段），不對 30 萬題全量做；裝置端不放向量，改帶預先物化的 top-8 語意鄰居表。

六、**D1 在新架構裡沒有非它不可的位置**。答題事件 2.4 GB／日，4.6 天撞穿 10 GB 上限；100 個 bound parameters 的限制直接絆倒離線批次上傳；2 MB 單列上限讓離線包不可能進 D1；寫入尖峰 600–800/s 超出 D1 上限 3–4 倍。保留 D1 只是為了不重寫既有的 auth/admin 程式碼，新功能一律不進 D1，主資料層走 Neon Postgres，離線包走 R2。

# 一、通用約定（所有表適用）

```sql
-- ID：UUIDv7。時間有序 → B-tree 插入不隨機、天然可當分頁游標、
-- 且客戶端能離線自產不撞號（這是離線優先的前提，序號主鍵做不到）。
-- 對外可讀識別一律用 slug/code，內部關聯一律用 uuid。永不重用，永不改值。
CREATE DOMAIN uuid7 AS uuid;

-- 時間：全部 timestamptz。裝置端用 INTEGER 毫秒 epoch。
-- 既有 db.js 用「秒」，事件側必須改毫秒 —— 同一秒內連續作答的排序會壞掉。
-- 事件的全序 key 是 (hlc_ts, device_id, event_id)，不是牆上時鐘。

-- 稽核欄位組（巨集，內容側與營運側每張表都有）
--   created_at timestamptz NOT NULL DEFAULT now()
--   created_by uuid7
--   updated_at timestamptz NOT NULL DEFAULT now()
--   updated_by uuid7
--   deleted_at timestamptz            -- 軟刪除
--   deleted_by uuid7
--   delete_reason text
-- 讀取一律走 v_xxx（WHERE deleted_at IS NULL）。直接 SELECT 基表要在 review 被擋。

-- 溯源四問 → 四組欄位（見 §2.4 content_revisions）
--   誰寫的     authored_by / author_kind / model_id / prompt_hash / extractor_version
--   根據什麼   citations 表（多筆）+ derived_from_revision_id
--   什麼時候   authored_at / published_at / revision 的 content_hash
--   審過沒     review_level / reviewed_by[] / reviewed_at / review_status
```

## 2.1 考試與科目骨幹

```sql
-- 考試。會考、學測、分科、統測、TOCFL…；一個考試有多個施測年度
CREATE TABLE exams (
  id            uuid7 PRIMARY KEY,
  code          text NOT NULL UNIQUE,        -- 'cap' | 'gsat' | 'ast' | 'tcte'
  name          text NOT NULL,               -- 國中教育會考
  authority     text NOT NULL,               -- 心測中心 | 大考中心
  stage         text NOT NULL,               -- junior | senior
  -- 著作權法 §9 I(5)：依法令舉行之考試試題不得為著作權標的。
  -- 這個布林決定該考試的歷屆題能不能整題落地打包（見 §3.6）。
  items_public_domain boolean NOT NULL DEFAULT false,
  status        text NOT NULL DEFAULT 'active',   -- active | sunset
  created_at timestamptz NOT NULL DEFAULT now(), deleted_at timestamptz
);

CREATE TABLE exam_administrations (           -- 一次施測（114 學測）
  id uuid7 PRIMARY KEY,
  exam_id uuid7 NOT NULL REFERENCES exams(id),
  roc_year smallint NOT NULL,                 -- 114
  session  text,                              -- 第一次 | 第二次
  held_on  date,
  UNIQUE (exam_id, roc_year, session)
);

CREATE TABLE subjects (
  id      uuid7 PRIMARY KEY,
  code    text NOT NULL UNIQUE,               -- 'math_a' | 'sci_chem' | 'chin'
  name    text NOT NULL,
  -- 學段分開建列而不是加一個欄位：國中數學與高中數學 A 的課綱、題庫、
  -- 掌握度、離線包分片邊界全部不同，硬合成一列會讓每支查詢都得 if-else。
  stage   text NOT NULL,                      -- G7-9 | G10-12 | G10-12-adv
  parent_subject_id uuid7 REFERENCES subjects(id),  -- 自然 → 物理/化學/生物/地科
  order_index smallint NOT NULL DEFAULT 0,
  color_token text, icon text
);

-- 考試 × 科目（多對多）：同一個「數學 A」同時屬於學測與分科
CREATE TABLE exam_subjects (
  exam_id uuid7 NOT NULL REFERENCES exams(id),
  subject_id uuid7 NOT NULL REFERENCES subjects(id),
  weight numeric(4,3),                        -- 該科在該考試的分數佔比
  item_count_typical smallint,                -- 典型題數，供模考產卷
  duration_min smallint,
  PRIMARY KEY (exam_id, subject_id)
);
```

```sql
CREATE TABLE curriculum_editions (
  id uuid7 PRIMARY KEY,
  code text NOT NULL UNIQUE,                  -- '108' | '118'
  effective_from_school_year smallint NOT NULL,   -- 入學年度
  status text NOT NULL DEFAULT 'draft'        -- draft | active | deprecated | retired
);

CREATE TABLE standards (                      -- 學習內容／學習表現條目
  id uuid7 PRIMARY KEY,
  edition_id uuid7 NOT NULL REFERENCES curriculum_editions(id),
  code text NOT NULL,                         -- '數-J-A2' | 'Ba-IV-1' | 'CMa-10A-3'

  subject_id uuid7 REFERENCES subjects(id),
  band text,                                  -- 學習階段 IV / V

  UNIQUE (edition_id, code)

CREATE INDEX ON standards (subject_id, edition_id);

-- 新舊課綱條目的對照。108→118 差異報告產出後由專家確認，
-- 是「只換 ALIGNED_TO」還是「概念節點要 SPLIT/MOVE」的判斷依據。
CREATE TABLE standard_crosswalk (
  from_standard_id uuid7 NOT NULL REFERENCES standards(id),
  to_standard_id   uuid7 REFERENCES standards(id),     -- NULL = 該條目被移除
  relation text NOT NULL,   -- same | reworded | narrowed | broadened | moved_stage | removed | added
  confidence numeric(3,2) NOT NULL,
  reviewed_by uuid7, reviewed_at timestamptz,
  PRIMARY KEY (from_standard_id, to_standard_id)
);
```

## 2.3 單元與知識圖譜

```sql
-- 單元＝一份 .unit.md 的身分。穩定不可變的那一半。
CREATE TABLE units (
  id uuid7 PRIMARY KEY,
  slug text NOT NULL UNIQUE,                  -- 'MATH-H-ALG-QUAD-01'，發布後永不變
  subject_id uuid7 NOT NULL REFERENCES subjects(id),
  strand text,                                -- 領域／主題
  lifecycle text NOT NULL DEFAULT 'draft',    -- draft|review|active|deprecated|retired
  superseded_by uuid7 REFERENCES units(id),   -- retired 後查舊 slug 回 301 到這裡
  source_path text NOT NULL,                  -- git 路徑，DB↔git 的錨點
  created_at timestamptz NOT NULL DEFAULT now(), deleted_at timestamptz
);

-- 知識節點。型別與屬性見既有《知識圖譜設計》28 型；此處只落資料庫形。
CREATE TABLE concept_families (               -- 跨學段容器（國中/高中二次函數同一 family）
  id uuid7 PRIMARY KEY, slug text NOT NULL UNIQUE, label text NOT NULL
);

CREATE TABLE kg_nodes (
  id uuid7 PRIMARY KEY,
  slug text NOT NULL UNIQUE,
  node_type text NOT NULL,                    -- Concept|Skill|Formula|Misconception|Lexeme|...
  family_id uuid7 REFERENCES concept_families(id),
  depth_index smallint,                       -- 同 family 內深度序號
  subject_ids uuid7[] NOT NULL DEFAULT '{}',  -- 跨科節點可多值
  stage text NOT NULL,
  label text NOT NULL,
  aliases text[] NOT NULL DEFAULT '{}',       -- 學生口語「湊平方」也要進，搜尋命中率靠它
  -- 型別專屬屬性放 JSONB 而不是每型一張表：28 種型別各自 3–8 個欄位，
  -- 開 28 張表 join 成本高且新增型別要動 schema；
  -- 但白名單與必填由 JSON Schema 在 CI 強制（見 §10），不是「隨便塞」。
  attrs jsonb NOT NULL DEFAULT '{}',
  difficulty numeric(3,2),                    -- IRT b 值中位數，DB-native 每日回填
  exam_weight jsonb NOT NULL DEFAULT '{}',    -- {"gsat":0.6,"cap":0.8}
  est_minutes smallint,
  mastery_model text NOT NULL DEFAULT 'partial',   -- binary | partial
  item_count int NOT NULL DEFAULT 0,          -- DB-native，覆蓋率監控用
  lifecycle text NOT NULL DEFAULT 'draft',
  kg_version_in text, kg_version_out text,    -- semver 生效／失效
  confidence numeric(3,2) NOT NULL DEFAULT 1.0,
  created_at timestamptz NOT NULL DEFAULT now(), deleted_at timestamptz
);
CREATE INDEX ON kg_nodes (node_type, lifecycle);
CREATE INDEX ON kg_nodes USING gin (subject_ids);
CREATE INDEX ON kg_nodes USING gin (aliases);
-- Lexeme 有 8,000 列且不進主圖佈局與 PageRank，用 partial index 讓主圖查詢不掃到它
CREATE INDEX ON kg_nodes (family_id) WHERE node_type <> 'Lexeme';

CREATE TABLE kg_edges (
  id uuid7 PRIMARY KEY,
  edge_type text NOT NULL,                    -- PREREQUISITE_OF | IS_PART_OF | ...
  from_id uuid7 NOT NULL REFERENCES kg_nodes(id),
  to_id   uuid7 NOT NULL REFERENCES kg_nodes(id),
  -- tier 是硬約束不是註記：只有 hard 邊能進掌握度計算。
  -- CHECK 讓「LLM 產的未審邊被當成硬邊」在資料庫層就寫不進去。
  tier text NOT NULL,                         -- hard | soft
  review_status text NOT NULL DEFAULT 'auto', -- auto|reviewed|double_reviewed|expert_locked|disputed
  weight numeric(4,3), confidence numeric(3,2) NOT NULL,
  scope text[] NOT NULL DEFAULT '{}',
  evidence jsonb NOT NULL DEFAULT '{}',       -- {item_count, co_error_rate, conditional_p}
  attrs jsonb NOT NULL DEFAULT '{}',          -- map_kind / contrast_axes / relation…
  note text,
  created_at timestamptz NOT NULL DEFAULT now(), deleted_at timestamptz,
  CONSTRAINT hard_edge_must_be_reviewed
    CHECK (tier <> 'hard' OR review_status <> 'auto'),
  CONSTRAINT no_self_loop CHECK (from_id <> to_id),
  UNIQUE (edge_type, from_id, to_id)
);
CREATE INDEX ON kg_edges (from_id, edge_type) WHERE deleted_at IS NULL;
CREATE INDEX ON kg_edges (to_id, edge_type)   WHERE deleted_at IS NULL;

-- 概念 ↔ 課綱：多對多，且掛在 edition 上。課綱改版換的是這張表，不是 kg_nodes。
CREATE TABLE concept_standards (
  node_id uuid7 NOT NULL REFERENCES kg_nodes(id),
  standard_id uuid7 NOT NULL REFERENCES standards(id),
  coverage numeric(3,2) NOT NULL DEFAULT 1.0,
  PRIMARY KEY (node_id, standard_id)
);
CREATE INDEX ON concept_standards (standard_id);
```

## 2.4 講解區塊與版本化核心（本節是整份設計的樞紐）

```sql
-- 講解區塊的身分。一個單元 14 個固定區塊 S01–S14。
CREATE TABLE blocks (
  id uuid7 PRIMARY KEY,
  unit_id uuid7 NOT NULL REFERENCES units(id),
  block_code text NOT NULL,                   -- 'S01'…'S14'
  order_index smallint NOT NULL,
  depth_level smallint NOT NULL,              -- 1|2|3 三種閱讀深度的最低出現層
  UNIQUE (unit_id, block_code)
);

-- === 不可變版本表 ===
-- 一張表管所有內容型實體的版本，而不是每種實體一張 xxx_versions：
-- 溯源、審核、release 凍結、勘誤的邏輯完全相同，分開寫必然漂移。
CREATE TABLE content_revisions (
  id uuid7 PRIMARY KEY,
  entity_type text NOT NULL,                  -- unit | block | kg_node | kg_edge | item | item_solution
  entity_id   uuid7 NOT NULL,
  rev_no      int  NOT NULL,                  -- 該實體內遞增
  -- content_hash = sha256(正規化後的內容)。這是 DB 與 git 的錨：
  -- 同一個 hash 必然對得到 git 裡的一個 blob，對不到就是有人手改了 DB。
  content_hash bytea NOT NULL,
  git_commit  text,                           -- 40 hex
  body        jsonb NOT NULL,                 -- 該版的完整內容（含 markdown/latex/欄位）
  -- 變更分級決定學習紀錄怎麼處理，見 §6.2。這是必填，CI 會擋空值。
  change_class text NOT NULL,                 -- cosmetic|clarify|material|answer_changed
  change_note  text NOT NULL,
  derived_from_revision_id uuid7 REFERENCES content_revisions(id),
  -- 溯源：誰寫的
  author_kind text NOT NULL,                  -- human | llm | import | curriculum_parse
  authored_by uuid7,                          -- 人：作者 id
  model_id    text,                           -- LLM：claude-opus-5 等
  prompt_hash bytea,                          -- LLM：prompt 模板的雜湊，可回溯生成條件
  extractor_version text,
  authored_at timestamptz NOT NULL DEFAULT now(),
  -- 溯源：審過沒
  review_status text NOT NULL DEFAULT 'draft', -- draft|in_review|approved|rejected|quarantined
  review_level  smallint NOT NULL DEFAULT 0,   -- 0 未審 1 單審 2 雙審 3 專家鎖定
  reviewers jsonb NOT NULL DEFAULT '[]',       -- [{user_id, role, verdict, at, comment}]
  approved_at timestamptz,
  UNIQUE (entity_type, entity_id, rev_no),
  UNIQUE (entity_type, entity_id, content_hash)
);
CREATE INDEX ON content_revisions (entity_type, entity_id, rev_no DESC);
CREATE INDEX ON content_revisions (review_status) WHERE review_status <> 'approved';

-- === Release：一組 revision 的凍結集合 ===
-- 「學生看到的是哪一版」不能靠 max(rev_no) 現算 —— 那會讓兩個學生在
-- 發版當下看到不同內容，而事後無法重現任何一邊。release 是唯一可重現的座標。
CREATE TABLE content_releases (
  id uuid7 PRIMARY KEY,
  version text NOT NULL UNIQUE,               -- '2026.09.1'
  channel text NOT NULL,                      -- stable | beta | internal
  kg_version text NOT NULL,                   -- semver
  edition_id uuid7 NOT NULL REFERENCES curriculum_editions(id),
  built_from_commit text NOT NULL,
  status text NOT NULL DEFAULT 'building',    -- building|verified|published|rolled_back
  published_at timestamptz, rolled_back_at timestamptz,
  qc_report jsonb                             -- §10 的檢查結果全文
);

CREATE TABLE release_members (
  release_id  uuid7 NOT NULL REFERENCES content_releases(id),
  entity_type text NOT NULL,
  entity_id   uuid7 NOT NULL,
  revision_id uuid7 NOT NULL REFERENCES content_revisions(id),
  PRIMARY KEY (release_id, entity_type, entity_id)
);
CREATE INDEX ON release_members (revision_id);
```

## 2.5 來源引用、媒體、授權

```sql
CREATE TABLE licenses (
  code text PRIMARY KEY,                      -- 'OGDL-1.0'|'CC-BY-4.0'|'CC-BY-NC-SA-3.0-TW'|'PD'|'PROPRIETARY'
  name text NOT NULL,
  -- 這三個布林是全站可用性的閘門，不是註記。
  -- NC 授權對付費/含廣告 App 一律 allows_commercial=false → 自動降為 link_only。
  allows_commercial boolean NOT NULL,
  allows_derivative boolean NOT NULL,
  share_alike boolean NOT NULL,
  attribution_required boolean NOT NULL DEFAULT true,
  url text
);

CREATE TABLE sources (                        -- 一個外部來源（一本書、一篇論文、一個資料集、一份官方公告）
  id uuid7 PRIMARY KEY,
  source_kind text NOT NULL,                  -- textbook|exam_paper|gov_open_data|journal|encyclopedia|web|self
  title text NOT NULL, publisher text, authors text[],
  url text, isbn text, doi text,
  published_on date, retrieved_at timestamptz,
  license_code text NOT NULL REFERENCES licenses(code),
  -- usage_mode 由 license 推導但可再收緊，不可放寬（CI 檢查）
  usage_mode text NOT NULL,                   -- bundle | embed | link_only | forbidden
  credibility_tier smallint NOT NULL,         -- 1 官方 2 學術 3 主流媒體 4 其他
  freshness_class text NOT NULL DEFAULT 'evergreen',  -- evergreen|annual|volatile
  expires_on date,                            -- volatile 類強制填，到期自動降權
  snapshot_r2_key text,                       -- 取用當下的存證快照（連結會死）
  created_at timestamptz NOT NULL DEFAULT now()
);

-- 引用：回答「這一段講解根據什麼」。一段內容可有多筆。
CREATE TABLE citations (
  id uuid7 PRIMARY KEY,
  revision_id uuid7 NOT NULL REFERENCES content_revisions(id),
  source_id   uuid7 NOT NULL REFERENCES sources(id),
  locator text,                               -- 頁碼／章節／時間碼
  quoted_text text,                           -- 實際引用的原文（長度上限 CI 檢查）
  claim_anchor text NOT NULL,                 -- 這筆引用支持的是哪一句（區塊內錨點）
  -- 三選一，缺一不得上架：有推導 | 有出處 | 明確標為約定
  support_kind text NOT NULL                  -- derivation | citation | convention
);
CREATE INDEX ON citations (revision_id);
CREATE INDEX ON citations (source_id);

CREATE TABLE media_assets (
  id uuid7 PRIMARY KEY,
  asset_kind text NOT NULL,                   -- image|svg|audio|video|interactive|geojson
  -- 內容定址：同一張圖不論被幾個單元用都只有一份，且 hash 就是 R2 key。
  sha256 bytea NOT NULL UNIQUE,
  r2_key text NOT NULL,
  mime text NOT NULL, bytes int NOT NULL,
  width int, height int, duration_ms int,
  alt_text text NOT NULL,                     -- 無障礙必填，CI 擋空
```

## 4.2 學習事件（append-only，整套系統的真相）

```sql
-- 這張表只有 INSERT。沒有 UPDATE、沒有 DELETE（除了 retention 的整分割 DROP）。
-- 權限上直接 REVOKE UPDATE,DELETE，讓「不小心改了歷史」不可能發生。
CREATE TABLE learning_events (
  event_id uuid7 NOT NULL,                    -- 客戶端產生，離線可用
  user_id  uuid7 NOT NULL,
  device_id uuid7 NOT NULL,
  -- 全序 key：牆上時鐘在多裝置下不可信，HLC 保證因果順序且可比較
  hlc_ts   bigint NOT NULL,                   -- 混合邏輯時鐘
  occurred_at timestamptz NOT NULL,           -- 裝置端的當地時間（分割鍵）
  received_at timestamptz NOT NULL DEFAULT now(),
  event_type text NOT NULL,                   -- attempt|reveal|hint|read_block|start_session|
                                              -- end_session|rate_difficulty|bookmark|note_update|
                                              -- mock_start|mock_submit|plan_check
  -- 事實綁 revision：要能回答「他當時看到的是哪一版題目／哪一版詳解」。
  -- 內容改版後這筆事件的解讀方式可能改變，沒有 revision 就永遠說不清。
  item_id uuid7, item_revision_id uuid7,
  block_id uuid7, block_revision_id uuid7,
  release_id uuid7,                           -- 當時裝置上的內容 release
  node_id uuid7,                              -- 對應的主考點（編譯時快照，免得日後標註改了讀不回來）
  session_id uuid7,
  payload jsonb NOT NULL DEFAULT '{}',        -- {choice:"B",correct:false,ms:41200,confidence:2,…}
  -- 冪等鍵：見 §6.4 三層去重的第二層
  idem_key text NOT NULL,
  schema_version smallint NOT NULL DEFAULT 1,
  PRIMARY KEY (event_id, occurred_at)
) PARTITION BY RANGE (occurred_at);
-- 每月一個分割。90 天以上的分割每季導出 Parquet 到 R2 後 DETACH + DROP。
-- 不 DELETE：876 GB/年的表上做 DELETE 會產生等量的 WAL 與 bloat。

CREATE UNIQUE INDEX ON learning_events (user_id, idem_key, occurred_at);
CREATE INDEX ON learning_events (user_id, occurred_at DESC);
CREATE INDEX ON learning_events (item_id, occurred_at) WHERE event_type = 'attempt';
-- 歷史作答失效標記不能寫進這張表（它 append-only），改用旁掛表
CREATE TABLE event_invalidations (
  event_id uuid7 NOT NULL, occurred_at timestamptz NOT NULL,
  reason text NOT NULL,                       -- answer_changed|item_retracted|abuse|test_data
  changeset_id uuid7, created_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (event_id, occurred_at)
);

-- 同步游標：per-user 單調遞增序號，客戶端只要記一個數字就能續傳
CREATE TABLE sync_cursors (
  user_id uuid7 NOT NULL, device_id uuid7 NOT NULL,
  server_seq bigint NOT NULL DEFAULT 0,
  last_push_at timestamptz, last_pull_at timestamptz,
  PRIMARY KEY (user_id, device_id)
);
CREATE SEQUENCE server_seq_global;
CREATE TABLE sync_outbox (                    -- 伺服器 → 裝置的事件流（含其他裝置寫入的）
  user_id uuid7 NOT NULL, server_seq bigint NOT NULL DEFAULT nextval('server_seq_global'),
  event_id uuid7 NOT NULL, occurred_at timestamptz NOT NULL,
  PRIMARY KEY (user_id, server_seq)
);
```

```sql
  fixed_in_revision_id uuid7, fixed_in_release_id uuid7,
  -- 修正後要不要讓歷史作答失效，由這個欄位決定（見 §6.2）
  invalidates_history boolean NOT NULL DEFAULT false,

);
CREATE INDEX ON errata (status, severity, created_at);

CREATE TABLE experiments (
  id uuid7 PRIMARY KEY, key text NOT NULL UNIQUE,
  hypothesis text NOT NULL, primary_metric text NOT NULL,
  variants jsonb NOT NULL,                    -- [{name:"control",weight:0.5},…]
  -- 分流用 hash(user_id || salt)，不存指派表：3 億次曝光不需要 3 億列。
  salt text NOT NULL,
  unit text NOT NULL DEFAULT 'user',          -- user|device|session
  status text NOT NULL DEFAULT 'draft',
  started_at timestamptz, stopped_at timestamptz, decision jsonb
);
CREATE TABLE experiment_exposures (           -- 只記首次曝光，不記每次
  experiment_id uuid7 NOT NULL, user_id uuid7 NOT NULL,

CREATE TABLE audit_log (                      -- 誰在什麼時候改了什麼
  id bigserial PRIMARY KEY,

  -- 法定期限 30 天。這個欄位讓「逾期未處理」可以被監控告警。
```

# 六、不可妥協的資料原則（六條）

## 6.1 來源追溯

「這是誰寫的、根據什麼、什麼時候、審過沒有」四問，各有明確欄位：

| 問題 | 欄位 |
|---|---|
| 誰寫的 | `content_revisions.author_kind` + `authored_by` / `model_id` + `prompt_hash` + `extractor_version` |
| 根據什麼 | `citations`（多筆，每筆有 `claim_anchor` 指向被支持的那一句、`support_kind ∈ {derivation, citation, convention}`）+ `derived_from_revision_id` |
| 什麼時候 | `authored_at`、`content_hash`、`git_commit`、`release_members` 決定的實際生效區間 |
| 審過沒 | `review_status` + `review_level`(0/1/2/3) + `reviewers[]` + `approved_at` |

硬規則：**凡是結論就必須有推導、有出處，或明確標示為「約定」，三者缺一即不得上架**。CI 檢查每個 `claim_anchor` 都被 `citations` 覆蓋。`kg_edges` 的 `CHECK (tier <> 'hard' OR review_status <> 'auto')` 讓「LLM 產的未審邊被拿去算掌握度」在資料庫層就寫不進去。

## 6.2 版本化：學習紀錄綁哪一版？

**答案是分開綁**：

- **事實綁 revision**：`learning_events.item_revision_id` NOT NULL。要能回答「他當時看到的是哪一版」。
- **狀態綁穩定 id**：`mastery_state.node_id`、`srs_state.item_id`。改版不該讓進度歸零。

`change_class` 決定改版時對歷史做什麼：

| change_class | 對歷史作答 | 對 SRS | 對筆記 |
|---|---|---|---|
| `cosmetic`（錯字、排版） | 不動 | 不動 | 不動 |
| `clarify`（敘述更清楚，答案不變） | 不動 | 不動 | UI 標「原文已更新」 |
| `material`（數據／情境改動） | 保留但標 `stale`，統計分開算 | 保留，`due_at` 提前 | 標「原文已更新」 |
| `answer_changed`（答案錯了） | 全數寫入 `event_invalidations`，**排除出 fold** | `state='relearning'`，重新排程 | 保留 |

**課綱改版怎麼辦**：`standards` 是獨立層，改版換的是 `standards` 列與 `concept_standards` 邊，`kg_nodes` 85% 不動。`users.curriculum_edition_id` 是查詢過濾條件，新生走 118、在校生繼續 108，**同一組概念節點兩組課綱邊**。絕不 fork 兩張圖——那會讓標註工作與作答資料一分為二，不可逆。

## 6.3 事件溯源：為什麼掌握度必須是衍生狀態

具體會發生、且一定會發生的四件事：

1. **FSRS 參數重估**。用全站資料重新擬合後，每個人的 `stability` 都該重算。若排程是唯一真相，只能「從今天起用新參數」，歷史永遠帶著舊參數的偏差。
2. **IRT 重估**。難度變了，同一次作答對掌握度的貢獻就變了。
3. **圖譜 SPLIT**。一個節點拆兩個，該生在舊節點的掌握度要依「他實際做過哪些題」重新分派——只有回到原始事件才做得到。
4. **答案發現寫錯**。三個月的作答要作廢重算。若掌握度是唯一真相，這些人被錯誤地判定為「這個概念不會」，而且救不回來。

外加兩個結構性理由：**離線多裝置合併沒有衝突可解**（兩台裝置各自答同一題，領域語意上兩筆都算數，是集合聯集不是列衝突）；**申訴與稽核需要原始事實**（「為什麼系統說我這裡不會」必須答得出來）。

落地：所有衍生表帶 `fold_version`，重算是 bump 版本後重跑，不是就地修補。事件表 `REVOKE UPDATE, DELETE`。

## 6.4 冪等與去重（三層，缺一不可）

| 層 | 機制 | 擋掉什麼 |
|---|---|---|
| L1 | `event_id`（UUIDv7，客戶端產）為 PK，`ON CONFLICT DO NOTHING` | 網路重試、批次重送 |
| L2 | `UNIQUE (user_id, idem_key)`，`idem_key = base64(sha256(user_id‖item_id‖attempt_no‖client_started_at_ms))` | App 重裝／換裝置後重產 uuid 但語意相同的重送 |
| L3 | 寫入前的時間窗折疊：同 user+item 在 2 秒內的多筆 attempt 折成一筆 | UI 連點、雙指誤觸 |

回傳給客戶端的是「實際寫入筆數」與「已存在筆數」，客戶端據此推進游標——不能靠 HTTP 200 就當成功，重試路徑會漏。

## 6.5 軟刪除與稽核

- 內容與營運側一律 `deleted_at`；讀取走 `v_xxx` 視圖；直接 SELECT 基表在 code review 被擋。
- 使用者原創資料（notes）軟刪 30 天後硬刪。
- 事件表**不軟刪**（append-only），失效走旁掛的 `event_invalidations`。
- `audit_log` 記 before/after JSONB。寫入路徑用 trigger 而非應用層自律——應用層總有一條路徑會忘記。

## 6.6 個資最小化與可攜

- **最小化**：事件表只有 `user_id`（假名），沒有任何 PII。PII 集中在 `users` / `identities` 兩張表。IP 只存 HMAC。遙測不帶精確位置與裝置指紋。
- **可攜（匯出）**：`data_subject_requests(kind='export')` → 產出 JSON + CSV zip 放 R2，簽名 URL 7 天到期。內容包含：帳號欄位、全部原始事件、筆記原文、計畫、模考結果，以及**衍生狀態的計算說明**（不只給數字，給「這個數字怎麼來的」）。
- **刪除（crypto-shredding）**：丟棄 `users.dek_id` 對應的 DEK → 所有 PII 密文瞬間不可解。事件表保留假名化列供統計（合法利益），但 30 天後 `user_id` 也重寫為 tombstone id。**理由**：在 876 GB 的分割表上做 `DELETE WHERE user_id=?` 會掃遍所有分割並產生等量 WAL，一天幾百筆刪除請求就會拖垮寫入。crypto-shredding 讓刪除變成 O(1)。
- 未成年（`age_bracket='child'`）預設關閉個人化與行為分析，`consent` 需家長流程。

# 七、內容存 DB 還是 git：明確建議

**建議：git-first、DB-projected、R2-distributed。單向編譯，DB 永不回寫 git。**

四分法：

| 類別 | 例子 | 權威來源 | 理由 |
|---|---|---|---|
| **作品型** | 講解區塊、詳解、例題、圖說、改寫後的閱讀文本 | **git**（`.unit.md` / `.item.yaml`） | 有作者、要 diff、要 blame、要 PR review、要能回退到任一版。這正是 VCS 的定義域，用 DB 重造一次只會做得更差。 |
| **關係型** | KG 邊、題目↔概念標註、難度先驗 | **git**（`.edges.jsonl`，由標註台自動產生並 commit） | 需要 code review 級別的把關，且量小（8 萬列）到 git 完全承受得住。 |
| **事實型** | IRT 參數、item_stats、item_count、掌握度分佈 | **DB** | 每日重算、沒有作者、進 git 會讓每次 diff 都是幾萬行雜訊，把真正的內容變更淹掉。 |
| **工作流型** | 審核意見、勘誤工單、A/B 指派、實驗結果 | **DB** | 是流程狀態不是作品，需要並發寫入與交易。 |

**混合怎麼做**：

```
標註台/勘誤修正 → DB 草稿 → 「產生 PR」按鈕 → git PR
                                              ↓
                                        CI（§10 六層檢查）
                                              ↓
                                          merge to main
                                              ↓
              編譯器：解析 → 正規化 → 算 content_hash → 寫 content_revisions
                                              ↓
                          建立 content_release + release_members（凍結）
                                              ↓
                                產 R2 離線包（§8）+ 熱快取失效
```

**唯一不可退讓的一條**：DB 裡的內容表對應用層是唯讀的（`GRANT SELECT` only，寫入只給編譯器的角色）。允許 DB 直接改內容的那一天，git 就不再是真相，blame 立刻失效，離線包與線上開始漂移，而漂移只會在使用者回報「我手機上看到的跟網頁不一樣」時才被發現。

**例外處理**：緊急下架不需要走 git（`items.lifecycle='quarantined'` 是 DB 欄位，不是內容），這讓「發現答案錯了要立刻停止出這題」能在 30 秒內完成，而修正內容仍走正規流程。

# 八、搜尋

## 8.1 中文全文檢索：問題與解法

**SQLite FTS5 的中文問題**：預設 `unicode61` tokenizer 依 Unicode 類別切詞，中日韓漢字之間沒有空白 → 整段中文變成一個巨大 token，搜「二次函數」永遠零命中。

三條路的實測取捨：

| 方案 | 可行性 | 判斷 |
|---|---|---|
| ICU tokenizer | 需 `-DSQLITE_ENABLE_ICU` 自訂編譯。**D1 沒有；iOS 系統 SQLite 沒有**（要自帶 SQLCipher/自編譯，App 體積 +3–6 MB）；Android Room 用系統版也沒有 | ✗ 可移植性歸零 |
| `trigram` tokenizer（3.34+ 內建） | 中文 trigram = 3 個漢字，**查詢短於 3 字直接失效**（「函數」「電位」都是 2 字），索引膨脹約 3× | ✗ 常見查詢長度剛好落在盲區 |
| **應用層 bigram + 詞典 unigram 混合切分** | 純資料處理，不依賴任何自訂 build；2 字查詢天然支援；單字查詢用 prefix match | ✓ **採用** |

具體做法：

```
原文  「二次函數的判別式」
切分  bigram：二次 次函 函數 數的 的判 判別 別式
      + 詞典詞（glossary_terms）：二次函數 判別式
      → 寫入 FTS5 的字串："二次 次函 函數 數的 的判 判別 別式 二次函數 判別式"
查詢  「二次函數」→ 同一切分器 → phrase query: "二次 次函 函數" OR "二次函數"
      詞典命中的 unigram 給更高 bm25 權重（透過分欄）
單字  「函」→ prefix query: 函*   （命中 函數/函式/…，語意上正是使用者要的）
```

- FTS5 用 `content=''`（contentless）：原文留在 `blocks`/`content_revisions`，索引不重複存一份，省約 45% 空間。
- 一份切詞器實作在 **Rust core**，經 UniFFI 給 iOS/Android、wasm 給 Web、原生給 Worker——**伺服器端與裝置端用同一份切分**，這樣同一個查詢在線上與離線的排序結果一致。這件事沒有捷徑：兩份實作必然漂移，而漂移的症狀是「離線搜得到、上線搜不到」，極難除錯。

**伺服器端（Neon Postgres）**：Neon 不支援 `pg_bigm` / `pgroonga` / `zhparser`（自管 Postgres 才有）。`pg_trgm` 對 CJK 效果差（同樣是 3 漢字問題）。所以做法一致：**應用層切分器產出空白分隔字串 → `to_tsvector('simple', …)` → GIN 索引**。`simple` 設定不做詞幹還原、不去停用詞，正是我們要的（切分已經在外面做完）。

```sql
ALTER TABLE content_revisions ADD COLUMN search_tsv tsvector;
-- 由編譯器寫入（不用 generated column：切分邏輯在應用層，不在 SQL）
CREATE INDEX ON content_revisions USING gin (search_tsv);
```

## 8.2 語意檢索：要，但範圍要克制

**要做**，但只對「概念層 + 講解區塊 + 題型代表題」約 55,000 段做，**不對 30 萬題全量做**。理由：題目的檢索需求 95% 是「按考點／年份／難度篩選」，那是結構化查詢；語意檢索對題目的增益集中在「找相似題」，而相似題用 `item_concepts` + `item_tags` 的重疊度已經能給出 80% 的效果，成本卻是 1/50。

```sql
CREATE TABLE embeddings (
  entity_type text NOT NULL, entity_id uuid7 NOT NULL,
  revision_id uuid7 NOT NULL,
  model text NOT NULL,                        -- 換模型要能共存與比較
  vec halfvec(1024) NOT NULL,                 -- halfvec：記憶體與索引減半，召回幾乎無損
  PRIMARY KEY (entity_type, entity_id, model)
);
CREATE INDEX ON embeddings USING hnsw (vec halfvec_cosine_ops)
  WITH (m = 16, ef_construction = 64);
```

成本：55,000 段 × 約 400 token = 2,200 萬 token，用便宜的 embedding 模型單次約 US$0.5–2；每季重建一次。**這個數字小到不必猶豫**。真正的成本在「對 30 萬題全量做」（1.2 億 token）而收益遞減，所以不做。

**裝置端不放向量**。理由：HNSW 索引在手機上跑得動但佔 60–100 MB，且更新困難。改成把 top-8 語意鄰居**預先物化成一張表**帶進離線包：

```sql
CREATE TABLE semantic_neighbors (
  src_type text NOT NULL, src_id uuid7 NOT NULL,
  dst_id uuid7 NOT NULL, rank smallint NOT NULL, score real NOT NULL,
  PRIMARY KEY (src_type, src_id, rank)
);
-- 50,000 × 8 = 40 萬列 × ~26 B ≈ 10 MB，可接受
```

離線的「相關內容」因此是查表而非計算，且與線上結果一致。

## 8.3 混合排序

三路召回 → RRF 融合 → 業務加權：

```
1. 精確路：aliases / glossary_terms / slug 完全匹配        → 直接置頂（rank 0）
2. 詞彙路：FTS5 bm25 / ts_rank_cd                         → rank_fts
3. 語意路：向量 cosine（或離線的 semantic_neighbors）      → rank_vec

RRF:  base = Σ 1/(60 + rank_i)
final = base
      × (1 + 0.3·exam_weight[使用者目標考試])
      × (1 + 0.4·(1 − mastery))          -- 弱點加權：不會的東西排前面
      × stage_match                       -- 使用者學段不符的同名節點降到 0.4
      × (lifecycle = 'active' ? 1 : 0.2)
```

`k=60` 是 RRF 的標準值，作用是讓「兩路都排第 10」勝過「一路第 1、一路沒中」——這對中文搜尋特別重要，因為詞彙路對口語查詢（「湊平方」）會完全落空，全靠語意路救。

# 九、離線包管線

## 9.1 分片策略

分片鍵 = `(exam, subject, stage)`。**理由：這條線同時是使用者的選科邊界、購買邊界與刪除邊界。** 刪一科 = 刪一個檔，不需要 `DELETE` + `VACUUM`（在手機上對 40 MB 的表做 VACUUM 要數秒且需要等量暫存空間）。

| pack | 內容 | 估計大小 |
|---|---|---|
| `core` | 考試、科目、單元目錄、KG 節點與硬邊、術語詞典、semantic_neighbors | 8–12 MB |
| `unit.{subject}` | 講解區塊全文 + FTS 索引 | 25–40 MB/科 |
| `items.{exam}.{subject}` | 題目 + 選項 + 答案 + 詳解 + FTS | 30–60 MB/科 |
| `media.{subject}` | 媒體 **manifest**（不含二進位） | 0.5–2 MB |

媒體二進位不進 pack：按需從 R2 拉，本機 LRU 快取（上限使用者可設，預設 500 MB）。理由：媒體佔總體積 80% 但只有 15% 會被看到。

## 9.2 產出管線

```
content_release(status='verified')
  → 每個 pack 分別：SELECT 該分片的 release_members → 寫入乾淨的 SQLite 檔
  → 建 FTS5 索引（用同一份切詞器）
  → 寫 __meta / __checksums 表
  → PRAGMA journal_mode=DELETE; PRAGMA page_size=4096; VACUUM
  → sha256 → 檔名即 hash（內容定址，CDN 可永久快取）
  → Ed25519 簽章 → 上傳 R2 → 更新 pack_manifest
```

## 9.3 增量更新

**基準包 + delta 包**，不做原地 patch：

- delta 是**同 schema 的 SQLite 檔**，只含變更列，外加一張 `__deleted(table_name, pk)`。
- 裝置端不改基準包（基準包保持 content-addressed 可驗證），改把 delta apply 到一個 `overlay` DB，查詢走 view：

```sql
-- 裝置端：ATTACH 'items.base.sqlite' AS base; ATTACH 'items.overlay.sqlite' AS ov;
CREATE TEMP VIEW items AS
  SELECT * FROM ov.items
  UNION ALL
  SELECT * FROM base.items b
   WHERE NOT EXISTS (SELECT 1 FROM ov.items o WHERE o.id = b.id)
     AND NOT EXISTS (SELECT 1 FROM ov.__deleted d WHERE d.table_name='items' AND d.pk = b.id);
```

- **當 overlay 累積列數超過基準的 30%，伺服器改發完整基準包**。理由：view 的 `NOT EXISTS` 成本隨 overlay 成長，且 delta 鏈越長越難驗證。
- delta 鏈最長 8 個版本；超過就要求全量重下。伺服器保留最近 12 個版本的 delta。

## 9.4 完整性驗證（三層，缺一不可）

| 層 | 檢查 | 失敗處置 |
|---|---|---|
| 傳輸層 | 檔案 sha256 == 檔名 == manifest 值；manifest 的 Ed25519 簽章驗證 | 丟棄重下 |
| 結構層 | `PRAGMA integrity_check`、`PRAGMA foreign_key_check`、schema_version 相容 | 丟棄重下 |
| 語意層 | `__checksums` 表逐表比對 `count(*)` 與 `xor_hash`；`__assertions` 檢查（每個 active concept ≥ 5 題、每題恰一 primary、無孤兒 media 引用） | 標為 unusable，回退上一版 |

硬規則：**未通過三層驗證的 pack 不得被查詢層 ATTACH**。這條要寫成單元測試，因為「先讓使用者用著、背景再驗」的誘惑很大，而那會讓損毀的 pack 產生錯誤的學習內容，比不能用糟得多。

`xor_hash` 用 `XOR(sha256(row))` 而非全表 hash：可增量計算、與列順序無關、apply delta 後能就地更新，不必重掃全表。

# 十、資料品質

## 10.1 六層驗證

| 層 | 檢查 | 執行時機 |
|---|---|---|
| L0 Schema | YAML front matter 必填欄位、enum 白名單、`kg_nodes.attrs` 對 JSON Schema | pre-commit（< 2s） |
| L1 參照完整性 | 所有 id 存在、無孤兒、`prereq`/`next` 指向的單元存在 | pre-commit |
| L2 圖約束 | `PREREQUISITE_OF` 全域無環 + 遞移約簡、`IS_PART_OF` 單一父且深度 ≤ 5、out-degree ≤ 12、孤島偵測 | PR |
| L3 內容 lint | S01–S14 齊全、字數區間、每個結論有 `claim_anchor` 對應的 citation、LaTeX 可編譯、圖片有 alt、授權碼合法、**NC 素材不得 bundle** | PR |
| L4 覆蓋率 | 每 active concept `item_count ≥ 5`、每題恰一 primary、每 concept 至少一條 `ALIGNED_TO` | PR + nightly |
| L5 統計異常 | 見 §10.5 | nightly + release gate |

## 10.2 CI 檢查

```yaml
pre-commit:  L0 + L1（只跑動到的檔案）           目標 < 2 秒
pull-request: L0–L4 全量 + LLM 抽取器黃金集回歸  目標 < 8 分鐘
nightly:     L5 + 影子評估 + 死連結掃描 + 過期素材偵測
release-gate: 全部六層 + pack 產出後的三層完整性驗證，任一不過即擋版
```

## 10.3 匯入前的 dry-run

`content-cli apply --dry-run <changeset>` 必須輸出：

```
變更摘要      新增 42 節點 / 修改 118 / MERGE 3 / SPLIT 1 / RETIRE 7
影響題目      2,341 題需重新掛載（其中 87 題 split_map 未覆蓋 → 人工佇列）
影響使用者    18,442 人的 mastery 會變動
掌握度變動分佈  p50 −0.02  p90 −0.09  p99 −0.31   ← 有 1% 的人掉 0.31，需說明卡
影子評估      top-3 推薦差異率 11.3%（門檻 15%）  ✓
違規          0 blocking / 3 warning
```

沒有 dry-run 的 changeset 不准 apply。這是 CLI 層強制，不是流程規範。

## 10.4 參照完整性的落地

Postgres 有真 FK，直接用。**離線包的 SQLite 不宣告 FK**（`PRAGMA foreign_keys` 的狀態不在 pack 的掌控裡，這一點沿用既有 `004_chats.sql` 的判斷），改成產出時跑一次 `foreign_key_check` 並寫進 `__assertions`——把約束變成**產出時的驗證**而非**執行時的行為**，行為看得見，不依賴連線設定。

## 10.5 統計異常偵測

| 偵測器 | 規則 | 處置 |
|---|---|---|
| `option_rate.distractor_wins` | 某誘答選中率 > 正確選項且 n ≥ 200 | **立即 `auto_quarantine`** + critical errata |
| `p_correct.shift_on_revision` | 新 revision 上線 7 天內正確率偏移 > 15 個百分點且 n ≥ 200 | major errata + 人工複核 |
| `p_correct.extreme` | p < 0.05 或 p > 0.98 且 n ≥ 300 | minor errata（可能是瑕疵題或送分題） |
| `time.too_fast` | 中位作答時間 < 3 秒且正確率 > 90% | 疑似洩題／重複題，查 `variant_of` |
| `discrimination.negative` | 點二列相關 < 0 且 n ≥ 300 | **quarantine**（強者答錯、弱者答對＝題目有問題） |
| `mastery.iqr_collapse` | 某 concept 掌握度分佈 IQR < 0.05 | 題目太少或太同質，進題目擴充佇列 |
| `coverage.regression` | release 後某 Topic 覆蓋率跌破 90% | 擋版 |

`auto_quarantine` 的副作用要一起做：該題的 `srs_state` 全部 `state='suspended'`，正在做的模考該題不計分，且**不追溯扣分**——使用者不該為我們的錯誤付出代價。

## 11.2 查詢熱點

| # | 查詢 | 頻率 | 對策 |
|---|---|---|---|
| 1 | 事件批次寫入 | 尖峰 600–800 writes/s | 分割表 + Queues 緩衝 + 客戶端每 50 筆打包 |
| 2 | 複習佇列 `srs_state WHERE user_id=? AND due_at<=?` | 6 萬 DAU × 20 次/日 | `(user_id, due_at)` partial index；覆蓋索引 |
| 3 | 取題目 revision by id | 極高 | 內容不可變 → Cache-Control immutable，CDN/KV 命中率 > 98% |
| 4 | 混合搜尋 | 6 萬 DAU × 3 次 | GIN + HNSW；離線優先在裝置端解決 |
| 5 | 統計頁聚合 | 6 萬 DAU × 5 次 | **預聚合到 `daily_rollup`**，絕不即時掃事件 |

熱點 5 是最容易寫錯的：`SELECT count(*) FROM learning_events WHERE user_id=? AND occurred_at > ?` 對一個活躍使用者要掃 6 萬列，×30 萬次/日 = 每日 180 億列掃描。在 Postgres 上是 p95 難看，在 D1 上是直接的計費災難（rows read 算掃描列數不是回傳列數）。

## 11.3 D1 夠不夠：逐條判定

| D1 限制 | 我們的數字 | 判定 |
|---|---|---|
| 資料庫上限 10 GB（付費） | 事件 2.4 GB／日 | ❌ **4.6 天撞穿。架構層級不可行** |
| 同上 | 內容+題庫 3.8 GB | ⚠️ 塞得下但無成長空間 |
| 單列／BLOB 2 MB | 離線包 30–60 MB | ❌ 離線包不可能進 D1，必須 R2 |
| 每查詢 ≤ 100 bound parameters | 離線同步一次 200 筆 × 12 欄 = 2,400 | ❌ **直接違規**，必須拆 batch |
| 寫入吞吐約 200 writes/s | 尖峰 600–800 | ❌ 超出 3–4 倍 |
| 中文全文檢索 | FTS5 無 ICU，無自訂 tokenizer 註冊 | ⚠️ bigram 方案可行（不需自訂 build），但索引寫入會吃掉 rows written |
| 向量檢索 | 無 | ❌ 需 Vectorize 或 pgvector |
| 讀取計費（掃描列數） | 統計頁每日 180 億 rows read | ⚠️ 約 $515/月，錢還好但 p95 難看 |

**結論：D1 在新架構裡沒有非它不可的位置。** 保留它的唯一理由是不重寫既有的 auth/admin/watch/AI 點數程式碼（那是實打實的資產），但**新功能一律不進 D1**。

## 11.4 遷移路徑（每階段可上線、可回頭）

```
Phase 0  D1 維持現狀（帳號、審核、訂單、通知）。新的內容庫直接建在 Neon。
         不動任何既有程式碼。            ← 現在就可以開始，零風險

Phase 1  事件流上線：Workers → Queues → Neon learning_events（月分割）。
         裝置端 op-log + 三層去重。掌握度/SRS 的 fold 跑在 Neon。
         D1 完全不碰事件。

Phase 2  內容編譯管線：git → CI → Neon → R2 離線包。
         搜尋（GIN + HNSW）與離線包三層驗證上線。

Phase 3  users/prefs 從 D1 遷 Neon：雙寫 → 每日對帳（count + 逐欄 hash）→
         切讀 → 觀察 14 天 → 停寫 D1。
         D1 剩下的只有「Worker 邊緣需要的低延遲小表」，而那些其實更適合 KV／DO：
         session 黑名單、feature flag、rate limit 計數。

Phase 4  事件熱資料 90 天留 Neon；冷資料每季 Parquet → R2，
         分析走 DuckDB / ClickHouse。Neon 熱資料穩定在 250 GB 上下。
```

回頭機制：Phase 1–3 每一階段的雙寫期至少 14 天，且對帳腳本必須是「逐欄比對」而非「筆數比對」——筆數相同但欄位漂移是遷移最常見的事故，而且只在使用者回報時才會被發現。

## 1. 冪等批次寫入學習事件（三層去重的 L1 + L2）

```sql
-- Worker 端：一次最多 200 筆。D1 有 100 bound params 上限，
-- Neon 沒有，但仍用 unnest 傳陣列 —— 參數數量固定為 12，與批次大小無關。
WITH incoming AS (
  SELECT * FROM unnest(
    $1::uuid[],  $2::uuid[],  $3::uuid[],  $4::bigint[],
    $5::timestamptz[], $6::text[], $7::uuid[], $8::uuid[],
    $9::uuid[], $10::uuid[], $11::jsonb[], $12::text[]
  ) AS t(event_id, user_id, device_id, hlc_ts,
         occurred_at, event_type, item_id, item_revision_id,
         release_id, session_id, payload, idem_key)
),
-- L3：2 秒時間窗折疊（UI 連點）。同 user+item 同秒窗只留 hlc_ts 最小的一筆。
folded AS (
  SELECT DISTINCT ON (user_id, item_id, event_type,
                      floor(extract(epoch from occurred_at) / 2))
         *
    FROM incoming
   WHERE event_type = 'attempt'
   ORDER BY user_id, item_id, event_type,
            floor(extract(epoch from occurred_at) / 2), hlc_ts
),
all_rows AS (
  SELECT * FROM folded
  UNION ALL
  SELECT * FROM incoming WHERE event_type <> 'attempt'
),
ins AS (
  INSERT INTO learning_events (
    event_id, user_id, device_id, hlc_ts, occurred_at,
    event_type, item_id, item_revision_id, release_id,
    session_id, payload, idem_key)
  SELECT * FROM all_rows
  -- L1：event_id 重送
  ON CONFLICT (event_id, occurred_at) DO NOTHING
  RETURNING event_id
)
SELECT
  (SELECT count(*) FROM ins)                                AS inserted,
  (SELECT count(*) FROM all_rows) - (SELECT count(*) FROM ins) AS duplicates;
-- L2 由 UNIQUE (user_id, idem_key, occurred_at) 擋，撞到會拋錯，
-- 呼叫端捕捉 23505 後改用逐筆 ON CONFLICT DO NOTHING 重跑該批。
-- 回傳 inserted 給客戶端推進游標 —— 不能靠 HTTP 200，重試路徑會漏。
```

## 2. 從事件重算單一使用者的掌握度（fold）

```sql
-- fold_version bump 後的重算。全量重算就是對所有 user_id 跑一次。
-- 排除 event_invalidations（答案改過的歷史作答）是關鍵，
-- 少了這個 join 就會用錯誤答案算出錯誤的掌握度，而且沒人會發現。
WITH valid_attempts AS (
  SELECT e.user_id, e.item_id, e.occurred_at, e.hlc_ts,
         (e.payload->>'correct')::boolean AS correct,
         ic.node_id, ic.weight, ic.role
    FROM learning_events e
    JOIN item_concepts ic ON ic.item_id = e.item_id
    LEFT JOIN event_invalidations iv
           ON iv.event_id = e.event_id AND iv.occurred_at = e.occurred_at
   WHERE e.user_id = $1
     AND e.event_type = 'attempt'
     AND e.occurred_at >= now() - interval '18 months'
     AND iv.event_id IS NULL              -- 失效的作答不進 fold
     AND ic.role IN ('primary', 'supporting')
),
-- 時間衰減：半衰期 90 天。近期表現代表現在的掌握度，一年前的不代表。
scored AS (
  SELECT node_id,
         sum(w) AS sw,
         sum(w * CASE WHEN correct THEN 1 ELSE 0 END) AS swc,
         count(*) AS n,
         max(hlc_ts) AS last_hlc
    FROM (
      SELECT node_id, correct, hlc_ts,
             weight
               * CASE role WHEN 'primary' THEN 1.0 ELSE 0.4 END
               * pow(0.5, extract(epoch FROM now() - occurred_at) / (90*86400))
             AS w
        FROM valid_attempts
    ) t
   GROUP BY node_id
),
-- coverage：該概念下已作答的不同題目數 / 該概念的題庫題數，上限 1.0
cov AS (
  SELECT s.node_id, s.sw, s.swc, s.n, s.last_hlc,
         least(1.0, s.n::numeric / greatest(5, n.item_count)) AS coverage
    FROM scored s JOIN kg_nodes n ON n.id = s.node_id
)
INSERT INTO mastery_state (user_id, node_id, mastery, confidence,
                           coverage, n_attempts, n_correct,
                           last_event_hlc, fold_version, updated_at)
SELECT $1, node_id,
       -- coverage < 0.6 一律回 NULL。顯示一個樣本不足的百分比，
       -- 是最快讓學生誤判自己準備程度的方式。
       CASE WHEN coverage < 0.6 THEN NULL
            ELSE round((swc / nullif(sw,0))::numeric, 3) END,
       round(least(1.0, n::numeric / 12)::numeric, 2),
       round(coverage, 2), n, swc::int, last_hlc, $2, now()
  FROM cov
ON CONFLICT (user_id, node_id) DO UPDATE SET
  mastery = excluded.mastery, confidence = excluded.confidence,
  coverage = excluded.coverage, n_attempts = excluded.n_attempts,
  n_correct = excluded.n_correct, last_event_hlc = excluded.last_event_hlc,
  fold_version = excluded.fold_version, updated_at = excluded.updated_at;
```

## 3. 今日複習佇列（最高 QPS 的讀取）

```sql
-- 走 (user_id, due_at) WHERE state<>'suspended' 的 partial index，
-- 不做任何 join 到大表。item 內容另外從 CDN/KV 取（不可變，命中率 >98%）。
SELECT s.item_id, s.due_at, s.state, s.lapses,
       -- 弱點加權：同樣到期的題，主考點掌握度低的先出
       coalesce(m.mastery, 0.5) AS mastery_hint
  FROM srs_state s
  LEFT JOIN item_concepts ic
         ON ic.item_id = s.item_id AND ic.role = 'primary'
  LEFT JOIN mastery_state m
         ON m.user_id = s.user_id AND m.node_id = ic.node_id
 WHERE s.user_id = $1
   AND s.due_at <= now()
   AND s.state <> 'suspended'
 ORDER BY coalesce(m.mastery, 0.5) ASC, s.due_at ASC
 LIMIT 50;

-- EXPLAIN 必須是 Index Scan + Limit，不得出現 Seq Scan 或 Sort。
-- 這支查詢每日跑約 120 萬次，退化成 Sort 就是全站可感知的卡頓。
```

```sql
SELECT
  u.slug                                   AS unit,
  b.block_code,
  r.rev_no, r.change_class, r.change_note,
```

## 6. 中文混合檢索（伺服器端：FTS + 向量 + RRF）

```sql
-- $1 = 使用者原始查詢；$2 = 切詞器產出的空白分隔 bigram 字串；
-- $3 = 查詢的 embedding；$4 = user_id；$5 = 目標考試 code
WITH kw AS (
  SELECT r.entity_id, r.entity_type,
         row_number() OVER (
           ORDER BY ts_rank_cd(r.search_tsv,
                    to_tsquery('simple', $2), 32) DESC) AS rnk
    FROM content_revisions r
    JOIN release_members rm ON rm.revision_id = r.id AND rm.release_id = $6
   WHERE r.search_tsv @@ to_tsquery('simple', $2)
   LIMIT 100
),
vec AS (
  SELECT e.entity_id, e.entity_type,
         row_number() OVER (ORDER BY e.vec <=> $3::halfvec) AS rnk
    FROM embeddings e
   WHERE e.model = 'text-embedding-3-large'
   ORDER BY e.vec <=> $3::halfvec
   LIMIT 100
),
exact AS (      -- 別名／術語精確命中直接置頂
  SELECT n.id AS entity_id, 'kg_node'::text AS entity_type, 0 AS rnk
    FROM kg_nodes n
   WHERE n.lifecycle = 'active'
     AND ($1 = ANY(n.aliases) OR n.label = $1 OR n.slug = $1)
),
fused AS (
  SELECT entity_id, entity_type, sum(1.0 / (60 + rnk)) AS rrf
    FROM (SELECT * FROM kw UNION ALL SELECT * FROM vec UNION ALL SELECT * FROM exact) x
   GROUP BY entity_id, entity_type
)
SELECT f.entity_id, f.entity_type,
       f.rrf
         * (1 + 0.3 * coalesce((n.exam_weight->>$5)::numeric, 0))
         * (1 + 0.4 * (1 - coalesce(m.mastery, 0.5)))          -- 弱點加權
         * CASE WHEN n.stage IS NULL OR n.stage = u.stage_pref THEN 1 ELSE 0.4 END
         * CASE WHEN coalesce(n.lifecycle,'active')='active' THEN 1 ELSE 0.2 END
       AS score
  FROM fused f
  LEFT JOIN kg_nodes n ON n.id = f.entity_id AND f.entity_type = 'kg_node'
  LEFT JOIN mastery_state m ON m.user_id = $4 AND m.node_id = f.entity_id
  CROSS JOIN LATERAL (SELECT 'G10-12'::text AS stage_pref) u
 ORDER BY score DESC
 LIMIT 20;
```

## 7. 裝置端 FTS5 建索引與查詢（bigram 方案）

```sql
-- [SQLite] 離線包產出時建立。content='' 是 contentless：
-- 原文留在 blocks 表，索引不重複存一份，省約 45% 空間。
CREATE VIRTUAL TABLE fts_block USING fts5(
  title,          -- 標題欄（bm25 給高權重）
  term,           -- 詞典命中的術語 unigram（權重次之）
  body,           -- 內文 bigram
  content='',
  tokenize = "unicode61 remove_diacritics 2"
);

-- 寫入（由編譯器產生，值已經是切分器輸出的空白分隔字串）
INSERT INTO fts_block(rowid, title, term, body) VALUES
 (1,
  '二次 次函 函數 二次函數',
  '二次函數 判別式 配方法',
  '二次 次函 函數 數的 的判 判別 判別式 別式 …');

-- 查詢「二次函數」：切分器同樣產出 → phrase + 術語 OR
SELECT rowid,
       bm25(fts_block, 10.0, 6.0, 1.0) AS rank   -- title:10 term:6 body:1
  FROM fts_block
 WHERE fts_block MATCH '"二次 次函 函數" OR term:二次函數'
 ORDER BY rank
 LIMIT 20;

-- 單字查詢「函」退化成 prefix：命中 函數/函式/…，語意上正是使用者要的
SELECT rowid, bm25(fts_block) FROM fts_block
 WHERE fts_block MATCH '函*' ORDER BY 2 LIMIT 20;
```

## 8. 產出離線包的 delta（列級差異）

```sql
-- 比較兩個 release 在某個分片上的差異，輸出寫進 delta SQLite。
-- 用 release_members 而不是比 updated_at：後者無法處理回滾與重新發布。
WITH base AS (
  SELECT rm.entity_id, rm.revision_id
    FROM release_members rm
    JOIN items i ON i.id = rm.entity_id
   WHERE rm.release_id = $1 AND rm.entity_type = 'item'
     AND i.subject_id = $3
),
head AS (
  SELECT rm.entity_id, rm.revision_id
    FROM release_members rm
    JOIN items i ON i.id = rm.entity_id
   WHERE rm.release_id = $2 AND rm.entity_type = 'item'
     AND i.subject_id = $3
)
SELECT coalesce(h.entity_id, b.entity_id) AS item_id,
       CASE WHEN b.entity_id IS NULL THEN 'added'
            WHEN h.entity_id IS NULL THEN 'deleted'
            ELSE 'changed' END AS op,
       h.revision_id AS new_revision_id
  FROM base b FULL OUTER JOIN head h ON h.entity_id = b.entity_id
 WHERE b.revision_id IS DISTINCT FROM h.revision_id;
```

## 9. 離線包完整性：語意層驗證

```sql
-- [SQLite] 產出時寫入 __checksums，裝置端 apply delta 後重算比對。
-- xor_hash 與列順序無關且可增量更新，不必重掃全表。
CREATE TABLE __checksums (
  table_name TEXT PRIMARY KEY,
  row_count  INTEGER NOT NULL,
  xor_hash   BLOB    NOT NULL
);

-- 裝置端驗證（每次 apply delta 後跑一次，約 200ms/40MB）
WITH calc AS (
  SELECT 'items' AS t, count(*) AS c,
         -- SQLite 無內建 xor 聚合，用擴充函式或在應用層算；
         -- 這裡示意，實務由 Rust core 讀出後計算
         NULL AS h
    FROM items
)
SELECT c.t, c.c, k.row_count,
       CASE WHEN c.c = k.row_count THEN 'ok' ELSE 'MISMATCH' END AS verdict
  FROM calc c JOIN __checksums k ON k.table_name = c.t;

-- __assertions：語意層。任一 fail 即整個 pack 標 unusable，回退上一版。
CREATE TABLE __assertions (name TEXT PRIMARY KEY, sql TEXT, expect INTEGER);
INSERT INTO __assertions VALUES
 ('every_item_has_one_primary',
  'SELECT count(*) FROM (SELECT item_id FROM item_concepts WHERE role=''primary''
                          GROUP BY item_id HAVING count(*)<>1)', 0),
 ('no_orphan_media',
  'SELECT count(*) FROM revision_media rm
    LEFT JOIN media_assets a ON a.id=rm.asset_id WHERE a.id IS NULL', 0),
 ('active_concept_min_items',
  'SELECT count(*) FROM kg_nodes WHERE lifecycle=''active''
     AND node_type IN (''Concept'',''Skill'') AND item_count < 5', 0);
```

## 10. 答案改錯：讓歷史作答失效並重排程

```sql
-- errata 確認為 answer_changed 後，一個交易做完三件事。
-- 三件事必須一起成立：只做前兩件，使用者的掌握度還是錯的；
-- 只做後一件，統計還會用舊資料算。
BEGIN;

-- (1) 標記受影響的歷史作答失效
INSERT INTO event_invalidations (event_id, occurred_at, reason, changeset_id)
SELECT e.event_id, e.occurred_at, 'answer_changed', $2
  FROM learning_events e
 WHERE e.item_id = $1
   AND e.item_revision_id = $3          -- 只失效「錯誤的那一版」的作答
   AND e.event_type = 'attempt'
ON CONFLICT DO NOTHING;

-- (2) 受影響使用者的 SRS 轉 relearning，due 提前
UPDATE srs_state SET state = 'relearning', due_at = now(), reps = 0
 WHERE item_id = $1
   AND user_id IN (SELECT DISTINCT user_id FROM learning_events
                    WHERE item_id = $1 AND item_revision_id = $3);

-- (3) 清掉受污染的統計，等 rollup 重算
DELETE FROM item_stats WHERE item_id = $1 AND revision_id = $3;

COMMIT;

-- 之後對受影響的 user_id 集合排入 fold 重算佇列（查詢 2）。
-- 影響人數要寫進 errata.evidence，並觸發一次性說明卡 —— 靜默修正
-- 會讓學生看到掌握度無故變動而沒有解釋，那是最快的信任崩壞路徑。
```

## 11. 統計異常偵測：誘答勝出（critical，自動隔離）

```sql
WITH suspect AS (
  SELECT s.item_id, s.revision_id, s.n_attempts,
         (SELECT option_key FROM item_options_flat o
           WHERE o.revision_id = s.revision_id AND o.is_correct
           LIMIT 1) AS correct_key,
         s.option_rates
    FROM item_stats s
   WHERE s.window = 'd30' AND s.n_attempts >= 200
),
flagged AS (
  SELECT item_id, revision_id, n_attempts, correct_key,
         (option_rates ->> correct_key)::numeric AS p_correct_opt,
         (SELECT max((v)::numeric) FROM jsonb_each_text(option_rates) AS e(k,v)
           WHERE k <> correct_key) AS p_best_distractor
    FROM suspect
)
```

## 12. 統計異常偵測：改版後正確率偏移

```sql
SELECT a.item_id,
       a.revision_id AS old_rev, b.revision_id AS new_rev,
       a.p_correct AS p_old, b.p_correct AS p_new,
       round(b.p_correct - a.p_correct, 3) AS shift,
       b.n_attempts,
       r.change_class, r.change_note
  FROM item_stats a
  JOIN item_stats b ON b.item_id = a.item_id AND b.window = a.window
  JOIN content_revisions r ON r.id = b.revision_id
 WHERE a.window = 'd30'
   AND r.rev_no = (SELECT rev_no FROM content_revisions
                    WHERE id = a.revision_id) + 1
   AND b.n_attempts >= 200 AND a.n_attempts >= 200
   AND abs(b.p_correct - a.p_correct) > 0.15
   -- cosmetic 改動不該讓正確率動 15 個百分點，那代表改動被錯誤分級
   AND r.change_class IN ('cosmetic', 'clarify')
 ORDER BY abs(b.p_correct - a.p_correct) DESC;
```
