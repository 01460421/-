
## area
考試準備 App 的自適應練習與能力評估引擎（能力估計、CAT 診斷、題目校準、間隔重複、知識點圖譜、出題策略、錯題根因分析）

## summary
整體架構建議收斂成「一個共用 logit 尺度 + 三個狀態層 + 一個排程器」，而不是把 IRT / BKT / SRS 當三套獨立系統各做各的。

共用尺度：所有東西都活在 logit 空間。使用者能力 θ（全域一個 + 每個知識點 KC 一個）、題目難度 b、掌握度 m = σ(θ_kc)，彼此可互轉。這是最重要的架構決策——它讓 CAT 選題、日常出題、SRS 到期判斷、根因分析全部用同一組數字對話。

三個狀態層（更新頻率由快到慢）：
1. 能力層：每個 (user, kc) 的 θ_kc 與不確定度 σ_kc。每次作答用 Elo-style 線上更新，裝置端純算術，O(1)。
2. 記憶層：每個 (user, kc) 的 FSRS 記憶狀態 (S, D)，回答「這個知識點在考試當天還記得多少」。只在複習事件時更新。
3. 參數層：題目的 IRT 參數 (a, b, c) 與健康度指標。全域共享，離線批次校準，只能上雲。

關鍵區分：θ 表達「學會的程度」，R（FSRS 保留率）表達「現在提取得出來嗎」。把兩者混成一個數字是最常見的設計錯誤——一個學生可能 θ 很高但三週沒碰所以 R=0.4，處方是「複習」；也可能 R=0.95 但 θ 低，處方是「重學」。兩種情況要走完全不同的分支。

排程器是唯一的決策入口，每次出題做一次加權排序：
priority = w1·(考試日遺忘風險) + w2·(藍圖權重 × 能力缺口) + w3·(先備知識阻塞) − w4·(挫敗風險)
再在候選集上套交錯練習與目標成功率約束。這比「SRS 佇列 + 弱項佇列 + 新題佇列」三條佇列互搶好維護得多。

最關鍵的取捨：這類產品的失敗模式幾乎不是「演算法不夠先進」，而是「題目參數沒校準」。所以第一版應把工程量壓在 Rasch + Elo + 規則式，省下的力氣全投到題目標註品質（q-matrix、誤概念選項對應、答案正確性）——標註品質對最終體驗的貢獻遠大於把 DKT 換成 AKT。

深度知識追蹤的誠實結論：Gervet et al.（JEDM 2020）的結論是，在中等規模資料上帶對特徵的邏輯迴歸（Best-LR / DAS3H）勝過 DKT；DKT 只在資料量很大或時序精度特別重要時領先。所以 DKT/SAKT/AKT 第一版明確不建議，第二版也只建議做特徵化邏輯迴歸這個中間形態。

## data_structures
以下用 PostgreSQL 語法。裝置端用 SQLite，schema 為子集（標註 [D] 者需同步到裝置）。

━━━━━━━━━━ 內容層（唯讀下發，[D]）━━━━━━━━━━

-- 知識點
CREATE TABLE kc (                                    -- [D]
  kc_id        BIGINT PRIMARY KEY,
  subject_id   INT NOT NULL,
  code         TEXT NOT NULL,           -- 'MATH.ALG.QUAD.VERTEX'
  name         TEXT NOT NULL,
  level        SMALLINT,                -- 階層深度，用於 UI 摺疊
  blueprint_w  REAL DEFAULT 0,          -- 考試藍圖權重，Σ=1（每科）
  est_learn_items SMALLINT DEFAULT 10,  -- 預估掌握所需題數，用於路徑成本
  UNIQUE(subject_id, code)
);

-- 先備知識 DAG
CREATE TABLE kc_edge (                               -- [D]
  parent_kc  BIGINT REFERENCES kc,      -- 先備
  child_kc   BIGINT REFERENCES kc,
  strength   REAL DEFAULT 1.0,          -- (0,1] 依賴強度
  PRIMARY KEY (parent_kc, child_kc)
);
-- 寫入時用 Kahn 演算法檢查無環。
-- 另存一張預計算的傳遞閉包，查詢祖先/後代 O(1)：
CREATE TABLE kc_closure (                            -- [D]
  ancestor_kc BIGINT, descendant_kc BIGINT,
  distance    SMALLINT,                 -- 最短路徑長度
  path_weight REAL,                     -- 路徑上 strength 的乘積（取最大者）
  PRIMARY KEY (ancestor_kc, descendant_kc)
);

-- 題目
CREATE TABLE item (                                  -- [D]（分批下發）
  item_id      BIGINT PRIMARY KEY,
  subject_id   INT NOT NULL,
  item_type    SMALLINT,                -- 1=單選 2=多選 3=填空 4=計算 5=分步
  n_options    SMALLINT,                -- 用於 3PL 的 c 固定值
  content_hash TEXT,                    -- 偵測重複題
  is_atomic    BOOL DEFAULT FALSE,      -- 只考單一 KC，供先備探測用
  enemy_group  BIGINT,                  -- 同組題不可出現在同一次測驗
  author_diff  SMALLINT,                -- 出題者標的難度 1/2/3，冷啟動先驗
  status       SMALLINT DEFAULT 0,      -- 0=pilot 1=provisional 2=calibrated 3=quarantined 4=retired
  created_at   TIMESTAMPTZ
);

-- q-matrix：題目 → 知識點
CREATE TABLE item_kc (                               -- [D]
  item_id BIGINT REFERENCES item,
  kc_id   BIGINT REFERENCES kc,
  weight  REAL NOT NULL,                -- 同一 item 的 Σweight = 1
  qm_corr REAL,                         -- 驗證用：corr(θ_kc, 該題得分)，離線算
  PRIMARY KEY (item_id, kc_id)
);
CREATE INDEX ON item_kc (kc_id, item_id);

-- 選項與誤概念對應（根因分析的核心資產）
CREATE TABLE item_option (                           -- [D]
  item_id       BIGINT,
  option_idx    SMALLINT,
  is_correct    BOOL,
  misconception_id BIGINT,              -- NULL 表示無特定誤概念
  is_near_miss  BOOL DEFAULT FALSE,     -- 此值 = 某中間量，暗示題意誤解
  numeric_value NUMERIC,                -- 數值題用，算「與正解的距離」
  select_rate   REAL,                   -- 全域被選率，離線更新
  mean_theta    REAL,                   -- 選此項者的平均 θ，壞題偵測用
  PRIMARY KEY (item_id, option_idx)
);

CREATE TABLE misconception (                         -- [D]
  misconception_id BIGINT PRIMARY KEY,
  kc_id      BIGINT,
  name       TEXT,                      -- '把 (a+b)² 展開成 a²+b²'
  counter_example_id BIGINT,            -- 針對性反例素材
  probe_item_ids BIGINT[]               -- 確認是否已修正的診斷題
);

-- 容易混淆的知識點對（交錯練習用）
CREATE TABLE confusion_pair (                        -- [D]
  kc_a BIGINT, kc_b BIGINT,
  weight REAL,                          -- 混淆強度，離線挖掘
  PRIMARY KEY (kc_a, kc_b)
);

CREATE TABLE item_param (                            -- [D]

  a            REAL DEFAULT 1.0,
  a_se         REAL,
  c            REAL DEFAULT 0.0,        -- 固定為 0.8/n_options
  n_responses  INT DEFAULT 0,           -- 去重後的有效作答數
  resp_theta_sd REAL,                   -- 作答者 θ 的 SD，<0.8 表示校準無效
  median_ms    INT,                     -- 作答時間中位數，根因分析用
  p25_ms INT, p75_ms INT, p90_ms INT,
  calibrated_at TIMESTAMPTZ,
  prev_b       REAL                     -- 上次校準值，偵測漂移（|Δb|>0.5 告警）
);
CREATE INDEX ON item_param (b);          -- CAT 選題按 b 分桶掃描

CREATE TABLE item_health (
  item_id       BIGINT PRIMARY KEY,
  r_pbis        REAL,                   -- 點二列相關，<0.10 可疑
  outfit_msq    REAL, infit_msq REAL,   -- >1.4 雜訊過大，<0.6 過度可預測
  high_theta_fail_rate REAL,            -- P(答錯|θ>1.5)，>0.5 強烈暗示答案錯
  worst_distractor_theta_gap REAL,      -- 最佳干擾項與正解的 mean_theta 差，<0 危險
  flags         TEXT[],                 -- {'low_discrimination','answer_suspect',...}
  reviewed_at   TIMESTAMPTZ,
  reviewer_note TEXT
);

CREATE INDEX ON attempt (item_id, server_ts DESC);

━━━━━━━━━━ 裝置端 vs 雲端的分工總表 ━━━━━━━━━━

【裝置端計算，離線可用】
Elo θ 更新、BKT P(L) 遞迴、EAP 能力估計（41 點求積）、CAT 選題與停止判定、
FSRS 排程與 21 參數個人化最佳化、deadline-aware 優先度計算、交錯約束修復、
目標成功率反解與閉迴路修正、挫敗偵測與介入、規則式根因分類、DAG 責任歸因。
→ 全部是 O(1) 或 O(小 n) 的算術，SQLite + 幾百行程式碼。使用者在飛機上也能完整使用。

【必須上雲，需跨使用者資料】
題目 IRT 參數校準（JMLE/MMLE-EM）、壞題偵測全套指標、干擾項統計、
q-matrix 驗證、全域曝光率統計、誤概念挖掘、混淆對挖掘、
Best-LR/DAS3H 訓練、LLM 輔助的離線內容生成。
→ 夜間批次，結果以參數表形式下發（2 萬題約 320KB，可增量同步）。

【同步協定】
裝置端只上傳 attempt 事件（append-only，用 ULID 保證冪等）。
所有能力/記憶狀態視為可從事件重放的衍生值——這讓「題目被 quarantine 後回溯重算 θ」
變成一個純粹的重放操作，而不需要複雜的補償邏輯。這個決定在第一版就要做對。

## implementation
━━━━━━━━━━ 第一版最小可行引擎（MVP）━━━━━━━━━━

一句話：**Rasch + Elo 一套能力估計 + FSRS-6 一套記憶模型 + 一個加權排程器 + 一組規則式診斷**。
全部跑在裝置端，雲端只做夜間題目校準與壞題偵測。程式碼量約 2500-4000 行（不含 UI）。

【模組清單與建置順序】

**Week 1-2：事件骨架**
先把 `attempt` 表與同步協定做對，其他都可以之後改。
關鍵：attempt_id 裝置端生成（ULID），server 端冪等寫入；所有狀態都標記為「可從事件重放」。
這是唯一一個之後很難改的決定。

**Week 2-3：Elo 能力層**
```
fun onAttempt(u, item, y):
    kcs = qmatrix[item]                          # [(kc, w)]
    theta_eff = Σ w·θ[u][kc]
    p = sigmoid(theta_eff − b[item])
    Ku = 0.8 / (1 + 0.05·n[u])
    for (kc, w) in kcs:
        θ[u][kc] += w · Ku · (y − p)
        σ²[u][kc] = 1 / (1/σ²[u][kc] + p·(1−p))
    θ[u][GLOBAL] += 0.5·Ku·(y − p)
    bkt_update(u, kcs, y)                        # 供 UI 顯示掌握度
    if item.status != PILOT:
        queue_item_delta(item, p − y)            # 上傳給伺服器彙總
```

**Week 5-6：排程器（核心）**
```
fun buildSession(u, n_items):
    d = days_until_exam(u)
    r_target = 0.85 if d>60 else 0.88 if d>30 else 0.92 if d>7 else 0.96
    p_star   = 0.85                                # 學習模式
    
    # 1) 對每個 kc 算優先度
    for kc in active_kcs(u):
        urgency  = blueprint_w[kc] · max(0, r_target − r_at_exam[u][kc])
        gap      = blueprint_w[kc] · max(0, 0.7 − mastery[u][kc])
        blocked  = Σ_{p ∈ unmastered_ancestors(kc)} 0.5·(1 − mastery[u][p])
        frustr   = max(0, 0.6 − mastery[u][kc]) · recent_fails[u][kc]
        prio[kc] = 3.0·urgency + 1.5·gap + 1.0·blocked − 1.2·frustr
    
    # 2) 新內容截止線
    if d <= 7:      candidates = seen_kcs_only
    elif d <= 21:   candidates = seen_kcs + top30pct_blueprint_new
    else:           candidates = all_kcs
    
    # 3) 按優先度取 kc，每個 kc 選題
    b_star = θ[u][kc] − logit(p_star) − delta[u]   # 閉迴路修正
    pool = items_of(kc)
                .filter(status ∈ {provisional, calibrated})
                .filter(not_seen_in_60d)
                .filter(not_in_used_enemy_groups)
    pick from top-5 by |b_i − b_star|, randomly       # randomesque
    
    # 4) 交錯約束修復
    seq = repair_interleaving(seq)     # 同 kc 不連續>2；精熟 kc 插混淆對
    
    # 5) 混入 2 題 pilot
    return seq
```

**第 1.5 版（上線後 2-3 個月，有了資料）**
- FSRS 個人化參數（使用者達 400 筆 review_log 就在裝置端跑一次 MLE）

**第 2 版（6-12 個月，資料量到位）**

**明確的不做清單**
DKT/SAKT/AKT（除非單科作答數 > 500 萬且已驗證 Best-LR 不足）、MIRT、
Sympson-Hetter、即時 LLM 歸因。

━━━━━━━━━━ 上線前必須有的觀測指標 ━━━━━━━━━━

模型健康：
- **校準度**：把 p_predicted 分 10 桶，畫實際答對率 vs 預測。這是最重要的單一指標，
  比 AUC 有用得多——AUC 好但校準差的模型會系統性出錯難度的題。
  目標：每桶偏差 < 0.05。
- Brier score（分模式、分能力段）
- FSRS 的 R 預測校準（同樣分桶檢查）
- 實際 session 正確率 vs p_star 的偏差（應該被 delta 修正吸收到 ±0.03 內）

題庫健康：
- calibrated / provisional / pilot / quarantined 的題數比例
- 每個 KC 的可用題數（< 20 題的 KC 要告警，CAT 會選無可選）
- 全域曝光率分布的 P95（> 0.3 表示題庫太小或選題太集中）

使用者體驗：
- 連續錯 3 題以上的 session 佔比（應 < 10%）
- 挫敗保護的觸發率與觸發後的續做率
- 根因診斷的「判斷不對」回饋率（> 15% 表示規則要調）
- 診斷報告完成率（15 分鐘測驗的中途放棄率）

[
 "【最重要】資料太少時，所有花俏演算法都不如簡單規則。冷啟動期（每題 < 100 筆作答、每使用者 < 50 題）的最佳策略就是：按考試藍圖權重出題、難度用出題者標籤、複習用固定間隔 1/3/7/14 天。此時上 IRT 或 DKT 不只沒有增益，還會因為參數估計的雜訊而**主動變壞**——一個 b_se=1.2 的難度估計拿去選題，比直接用「易/中/難」三級標籤更糟。建議把「n_responses 是否足夠」寫成程式碼中的顯式分支，而不是假設模型永遠可用。",
 "把「能力 θ」與「記憶保留率 R」混成一個數字，是這類系統最常見也最致命的架構錯誤。學過但忘了（θ 高、R 低，處方是複習）與沒學會（θ 低、R 高，處方是重學）需要完全不同的介入。一旦混成一個「掌握度」數字，這兩種情況就永遠分不開了，而且之後幾乎無法重構。",
 "SRS 的單位選錯。用「單題」當 SRS 卡片會導致同一個概念被排程 N 次（N = 該概念的題數），複習量爆炸且高度重複；用「知識點」才對應「我還記得這個觀念嗎」。但知識點也不能太粗——建議是 (kc × card_kind)，其中 card_kind 區分觀念回想／程序執行／應用辨識，因為這三者的遺忘速率確實不同。",
 "q-matrix（題目→知識點標註）的品質是整個系統的天花板，而且它是**沉默地**失效的。標錯的 q-matrix 會讓 DAG 責任歸因、KC 掌握度、補救路徑全部給出看似合理但實際錯誤的結果，而所有離線指標（AUC、校準度）看起來都正常。必須有資料驗證：定期算 corr(θ_kc, 該題得分)，接近 0 的標註要人工複查。這件事沒人會主動做，要排進 sprint。",
 "題目答案標錯的機率遠比你以為的高（實務上 0.5%-3%）。而「高能力者答錯率」這個單一指標就能抓到大部分，成本是幾行 SQL。不做這件事的代價是：一個真的學會了的使用者被系統判定為不會，被塞進補救路徑，然後去論壇抱怨。這種負面體驗的傳播力遠大於正面體驗。",
 "CAT 用點估計 θ 選題，在前 3-5 題會嚴重不穩（此時 θ̂ 基本上是雜訊），導致早期選題品質很差。必須用後驗期望訊息量 E[I] = Σ I(X_k)·posterior(X_k)，成本幾乎為零但改善顯著。同理，15 分鐘診斷絕不該輸出點估計分數——2 題就宣稱「你幾何弱」是統計上不誠實的，且一旦使用者感覺被誤判，產品信任很難修復。輸出三級後驗機率並在信心不足時明說「資料不足」。",
 "2PL 的鑑別度 a 在作答數 < 500 時估出來的值雜訊極大，用它做選題（訊息量有 a² 項）會讓系統瘋狂偏好一批其實只是運氣好估出高 a 的題。第一版算 a 但只拿它當品管訊號，不拿去選題。",
 "Elo 的 K 值若不隨經驗衰減，老使用者的 θ 會永遠在雜訊中震盪（連對三題就跳 +0.5，這在 UI 上表現為能力曲線像股票 K 線）。K = α/(1+β·n) 這個衰減不是可選的優化，是必需的。",
 "BKT 的四參數在 EM 擬合時會落入退化解（學到 P(G)>0.5，即「答對表示不會」），這種解在 likelihood 上完全合法但語意荒謬。必須硬 clamp P(G)<0.5、P(S)<0.5。第一版直接用固定參數不擬合，避開整個問題。",
 "交錯練習會讓當下正確率下降 5-15%，使用者的主觀感受是「我變差了」或「系統在亂出題」。這是有實證支持的介入，但**沒有配套溝通就會造成流失**。必須在 UI 上明說「這是混合練習，會比較難，這是刻意的」，並用「長期記憶預估」而非「本次正確率」當回饋。演算法正確但溝通錯誤，淨效果是負的。",
 "傳統 SRS 假設無限期記憶，備考不是。直接套 Anki 的排程會在考前一天安排 45 天後的複習，並且會在考前 3 天還在引入全新內容（那些內容的 S≈2.3 天，根本撐不到考試）。「距考試 ≤7 天停止引入新內容」這條規則對成效的影響可能大於任何演算法選擇，但幾乎所有 SRS 產品都沒做。",
 "把單次粗心誤判成「概念不懂」並塞一堆基礎題，是最傷害使用者信任的行為之一。粗心的正確處方是**不處理**——只記錄，不介入。根因分類的信心門檻要設高（>0.55 才顯示），寧可少說也不要說錯。錯誤的歸因比沒有歸因更糟。",
 "「越弱越練」是自適應系統的天然失控迴圈：使用者最弱的 KC 被優先排程 → 答錯 → 更確定是弱項 → 更優先排程 → 挫敗 → 流失。必須在排程優先度中顯式扣除 frustration_risk 項，並且極弱的 KC 應該先走補救路徑（學先備）而非直接反覆練該 KC。",
 "過度保護同樣致命。持續給簡單題會讓學習停滯，而且使用者會察覺「這 App 在哄我」——這比讓他挫敗更傷害產品信任，因為它讓所有正向回饋都變得沒有意義。保護模式必須有硬上限（最多 8 題、簡單題佔比 <20%、連對 5 題立即退出）。",
 "題目參數會隨時間漂移，主因是題目外流（答案被公開討論導致答對率虛高）。若不做漂移偵測，題庫會慢慢變成「大家都答對的題」，而系統誤以為使用者能力提升了。每季重校準並對 |Δb| > 0.5 的題目告警。",
 "狀態沒有設計成「可從事件重放」，會讓壞題回溯變成不可能的任務。一旦某題被判定答案錯誤並 quarantine，所有受它影響的 θ 都應該重算——如果你的 θ 是就地更新的（沒有保留事件），這件事只能放棄，於是那批使用者的能力估計永久被污染。attempt 表 append-only + 狀態可重放，這個決定必須在第一版就做對，之後補的成本極高。",
 "FSRS 需要 4 級評分而備考作答是二元對錯，中間的映射（用作答時間切 Hard/Good/Easy）是整個記憶模型中最脆弱的環節。時間門檻必須按題型分別校準（計算題與觀念題的時間分布完全不同），而且要排除異常值（使用者中途去接電話會產生 30 分鐘的作答時間）。建議 clamp 到 P99 並排除 > 5 分鐘的樣本。",
 "DAG 責任歸因如果只做機率推論不做驗證，會產生「看似深刻但實際錯誤」的診斷。必須有原子題探測這一步——而這意味著每個 KC 至少要有 6 題只考單一 KC 的題目，這是內容建置的硬需求，必須在題庫規劃階段就納入，不能事後補。",
 "評估模型時看 AUC 而不看校準度，是這類系統最常見的評估錯誤。AUC 只衡量排序能力，但選題需要的是**準確的機率值**——一個 AUC 0.82 但系統性高估 8% 的模型，會持續出比目標更難的題，使用者體感是「這 App 老是給我不會的」。校準曲線（p_predicted 分桶 vs 實際答對率）才是該盯的指標。",
 "LLM 即時歸因看起來很誘人但實務上三重失敗：延遲 1-3 秒（打斷作答節奏）、每次作答一次呼叫的成本、以及同樣情況給不同答案的不一致性（使用者會發現）。LLM 的正確位置是離線批次生成結構化知識（誤概念、反例、步驟標註），線上只查表。",
 "不要一次上線全部功能就開始調參。先讓 Elo + FSRS + 固定規則跑 4-6 週累積校準資料，再逐步開啟適性選題、根因分類、診斷報告。原因是這些模組彼此耦合——如果同時上線，出問題時你無法知道是選題邏輯錯、參數校準差、還是根因規則的門檻設錯。"
